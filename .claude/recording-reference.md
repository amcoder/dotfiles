# Screen recording reference

The full notes behind `rules/recording.md`: how each fact there was established, what was measured, and what was tried first. Moved verbatim from CLAUDE.md.

**Screen recording** (`.local/bin/record-region`, `services/RecordingService.qml`, `modules/bar/Recording.qml`): `$mod+Ctrl+p` toggles a wf-recorder capture, sitting beside the two grimshot screenshot binds it is the moving-picture half of. Files land in `$(xdg-user-dir VIDEOS)/Recordings`, timestamped with dashes rather than `date -Ins`'s colons, which are legal in a filename and a nuisance in every app the file is later dragged into. Video only — wf-recorder's `-a` is what would add audio.

**Left to itself wf-recorder follows the output's refresh rate**, which on the G9's 240Hz mode is a 240fps recording that nothing wants, so `RecordingService.framerate` pins it at 60. Measured over the same 8s capture of one window: the default produced 1853 frames and 1.5MB, `-r 60` 478 frames and 396KB, `-r 30` 239 and 236KB. The duplicate-DTS warnings a 240fps file drew from `ffmpeg -f null` did **not** reproduce across that comparison, so they are not the framerate and remain unexplained; every one of the three decoded clean.

The selection is **`grimshot anything`'s, exactly**: every visible window's rect goes to slurp on stdin and `-o` adds one more per output, so a click picks a window or a whole screen and a drag picks an arbitrary area. It stays a script rather than moving into the service because the jq filter is full of backslashes, which a QML string eats — the same trap `LauncherService`'s embedded awk is written around.

**wf-recorder finalises its container on SIGTERM and not only on SIGINT, and that is what lets the recorder be a quickshell `Process`.** Measured with a SIGKILL control, since exit status alone proves nothing here — all three exit 0: SIGINT and SIGTERM both leave a `moov` atom and a playable file, SIGKILL leaves a 48-byte `ftyp`/`free`/`mdat` stub with no `moov`. So `running = false` saves the recording, and a `systemctl --user restart quickshell` **stops** one rather than truncating it. This is the deliberate exception to the rule that apps are launched with `I3.dispatch("exec …")` and never as a `Process`: that rule is about surviving a shell restart, and here being stopped by one is the correct behaviour, since the indicator that stops a recording goes away with the shell.

**The `exec` in the recorder's `sh -c` is load-bearing.** Without it the shell stays the process and takes the SIGTERM, leaving wf-recorder orphaned and the container never finalised; with it the recorder is a direct child of quickshell, which is how to check it (`ps -o ppid=` on the wf-recorder pid).

**wf-recorder writes limited-range YUV and tags it full-range**, so every recording came out washed out until the file was tagged for what it actually contains: `-p color_range=tv -p colorspace=bt709 -p color_primaries=bt709 -p color_trc=bt709`. Left alone it produces `yuvj420p` with `color_range=pc` while the samples occupy 16-235, so a player that honours the tag does no expansion and blacks sit at ~22 instead of 0.

The reason this is worth writing down is that **it presents as a player bug and is not one**: mpv honours the tag and looked washed out, VLC guesses limited range and looked correct, so the file appeared fine in half the places it was opened. mpv is the honest reporter here.

Measured against a `grim` capture of the same frame, which is the ground truth for this — record a region, grab it with grim while recording, extract the frame and difference the two. Mean per-channel error over the frame, rendered **by mpv**: 23.18 before, 0.79 after. The fitted transfer on the broken file was `0.8328*ref + 16.40` against the textbook limited-range squeeze of `0.8588*ref + 16`, and expanding by `(v-16)*255/219` by hand took the error from 14.02 to 1.01, which is what identified the mechanism. `-x yuv420p` does **not** help — wf-recorder overrides it and the file is still tagged `pc`. `-F "scale=out_range=full"` is the other repair, making the data match the existing full-range tag, and it measured slightly worse (1.55) as well as leaving a full-range h264 file that anything ignoring the flag will crush.

**wf-recorder also converts with BT.601 whatever the frame size**, which is a second and subtler mismatch, since the file is HD and any player guessing a matrix by resolution guesses BT.709. Measured directly by pushing pure red through the same conversion: Y comes out 81 (BT.601) at 320x240, 1280x720 and 1280x1408 alike, where BT.709 would be 63. So it does not vary with the monitor or the mode — and the default codec is software libx264, not anything the GPU picks, so it does not vary with hardware either. `-F "scale=out_color_matrix=bt709"` converts with the right matrix, which is better than re-tagging the file BT.601 because it leaves the samples and the tags and the resolution guess all saying the same thing. wf-recorder confirms it took the filter by logging `Using video filter: scale=out_color_matrix=bt709,fps=60`.

Confirmed end to end against a deliberately colourful, motionless page (`|BT.601-BT.709|` luma averaging 3.45 across the frame against 0.3 for the usual dark desktop, and zero motion between two `grim` grabs two seconds apart — both worth checking before trusting a run of this). The control and the fix come out mirror images: with no filter the Y plane matches BT.601 at 0.963 against BT.709's 3.486, with it BT.709 at 1.020 against BT.601's 3.499, and over the 632k pixels where the matrices actually disagree the split is 1.4 vs 9.9 and 9.8 vs 1.6. Rendered by mpv the whole-frame error halves, 3.70 to 1.74, and on saturated pixels falls 8.13 to 2.94.

**Do not test a matrix with a whole-frame colour average.** An earlier pass concluded from one that the data was already BT.709 and tagged it so, which was wrong: on a dark, low-saturation desktop the two matrices never predict a luma more than 3 apart, so the average has no power to separate them and simply reported noise. The test with power is the **Y plane**, which 4:2:0 does not subsample — predict luma from a `grim` capture under each matrix and difference it against the actual plane. That gave BT.601 a mean error of 0.313 (median 0.115, i.e. rounding) against BT.709's 0.647, on the same frame where the colour average had preferred BT.709.

**wf-recorder does not exit on a region it cannot capture.** Handed one outside any output it prints `Invalid region to capture: must be completely inside the output`, falls back to `selected region 0,0 0x0`, and goes on running — so a drag spanning two outputs would otherwise report a saved file with nothing in it. The service reads stderr with a `SplitParser` and not a `StdioCollector`, which buffers until the stream ends while this message is printed with the process still running, then stops the recorder, deletes the file and notifies. Exercised with a synthetic off-screen geometry rather than a real cross-output drag, this machine having one output.

The bar item is a red Phosphor `record` icon and the elapsed time, shown only while recording and clicking to stop, and its `visible: RecordingService.active` binding is also what warms the singleton — reached otherwise only over IPC, it would never be created and its `IpcHandler` never register. It hangs off the clock's **left** edge in the centre section, mirroring the media item on the right, so it grows outward rather than displacing anything: measured across the indicator appearing, the columns from the clock's left edge rightward are byte-identical, and only the 70px to its left change. Park the pointer before comparing two `grim` captures of the bar — the cursor is composited into the capture and lands right where the clock is.
