# Backup reference

The full notes behind `rules/backup.md`: how each fact there was established, what was measured, and what was tried first. Moved verbatim from CLAUDE.md.

**Backup** (`.local/bin/backup`, `.config/systemd/user/backup-{daily,weekly,yearly}.{service,timer}`): an rsync-over-ssh snapshot of `$HOME` to `backup@beedle:/volume1/backup/impa/amcoder`, rotated `--link-dest` style against `latest`. It runs as **systemd timers**, having previously run under a user-level **anacron** (`@hourly` in the user crontab, jobs in `~/.anacron/etc/anacrontab`, now commented out with a pointer).

The move off anacron is not cosmetic: anacron mails its output, and **mail on this machine is broken**, so the job failed silently for eighteen months. `sendmail.service` is `disabled; preset: enabled` with nothing listening on 127.0.0.1:25, and ~4000 messages sit in `/var/spool/mqueue-client` as `Deferred: Connection refused by [127.0.0.1]`. The last delivery into `/var/mail/amcoder` was 2026-06-13, days after the sendmail unit file was replaced on 2026-06-09. **So the mailbox is not a complete record of anything** — it held 334 anacron failures and zero successes, but stopped in May 2026 until the queue was flushed; it now runs to 2026-09-04. Ground truth for whether a backup ran is the NAS: the `latest` symlink and the `daily.N` mtimes, which showed the last success was 2026-04-17 and only three in the preceding fourteen months. Anacron's own spool timestamps prove nothing either — it records the date whether the job succeeded or failed.

The failures show **one root cause producing two symptoms in a cycle**, and the mail is what dates it. Through Jan 2026 it was `kex_exchange_identification: read: Connection reset by peer`, the DSM auto-block (see NAS mounts). From Jan 2026 it was `Too many authentication failures` — the same `Host *  IdentityAgent` problem wearing a different hat: six agent keys offered ahead of `beedle-back`'s own `IdentityFile`, against `MaxAuthTries 6`, so ssh never reached the right key. The changeover is when the keys moved into 1Password. From Jul 2026 the two **interleave in the same months** (Jul: 16 blocked / 17 auth, Aug: 25 / 10), which is the loop closing: six offers a run accumulate failed logins, those trip the auto-block, the block produces pre-banner resets until it lapses, and it starts over. That interleaving is why the block was never continuous — a successful sshfs mount on 2026-08-23 sits in the middle of it — and it is what makes "the key offers earned the block" evidenced rather than merely plausible. `IdentitiesOnly` cuts the loop at its source.

Three things about the units. `OnFailure=backup-failed@%n.service` sends a desktop notification through quickshell's notification daemon, and the handler must interpolate **`%i`, never `%I`** — `%n` is inserted unescaped, so unescaping it again turns `backup-daily.service` into `backup/daily.service` and hands you a `journalctl` line that does not work. **A NAS that is not on this network is not a failure**, so an `ExecCondition` probes `beedle:22` first; it has to normalise the probe to exit 1, because ExecCondition treats 1–254 as *skip* and 255 as *failure*, and 255 is exactly what ssh returns for a connection error — hence `nc -z` rather than `ssh true`. And `LogRateLimitIntervalSec=0` is set because `rsync -v` is a line per transferred file, which on a first run is enough to trip journald's rate limit and drop the very error the unit exists to report; for the same reason the script's rsync flags lost `-P` (progress, which had no consumer once output stopped going to mail) while keeping `--partial`.

`Persistent=true` gives the catch-up-after-downtime behaviour anacron provided — which also means **enabling a timer with `--now` fires an immediate catch-up run**, so do not do it while a backup is already in flight.

**A non-zero rsync exit discards the whole backup**, and that is the second bug behind the eighteen-month gap — independent of ssh, and one that would have kept failing every night after the auth fix. The script `exit`s on any non-zero code, so the rotation never runs: the temp directory is never renamed to `daily.0` and `latest` is never moved. Measured on the first repaired run: rsync sent 8.62G of 189G (21.91x speedup off `--link-dest`) and returned **23** — partial transfer — because of exactly 32 files under `projects/jbt/jbt-db/db-data/`, owned by uid 10001 inside a container and mode `rw-r-----`, which `amcoder` cannot read. A 99.99%-complete backup was thrown away. That is also what left six `daily-tmp-2025-02-22T*` directories on the NAS. The 86G `db-data` tree is now excluded — raw files of a live database are not a consistent snapshot anyway — and **code 24 is tolerated** (source files vanished mid-transfer, routine on a live `$HOME`) while 23 deliberately still fails, so a *new* unreadable path is loud rather than silent.

`fumon` — uwsm's "failed units monitor", running as `fumon.service` — already notifies on any user unit that fails, which is how the failed sshfs mounts were visible at all. It is *why* moving the backup onto systemd fixes the reporting even before `OnFailure`: under anacron the job was not a unit, so nothing watched it. The `backup-failed@` handler is kept anyway because it names the unit and the `journalctl` line to run, where fumon reports only that something failed.

**`backup_exclude` is a deny-list, and the failure mode of a deny-list is silence** — a new app drops a cache somewhere and it is backed up until somebody notices. Two things address that, and inverting to an allow-list is deliberately not one of them: it trades "backed up some junk" for "silently did not back up your data", which for a backup is the worse failure.

The first is **writing patterns by class rather than by path**. The list used to be path-specific (`projects/*/bin/`, `.config/Slack`), which matches exactly one location at exactly one depth — a nested repo's `target/` was invisible to it. Depth-independent patterns (`**/target/debug/`, `**/Library/`, `**/.venv/`, `**/obj/`) catch new instances anywhere without anyone noticing them. Measured over a real dry-run: 90.6G in 327,896 files before, **70.2G in 158,967 files after**. The file count matters as much as the bytes, because `--link-dest` carries every inode into every snapshot.

The second is `.local/bin/backup-audit` on a weekly timer — an `rsync -an` dry-run through the real exclude file, aggregated two path components deep, diffed against the previous run's baseline in `$XDG_STATE_HOME/backup-audit/baseline.tsv`. It notifies through quickshell when a directory arrives, or grows, past `BACKUP_AUDIT_THRESHOLD` (1G). It reports the *delta*, not the standing list, or it would restate the same large directories every week and be ignored. `rsync -F` per-directory `.rsync-filter` files are the escape hatch for one-off junk that needs no central edit.

Two things about the exclude file's syntax. **`+ ` lines are includes and order decides**, first match wins, so carving `.local/share/keyrings` (gnome-keyring, 76K, unrecoverable) out of the blanket `.local/` exclude needs the parent directories included first and an explicit `- /.local/share/*` after — five rules for one carve-out, and worth verifying by dry-run rather than by reading. And **a pattern with no interior slash matches at any depth**: the old `.local/` line was also excluding `~/.dotfiles/.local/`, so the dotfiles backup was silently missing its own vendored fonts and adw-gtk3 theme. Anchoring it as `- /.local/*` is what fixed that, and it is the same trap in reverse from the one the class patterns exploit.

One latent bug left alone: the `if [ "$?" = 0 ]` after the rsync error check tests the exit status of the preceding `if`, not rsync, so it is always true and the `else` branch renaming a stalled temp directory to `-failed-` is unreachable. Harmless — the earlier `exit $code` handles a real rsync failure — but it is why six `daily-tmp-2025-02-22T*` directories from a stalled run are still on the NAS with nothing to clean them up.

**The key's authority is restricted on the NAS, not only on this end.** `backup@beedle`'s `authorized_keys` entry carries `restrict,from="192.168.42.0/23"`, which turns off pty allocation, port forwarding, agent forwarding and X11 while still permitting command execution — all the script needs, since `ssh host "cmd"` and rsync never ask for a pty. Verified on fresh connections with multiplexing disabled so each exercised real pubkey auth: rsync transferred, `touch`/`mv`/`ln -s`/`rm -rf` all ran, `tty` reported `not a tty`, a remote forward was refused outright, and `SSH_AUTH_SOCK` came back empty on the far side. The previous unrestricted line is kept at `~/.ssh/authorized_keys.bak` on beedle. Hold a `ControlMaster` open while editing that file — it survives a broken key and is the difference between a mistake being a retry and being a trip to the DSM web UI.

**`command=` is ruled out rather than overlooked**, which is worth knowing because it is the usual answer for an unattended rsync key. `backup:39-57` runs `rm -rf`, `mv`, `ln -s` and `touch` on the far side, so the key needs arbitrary remote command execution and cannot be pinned to a forced command without moving the whole rotation server-side. Upstream `rrsync` would not run there in any case — it is perl, and beedle has `bash`, `sh` and `python3` but no perl.

**The `from=` netmask is a /23, not a /24.** The LAN is `192.168.42.0/23` and hosts land in both halves — beedle is 192.168.42.2 while demise is 192.168.43.36 and impa 192.168.43.29 — so the obvious `192.168.42.0/24` would have locked both clients out of their own backups. Take a host's prefix from `ip -4 -o addr show scope global` rather than inferring it from the NAS's address.

**`backup` is a member of `administrators`, deliberately.** DSM 7 permits SSH login only to that group and offers no per-user toggle for it — SSH is not one of the per-user "Applications", that list being AFP, DSM, FTP, File Station, SFTP, SMB, Universal Search and rsync. The membership is compensated by per-user rules, which beat the group's Allow (DSM resolves conflicts as NA > RW > RO for shares, Deny > Allow for applications): Read/Write on `backup` and `homes` only, No Access on the other eight, rsync allowed and everything else denied including DSM itself, and no passwordless sudo. The application denials are orthogonal to shell access — SFTP is denied and `ssh beedle-back 'cmd'` works fine, which is what the whole arrangement runs on. Do not "fix" the group membership; removing it locks the backup out.

**What no key restriction can do is stop the key deleting backups, because deleting old snapshots is the job.** The `backup` user can write to every machine's tree under `/volume1/backup` — `demise`, `impa`, `home-assistant`, `ctr-x1` and the `mipha.sparsebundle` Time Machine bundle — so a stolen plaintext key reaches all of them. The control for that is **immutable Btrfs snapshots** of the `backup` share, from DSM's Snapshot Replication package: scheduled daily, timed clear of both machines' timers (`OnCalendar=daily` with `RandomizedDelaySec=15m`, so runs start 00:00-00:15), with a retention policy and a WORM lock the NAS enforces against everyone, a DSM administrator included. Splitting the key per machine behind a forced command would confine each client to its own subdirectory and is the remaining unimplemented option, but it is second in value to the snapshots, which also cover a client destroying its *own* backups. Note the snapshots pin extents the rotation has deleted, so space is not reclaimed until they expire — noise against ~70G of data and 5.4T free, but it is the mechanism to remember if the volume tightens.


**Backup indicator and browser** (`.local/bin/backup-record`, `.local/bin/backup-browse`, `.local/bin/backup-browser`, `services/BackupService.qml`, `modules/bar/Backup.qml`, `modules/backup/`, `backups.qml`): a clock-running-backwards icon in the right section between the theme and insomnia items, blue and pulsing while a backup runs, red when the last run failed, yellow when nothing has succeeded for 48 hours. Its `BarPopup` shows what is running and for how long, how the last run ended, when the last success was and what rsync moved, and when the next timer fires, with "Back up now" / "Stop" and "Browse…"; `quickshell ipc call backup toggle|start|browse` reaches the same three.

**The units record their own state, so the shell watches one file and talks to systemd for nothing.** Each `backup-*.service` carries `ExecStartPre=backup-record start <interval>` and `ExecStopPost=backup-record finish <interval>`, which keep `$XDG_STATE_HOME/backup/status.json` (`state`, `current`, `last`, `lastSuccess`). `ExecStopPost` runs on **every** outcome, measured with transient units: `$SERVICE_RESULT` reads `success`, `exit-code`, `exec-condition` (the NAS probe skipped it, and there was no `ExecStartPre` run) and `timeout` (with `EXIT_STATUS=TERM`), so `finish` is the one place a run's fate is decided. The rsync figures come from a `--log-file` the script now writes with `--log-file-format=''`, which is measured to carry only the `--stats` summary and none of the per-file lines; the per-file listing still goes to the journal. systemd's unit signals were considered and rejected: a passive `busctl monitor` did receive `PropertiesChanged` for the units, but only because something else on the bus (uwsm's `fumon`) holds a `Subscribe()`, which is not a thing to depend on.

A stop from the panel is `systemctl --user stop`, and the script's TERM trap removes the half-built `*-tmp-*` directory from the NAS on the way out (verified: none left behind). It exits 143, which the units list in `SuccessExitStatus` so a deliberate stop does not fire `OnFailure`'s notification; `backup-record` turns `success` + `143` into `stopped`, which the panel reports and the icon does not colour. Note that a manual run rotates `daily.N` like any other, so each "Back up now" costs a daily slot.

Two things about `FileView` here, both measured. **A watch on a path that does not exist never fires when the file appears** -- the shell started before the first record showed "No backup recorded yet" through a whole run -- so a failed load is retried on a 30s timer until the file exists. And **the watch survives `os.replace`**: `backup-record` writes through a temp file and rename, and the panel followed every write. `BackupService` also checks a `running` record against `systemctl is-active` on load and every 30s, since a power cut mid-backup leaves a record nobody finishes.

The browser is **its own quickshell process**, `backups.qml` over a `FloatingWindow` (app_id `org.quickshell`, floated by a sway rule on its title), started by `backup-browser`: the panel launches it through `I3.dispatch("exec …")` so it lands in sway's scope, and a second launch first tries `quickshell -p backups.qml ipc call browser raise`, which exits 255 when no instance is up. Closing the window calls `Qt.quit()`. It is a window rather than an overlay because it is a working surface, and a second process rather than a surface in the shell because everything it reads is on a CIFS automount. Every read goes through `backup-browse` in a `Process` (`snapshots`, `list <snapshot> <path>`, `restore <snapshot> <path> replace|keep`), and reads are serialised rather than restarted: killing an in-flight `Process` lets its `exited` land *after* the replacement started and overwrite the newer listing. The two `ListView`s carry `keyNavigationEnabled: false` and the content item takes `forceActiveFocus()` on completion, because a `ListView` is a focus scope and, holding focus, would consume the arrow keys itself.

**Hard links are not visible over SMB as inode identity, but they are as link count, and neither is the discriminator used.** Measured on the mount: the same unchanged file in `daily.0`, `daily.1` and `daily.2` reports three different inode numbers (nothing in the mount options gives stable server inodes) while `nlink=10` on each, and a file changed that night reports `nlink=1`. The count alone cannot say *which* snapshot a file changed in, so `list` compares each entry against the next-older snapshot on **size and whole-second mtime** -- rsync's own quick check, and therefore exactly the rule `--link-dest` applied when it decided whether to link. Entries the older snapshot had and this one lacks are listed as **deleted**, struck through, and opened or restored from the older snapshot. A directory is compared the same way on its own mtime, which moves when its listing changes and not when a file inside is edited, so it is labelled "listing changed" rather than "changed"; an editor that writes through a temp file and rename (nvim) moves the parent's mtime, which is why `.config/sway` shows as changed after an edit to `sway/config`. The "previous" snapshot is by full-resolution mtime, because the daily and the weekly of the same night land within a minute of each other and the order decides which was linked against the other (measured: `weekly.0` four seconds after `daily.3`). Stat over CIFS is effectively free once a directory is listed (127 entries in two snapshots in 70ms cold), so the comparison costs nothing visible.

Restore copies from the NAS to the same path under `$HOME`. "Keep both" writes `name (backup YYYY-MM-DD).ext` beside the original; "Replace" over a directory is `rsync -a --delete` so the result *is* the snapshot (the dialog says so, since anything added since goes), and over anything else removes the destination and copies. Verified end to end with a scratch directory backed up, changed, and backed up again: the deleted file came back from the older snapshot, keep-both named its copy, replace from an older snapshot restored the older contents, and a directory replace removed what the snapshot lacked.

**Do not test a snapshot's read-only-ness with `test -w`.** It reads the permission bits, still 0777 from the Synology ACL, and has no visibility into the subvolume being read-only, so it reports the snapshot root and everything under it as writable. An actual `open(O_CREAT)` on the same path returns `EROFS`, which is the test with the power to tell the two apart; deleting one is separately refused, being root-owned and a subvolume wanting `btrfs subvolume delete`. Snapshots live at `/volume1/@sharesnap/<share>/GMT-<offset>-<timestamp>` and are readable from the `backup` account, but `btrfs subvolume list` is not (`Operation not permitted`) and neither is the package's own state under `/var/packages/SnapshotReplication`, so the immutability lock and the schedule can only be confirmed in the DSM UI.
