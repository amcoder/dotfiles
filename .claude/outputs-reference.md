# Output configuration reference

The full notes behind `rules/outputs.md`: how each fact there was established, what was measured, and what was tried first. Moved verbatim from CLAUDE.md.

**Output configuration** (`.local/bin/sway-outputs`, `sway-outputs.service`): the sway config names no output at all — mode and scale are derived from each panel's EDID at login and on hotplug.

Sway's own default is the EDID **preferred timing**, and on the Odyssey G9 that is 3840x1080, which is why the config used to carry a hand-written `mode 5120x1440@240Hz`. "Biggest mode" is not the fix either: the same panel advertises 3840x2160 (8.29MP), which beats its native 5120x1440 (7.37MP) on pixel count. Modes are therefore ranked by **aspect ratio first** — against the panel's physical size from the EDID — then pixel count, then refresh. Measured on that monitor: with the aspect term the rule picks 5120x1440@240, without it 3840x2160@60. This is the trap way-displays falls into too (its `mode_max()` compares `width * height`, so `MODE: MAX: TRUE` picks the wrong mode there and you are back to hand-configuring), and kanshi has no best-mode or auto-scale concept at all — which is why neither is installed.

The scale ladder is **integer**: 2 at or above 165 DPI, 1 below. Fractional scaling costs Xwayland sharpness, and 1/2 is what this setup always used by hand. DPI alone ignores viewing distance, so a 48" desktop panel and a 14" laptop at the same DPI do not want the same scale; `scaleOverrides` and `modeOverrides` at the top of the script are the escape hatch, keyed by either the sway identifier (`make model serial`) or the connector name. Prefer the identifier — **connector names are not stable**: this monitor moved from HDMI-A-1 to DP-2 and silently orphaned both `output` lines and the aspect-toggle script, with no symptom beyond the resolution being wrong.

Four things the implementation settles, each established by spike:

- **With no readable EDID, do not guess.** Ranking on pixel count alone is not a neutral fallback — it is what picks this panel's 3840x2160 (8.29MP) over its native 5120x1440 (7.37MP), i.e. exactly the wrong answer, and the one that looks like "it chose a lower resolution". An output with no EDID and no override is left to sway's own preferred-mode choice, and is deliberately *not* added to the seen-set, so a read that failed transiently at startup is retried on the next output event.
- **Sway's IPC does not report physical size**, so it comes from `/sys/class/drm/card*-<name>/edid` — detailed timing descriptor 1 (whole mm) in preference to the base block (whole cm). The connector directories are **symlinks**, so the glob needs `(-/)` and not `(/)`; and a sysfs binary attribute always stats as **zero bytes**, so the guard is `-r`, never `-s`. Both of those fail silently, leaving every output at aspect 0 and the wrong mode.
- **`(#b)` backreferences need `setopt extended_glob`**, which a script does not inherit from the interactive shell. Without it every `modeOverrides` value fails to parse.
- `resolve()` runs inside a command substitution, so a `die()` there exits only the subshell — it is reported once per caller and the script carries on. Overrides are therefore validated up front in the main shell.
- **A `swaymsg output` is a full modeset**, which is lockup trigger #1 (see `.claude/sway-lockup-investigation.md`), so nothing is ever issued unless it is a real change. `apply` on a correctly configured output prints `(unchanged)` and touches nothing.

**Applying over IPC is not enough on its own, and this is the central fact about the whole arrangement.** Sway resets an output it has no config for to its EDID preferred mode *and* its default scale on **every** apply — `swaymsg reload` included, which the quickshell power menu offers as "Reload Sway". That is `queue_output_config` in `sway/config/output.c`: with no matching `output_config` supplying `width`/`height` it calls `wlr_output_preferred_mode`, and with none supplying `scale` it calls `compute_default_scale`. So a reload silently dropped this monitor from 5120x1440 to 3840x1080, and the watcher's seen-set (below) meant nothing put it back.

So what `sway-outputs` resolves is also **written to a generated sway include**, `~/.config/sway/outputs.conf`, which `sway/config` `include`s — the same arrangement as `theme.conf`, and generated into the live config directory rather than the repo, so it is never tracked. Sway then owns the values: they are applied at startup before the first frame, and reasserted on every reload. Entries are keyed by identifier and **merged rather than rewritten**, so a monitor that is currently unplugged keeps its line and comes back correct the instant it is plugged in, before the watcher has even seen the event. `install` writes a one-line stub if the file is absent, since sway parses the `include` before anything has had a chance to generate it. Verified that sway really reads it by putting a bad directive in it and watching `sway --validate` name the file and line.

A corollary worth knowing: a runtime override (`sway-scale`, `sway-toggle-aspect`) holds until the next reload and is then reverted to the generated value. That is the same behaviour the hand-written `output` line always had.

`watch` configures an output **once, when it appears**, keyed on the identifier and dropped when it disconnects. It cannot re-apply on every event: a mode or scale set by hand afterwards (`sway-scale`, `sway-toggle-aspect`) fires an output event of its own, and re-applying on that would undo it a frame later. The cost is that a service restart forgets the set and reverts a hand-set value once. `swaymsg -r -m -t subscribe '["output"]'` is the change signal, debounced 300ms because a hotplug arrives as a burst; if that child dies the loop ends and `Restart=always` rebuilds it.

`sway-outputs show` reports what it resolved for every output; `scale` and `mode` print one field, which is how `sway-scale default` and `sway-toggle-aspect` stay in step with the ladder rather than carrying their own copy of it. `mode` also takes an aspect ratio — `sway-outputs mode DP-2 16:9` — and then returns the best mode at that shape **that still fits inside the native one**. That bound is the whole point of it: the G9's largest 16:9 mode by pixel count is 3840x2160, which the panel cannot display (1440 rows of hardware) and must downscale, while the bounded answer is 2560x1440@240, landing on the native pixel grid exactly.

`sway-laptop-lid` follows the lid, and names neither the panel nor the lid device — the same portability argument as the rest of this section, since the config is meant to drop onto a second laptop unedited. The panel is any DRM connector of an **internal** type (`eDP`, plus `LVDS` and `DSI` for older machines and tablets) whose `status` reads `connected`, which is also the test for "is this a laptop": logind reports a lid state on machines that have no lid, so gating on the lid would be wrong, while gating on the panel makes the script a no-op on a desktop. The state itself comes from logind's `LidClosed` property rather than `/proc/acpi/button/lid/*/state`, which does not exist on every machine — the ACPI path stays as a fallback, globbed, because the device under it is `LID`, `LID0` or a PNP id depending on the firmware. With no source answering it does nothing rather than guessing.

Sway's `bindswitch` passes the state explicitly (`lid:on` is **shut**, per `man 5 sway`), and `exec_always sway-laptop-lid` with no argument reads it at startup, which is what picks up a lid that was already closed. `--reload` on both bindings is load-bearing now that outputs.conf exists: a reload re-enables every output the include names, and re-running the binding matching the current lid state is what shuts the panel again. Verified against a fake DRM tree — a connected `eDP-1` and `LVDS-1` are found while a connected external `DP-1` and a disconnected `eDP-2` are not.

`sway-toggle-aspect` ($mod+Ctrl+backslash) swaps the focused output between those two, and takes an optional `W:H` argument. It replaced `sway-samsung-width`, which halved a hardcoded `HDMI-A-1` — the connector this monitor has not been on for some time. It compares **resolution only** when deciding which way to go, since the refresh in a mode string is rounded, and falls back to native from any third state; on a panel whose native mode already is the requested shape it says so and does nothing.

**Display panel** (`services/DisplayService.qml`, `modules/bar/Display.qml`, `modules/display/DisplayPanel.qml`): a monitor icon left of the volume item, opening a `BarPopup` with every output: an enable switch, the resolutions on offer with the refresh rates at the current one, the scale, and on an ultrawide a "Shape" pair swapping between the native mode and the best 16:9 mode inside it, which is `sway-toggle-aspect` as a click. Everything it sets is a sway `output` directive over `I3.dispatch`, and it holds exactly as long as a hand-run `swaymsg output` does: until the next `swaymsg reload`, when sway reasserts `outputs.conf`. The "reset" link beside an output that is off its defaults applies that same value now, mode and scale in one commit. Two switches under the header toggle **adaptive sync and HDR** (`output <name> adaptive_sync|hdr on|off`), shown only where `get_outputs`' `features` object reports the capability; both are connector properties, not modes, so neither is a modeset. Each is bound to the state sway reports rather than to its own click, so a refused `hdr on` (a renderer without HDR) leaves the switch off, and `hdr-run` or a terminal `swaymsg` moves it live.

The service reads two things and derives the rest. `swaymsg -t get_outputs` is the state and the mode list; `sway-outputs json` (new subcommand, one call for every output, ~20ms) is what the ladder resolves, so "native", "default" and the 16:9 candidate come from the same code that configures the outputs at login and never need a second copy here. An output the script cannot resolve (no EDID) is simply absent from that answer and the panel shows it without a native marker, a default scale or a shape row. A modeset or a hotplug arrives as a burst of output events, so the `subscribe '["output"]'` reader settles 300ms before re-reading, and the panel re-reads on open besides.

**No command is ever issued that is not a change.** Every setter compares against the current state first, and a same-value `swaymsg output DP-2 scale 1` was measured to produce an output event, so it is a real commit and not a no-op on sway's side; a commit is the modeset path in `.claude/sway-lockup-investigation.md`. Verified by clicking the already-selected shape, refresh and scale chips under a subscription: zero events. Ultrawide is a native mode at least twice as wide as tall (`ultrawideAspect`), which catches 21:9 and 32:9 and leaves 16:10 alone. The shape comparison is on resolution alone, as `sway-toggle-aspect`'s is, while "reset" compares the whole mode so a native-resolution output at a lower refresh still gets one.

The last active output cannot be disabled from the panel: the switch is dimmed and `setEnabled` refuses, because sway carries on with nowhere to draw and the bar goes with everything else. Enable and disable are otherwise untested on this machine, which has one output. `native` is a reserved word in QML, in a `const` inside a function as much as in a property name, and the parser reports it only as "Expected token `identifier'" with a line number, which is why the field is `nativeMode`.
