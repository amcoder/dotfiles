# Login reference

The full notes behind `rules/login.md`: how each fact there was established, what was measured, and what was tried first. Moved verbatim from CLAUDE.md.

**Login** (`system/greetd/`, `system/install-greetd`): login goes through **greetd** on VT7, which runs a bare sway hosting **gtkgreet**; picking a session there starts `uwsm start -- sway.desktop`, which is byte-for-byte what `uwsm start default` resolved to when it was typed by hand (`~/.config/uwsm/default-id` holds `sway.desktop`). Both machines are on it, and neither autologins — the laptop's greetd used to carry an `[initial_session]` running `sway-run`, and dropping it is what put the two on the same config.

`system/` is the third repo root outside the four paths `install` mirrors, after `themes/` and `claude/`, and for a harder reason than either: these files are root-owned and live in `/etc`, so they are **copied, not linked** — `sudo ./system/install-greetd` after any edit, or the change does nothing. That script is also where the non-file steps live (the `_greetd` group hedge, `sway --validate` on the greeter config, `systemctl enable greetd`), so it is the whole procedure rather than a `cp` wrapper.

**`sway --validate` brings the backend up before it parses the config**, which makes it near-useless where you most want it — under `sudo`, from a text console. It aborts outright on the unset `XDG_RUNTIME_DIR` that sudo does not pass through, and faking that one is worse than useless: it then spends ten seconds failing to open a DRM session and exits 1 for a good config and a bad one alike, a check that can never pass and that reads as "my config is broken". `WLR_BACKENDS=headless` plus a throwaway `XDG_RUNTIME_DIR` skips DRM and seat management entirely and leaves just the parse — measured at exit 0 on a good config and 1 with a real error message on a bad one, in 0.07s, with no display and no session. Note also that a typo'd *identifier* is not a parse error: `input typ:keyboard { … }` validates clean, because sway reads it as a device identifier that happens to match nothing.

**gtkgreet does not read `wayland-sessions` desktop entries** — it reads `/etc/greetd/environments`, a newline-separated list of raw command lines. That is a simplification worth knowing, because the obvious design (a `/usr/local/share/wayland-sessions/sway-uwsm.desktop` wrapper, per uwsm's own README) buys nothing here and would leave the packaged `sway.desktop` sitting next to it in every picker as a session that silently skips uwsm. The second line in `environments` is `zsh -lc sway`, a deliberate rescue: a login shell so `~/.profile` still runs, since with uwsm out of the picture nothing else would source it.

`source_profile = false` in `config.toml` is deliberate and is the one setting to not "fix". greetd's default is `true`, and uwsm sources `/etc/profile` and `~/.profile` itself — but `~/.profile` *prepends* to `PATH` with no re-entry guard, so letting both do it duplicates every entry. Turning it off leaves the greeter with **no `PATH` at all** — measured off a real greeter, the environment greetd hands its child contains none, because `/etc/environment` is empty on this machine and `common-session` carries no `pam_env`. That is survivable rather than fine: `sh(1)` falls back to `confstr(_CS_PATH)` for the lookups on the `command` line, which is how `env` finds `sway`. Anything the greeter runs that does its **own** `PATH` search instead of leaving it to `sh` must use an absolute path — `strace` is one such, and a diagnostic wrapper reading `strace … gtkgreet` died with `Cannot find executable 'gtkgreet'`, exec'd nothing, and looped the greeter into greetd's start limit until VT7 was a bare cursor.

The greeter's sway config **must not** `include /etc/sway/config.d/*` the way the packaged `/etc/greetd/sway-config` did. The only drop-in there is `50-systemd-user.conf`, which imports the environment into the systemd *user* manager — as `_greetd` that starts a user manager for the greeter account with nothing to manage. It carries an `output` line keyed by sway **identifier** (not connector — see the output section) matching the mode `sway-outputs` will pick, so login → session is not a second modeset; on any other machine the identifier matches nothing and the line is inert.

That last reasoning is half wrong, and it cost 30–60 seconds at every login until it was measured. **`pam_systemd` starts `user@105.service` for `_greetd` regardless** — it is in `common-session`, and `/run/user/105` comes up holding a session bus, pipewire, gnupg, keyring and gcr, for a login screen. Skipping the drop-in therefore does not avoid a user manager; it only leaves that manager with no `WAYLAND_DISPLAY`. gtkgreet calls `org.freedesktop.host.portal.Registry.Register` **synchronously inside `gtk_init`**, so until it returns nothing is drawn at all — not the wallpaper, not the clock, not the entry — and the screen sits on sway's solid background with a live cursor, looking like a healthy session with a missing greeter. That call activates `org.freedesktop.portal.Desktop`, which picks a backend by matching `XDG_CURRENT_DESKTOP` (unset here) against the `UseIn=` lines in `/usr/share/xdg-desktop-portal/portals/*.portal`, matches nothing, and falls back to `gtk.portal`. `xdg-desktop-portal-gtk.service` is `Type=dbus`, so systemd waits for it to claim its `BusName` — but it is itself a GTK app started by that display-less user manager, so it never does, and dbus-daemon gives up one `service_start_timeout` (25s) later. xdg-desktop-portal then retries, which is why this presented as "30 to 60 seconds" rather than a constant: attempts were captured at 25s, 50s and 75s.

The fix is `DBUS_SESSION_BUS_ADDRESS=unix:path=/nonexistent` on greetd's `command`, taking the greeter's session bus away on purpose — **25.14s to first paint with the bus, 0.07s without**. It costs the greeter nothing, because gtkgreet reaches greetd over `GREETD_SOCK` and wants no session bus, no accessibility bridge, no gvfs and no portals; verified with the bus gone that the stylesheet, the wallpaper and the `/etc/greetd/environments` session list all still render. Suppressing the portal from the *client* side does **not** work, and the numbers are kept in `config.toml` so nobody retries them: `GTK_USE_PORTAL=0` measures 25.08s, adding `NO_AT_BRIDGE=1` and `GIO_USE_VFS=local` 25.10s, and `XDG_CURRENT_DESKTOP=sway` 25.10s (`wlr.portal` advertises only Screenshot and ScreenCast, so the lookup still falls back to the gtk backend). None of them gate that `Register` call.

Two things about diagnosing this class of bug. greetd's journal carries **no sway or gtkgreet output at all**, so a misbehaving greeter is invisible until `command` is given a `> /tmp/…log 2>&1` redirect — greetd 0.10.3 does run the line through `sh(1)`, so the redirect works. And instrumenting the login path is the wrong way round, since a wrong wrapper leaves an unbootable greeter: `systemctl start user@105.service` plus `setpriv --reuid=105 --regid=114` runs gtkgreet as `_greetd` against a real systemd-activated session bus inside a headless nested sway, entirely outside the login path, which is where every number above came from. A hand-started `dbus-daemon` is **not** equivalent — the portal and a11y service files carry `SystemdService=`, so the real bus delegates activation to systemd while a private one exec's the binary directly, a different code path that does not reproduce the hang. `dbus-monitor` on that bus is what named the call; strace alone only showed an anonymous futex timeout.

Two things about `_greetd` that look like they should break and do not. It reaches the GPU by **logind ACL**, not group membership: `getfacl /dev/dri/card0` shows `user:<active user>:rw-` granted to whoever holds the active seat0 session, and greetd's greeter is one. `install-greetd` adds `_greetd` to `video` and `render` anyway as a hedge for the window before the session goes active. And it cannot read *anything* under `~` — `$HOME` is 0700 — which is why the wallpaper is copied to `/etc/greetd/wallpaper.png` and why `sway-config` sets `GTK_THEME=Adwaita:dark` rather than relying on the generated dotfiles GTK theme under `~/.local/share/themes`.

`gtkgreet.css` is **hand-written and static** — it is not in `theme`'s `TARGETS` and `theme set` does not touch it. That is a choice, not an oversight: the generated files all land under `~/.config`, and reaching `/etc` would mean `theme` needing root, which it has never needed. The palette in it is Catppuccin Mocha, and it tracks nothing — the install-time default is macchiato, and changing themes leaves the login screen where it is. gtkgreet's own widget ids are `#body`, `#clock`, `#input-field` and `#command-selector` (read off the binary, they are not documented); everything else in the file is plain GTK3, and a stylesheet passed with `--style` layers *over* the GTK theme rather than replacing it.

The way back in if the greeter ever fails is `Ctrl+Alt+F2`: `greetd.service` takes VT7 alone (`Conflicts=getty@tty7.service`) and tty1–tty6 keep their gettys. greetd gives up after 5 restarts in 30s, so a broken greeter leaves VT7 blank rather than looping forever. Test a change by switching to a getty **first** and restarting greetd from there — restarting it kills the graphical session either way, and from a getty you are already somewhere useful when it does not come back.
