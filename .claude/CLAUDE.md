# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Personal dotfiles for a Linux (Debian, Sway/Wayland) and macOS environment. The repo mirrors `$HOME`: `.config/`, `.local/bin/`, `.profile`, and `.zshenv` are symlinked into the home directory, so edits to files here take effect immediately in the live environment — no build or deploy step.

## Commands

- `./install` — symlink all tracked files into `$HOME` (backs up any existing non-symlink files). Must be re-run after adding a **new** file to the repo so its symlink gets created; editing existing files needs nothing.
- `./install --deps` — also install packages (Homebrew bundle from `Brewfile` on macOS, `apt` on Debian/Ubuntu).
- `dot-add <file>` — zsh function (defined in `.config/zsh/dot.zsh`) that moves an existing file from `$HOME` into the repo, symlinks it back, and commits it. Prefer this when bringing a new config file under management.
- `dot-prune` — deletes symlinks under the four managed roots that point into the repo but no longer resolve. `install` runs it after linking, because `ln` never removes anything: renaming a tracked file leaves a dangling link in `$HOME`, and quickshell dies loading one. It only touches links whose target is inside `$DOTFILES_DIR`, so unrelated broken links elsewhere in `~/.config` are left alone.

There are no tests or linters for the repo as a whole. Neovim Lua is formatted with stylua per `.config/nvim/.stylua.toml` (2-space indent, prefer single quotes).

## Structure

- **zsh** (`.config/zsh/`): the root `.zshenv` only sets `ZDOTDIR` to `.config/zsh`; all real config lives there. Plugins are managed by zinit (auto-cloned on first shell start). Load order is documented at the top of `.zshrc`. `install` writes a generated `dotfiles-dir.zsh` (untracked) into `ZDOTDIR` exporting `DOTFILES_DIR`.
- **Neovim** (`.config/nvim/`): kickstart.nvim-style single `init.lua` for options/keymaps, with lazy.nvim loading one plugin spec file per concern from `lua/plugins/`. Add new plugins as a new file in that directory. `lazy-lock.json` pins plugin versions.
- **Themes** (`themes/`, repo root — deliberately outside the four paths `install` symlinks): one palette per theme (`catppuccin-macchiato.json`, `nord.json`) plus `templates/`, from which `.local/bin/theme` renders every app-specific config. The selection lives in `$XDG_STATE_HOME/theme/current` and the rendered files land in `~/.config`, so switching themes never dirties the repo; `install` ends by running `theme apply`, defaulting to catppuccin-macchiato. Use `theme list`, `theme current`, `theme set <name>`, `theme apply`.

  Templates are written against a role vocabulary that reuses Catppuccin's 26 colour names as generic roles (`crust`/`mantle`/`base`, `surface0-2`, `overlay0-2`, `subtext0-1`, `text`, and 14 accent names) because it is the superset; themes with fewer colours map several roles to one hex. Placeholders are `{{role}}` (`#rrggbb`), `{{role_raw}}` (bare hex, for swaylock and Qt ARGB) and `{{role_rgb}}` (`r,g,b`, for kdeglobals) — `{{ }}` rather than `$` so sway's own `$var` syntax survives. Adding a theme means one JSON file; adding an app means a template plus an entry in `TARGETS`.

  Generated files go where each app already looks, never to a central directory, so nothing has to resolve a `~` or an absolute path — GTK's `@import` takes a URL with no `~`, and sway resolves a relative `include` against the config's own directory. Each theme also declares `"appearance": "dark" | "light"`, which `theme` applies as real desktop state, not just colours: `gsettings org.gnome.desktop.interface color-scheme` (which xdg-desktop-portal exposes as `org.freedesktop.appearance`, and which is what Electron apps such as Claude desktop follow), plus `gtk-application-prefer-dark-theme` in the generated `gtk-{3,4}.0/settings.ini`. Because it is state rather than a reload, `apply_appearance` runs even under `--no-reload`, so `install` leaves a fresh machine in the right mode. The `gtk-theme` bounce that forces GTK to re-read the palette must pass through a theme of the *same* appearance (`Adwaita-dark` for dark) — bouncing via light `Adwaita` leaves the whole desktop light if the run is interrupted between the two `gsettings` calls.

  The GTK3 palette is not written to `~/.config/gtk-3.0/gtk.css`: GTK3 loads that file exactly once, when the app starts, and re-reads it neither on a file change nor on a theme change, so every running GTK3 app — Chrome above all — kept the palette it launched with until it was restarted. Instead `theme` generates a whole GTK theme at `$XDG_DATA_HOME/themes/dotfiles`, whose `gtk-3.0/gtk{,-dark}.css` is an `@import` of `gtkTheme`'s stylesheet followed by our `@define-color` lines (a later definition wins), and points `gtk-theme` at it. That one GTK re-reads from disk on every `gtk-theme` set, which is what the bounce in `apply_appearance` is for — the generated theme's name never changes, so without the detour through `Adwaita-dark` gsettings emits no change at all. Verified end to end: a running Chrome with the GTK theme selected repaints across macchiato → latte → nord with no restart.

  The theme provider sits *below* `~/.config/gtk-3.0/gtk.css` in GTK's cascade, so that file must not also carry the palette — a stale in-memory copy would mask the generated theme in every app started before the switch. `prune` deletes it from the manifest of an older `theme` run, but a process already holding it needs one restart. GTK4 is unaffected by all this and keeps its palette in `~/.config/gtk-4.0/gtk.css`, because libadwaita ignores GTK themes entirely and reads only that file — GTK4 apps still need a restart.

  `gtkTheme` names the base theme the generated one imports, and must be an existing directory under `~/.themes`, `$XDG_DATA_HOME/themes` or `/usr/share/themes`, exactly — the names are case-sensitive and the installed adw-gtk3 build is lowercase `adw-gtk3-dark`, not `Adw-gtk3-dark`. A name that does not resolve leaves the generated theme with colours but no widget rules, so GTK falls back to its built-in Adwaita; `theme` warns rather than trusting the string, and the generated CSS falls back to the built-in Adwaita resource so apps stay styled.

  Where an app has no include mechanism (`kdeglobals`, `gtk-4.0/gtk.css`, `gtk-{3,4}.0/settings.ini`, `swaylock/config`, `wofi/style.css`) the whole file is generated and is no longer tracked; the generator unlinks a leftover repo symlink before writing, since `install` never removes stale links. bat reads `BAT_THEME` from the generated `zsh/theme.zsh`, and nvim reads `lua/theme.lua`.

  zsh picks up a switch without restarting: `.zshrc` defines `theme-reload`, a precmd hook that watches `theme.zsh`'s mtime (via `zstat`, not a forked `stat`) and, when it changes, re-sources it along with everything derived from it — `FZF_DEFAULT_OPTS` and `$P10K_CONFIG`. Re-sourcing the p10k config is what applies the change, since powerlevel10k runs with `POWERLEVEL9K_DISABLE_HOT_RELOAD=true` and the config file ends by calling `p10k reload` itself. The p10k prompt's rounded caps are drawn in reverse video, so the colour *behind* them cannot be "the default background" — it has to be named, which is what `THEME_P10K_EDGE` (the theme's `base`) is for; it must equal the terminal background or every segment sits in a visible box of the wrong colour. `theme apply` also deletes `$XDG_CACHE_HOME/p10k-instant-prompt-*.zsh`, which bakes the old palette into a prompt snapshot that outlives the theme switch.

  tmux is split so the template carries no layout: `templates/tmux.tmpl` generates `tmux/theme.tmux` as nothing but `set -g @thm_<role>` lines, and the tracked `.config/tmux/statusline.conf` holds the whole status line, referencing only `@thm_*`. `tmux.conf` sources the colours first, then the layout. Follow that split when theming another app — a template should be the palette, not the design.

  `statusline.conf` reproduces what the `catppuccin/tmux` tpm plugin used to render (rounded window style, window number on the right, icon flags, and the application + session status modules), with the plugin's option indirection flattened out. It sets options with `-gF`, so `#{@thm_*}` resolves when the file is sourced while a doubled `##{...}` survives to render time — which is why a theme switch has to re-source `tmux.conf`, not just rewrite `theme.tmux`. The session module's prefix-sensitive colour must stay a render-time `#{E:@thm_red}` reference: tmux cannot parse a raw `#rrggbb` inside a `#{?...}` conditional. `message-style` uses `bg=default` rather than overlay0 because that is what the plugin actually drew — its `%hidden CTP_MESSAGE_BACKGROUND` resolves empty on tmux 3.7 — and `status-{left,right}-length` are left at tmux's defaults for the same fidelity reason, so a long session name can still truncate at 40 columns.

  Equivalence with the plugin was checked by standing up two `tmux -L` servers — one running the real plugin with the old settings, one sourcing `theme.tmux` + `statusline.conf` — and diffing all 19 status/window/pane options. The comparison has to resolve `#{@thm_*}` on both sides first: the plugin defers those references while this layout bakes them at source time, and it keeps its status modules in `@catppuccin_status_{application,session}` rather than in `status-right`. Assert the comparison actually ran (non-empty values, expected option count) — a version that silently compared two empty files reported a false pass.
- **Qt/KDE theming** (`.config/kdeglobals`): `sway/profile` sets `QT_QPA_PLATFORMTHEME=kde`, so Qt apps load plasma-integration's platform theme, which takes its palette, widget style, icon theme and fonts from the `[Colors:*]`, `[KDE]`, `[Icons]` and `[General]` groups of `kdeglobals`. Both toolkits use Cantarell 11 for UI text and DejaVu Sans Mono 11 for fixed-width, so Qt and GTK render identically. The GTK half lives in gsettings (`org.gnome.desktop.interface font-name`, untracked dconf) rather than in `gtk-3.0/settings.ini`, so changing one side means changing both. When comparing fonts across the two, measure cap height rather than point size — point sizes are not comparable between typefaces. KDE Frameworks apps (Dolphin, etc.) ignore a qt5ct/qt6ct palette entirely and render fully light under `QT_QPA_PLATFORMTHEME=qt5ct`, so the colour scheme has to live in `kdeglobals` (generated from `themes/templates/kdeglobals.tmpl`). The `.config/qt{5,6}ct` configs remain only for Qt5 apps (VLC), which plasma-integration 6 does not cover — launch those with `QT_QPA_PLATFORMTHEME=qt5ct` if they need theming. KDE apps are single-instance, so testing a `kdeglobals` change needs `killall dolphin` first or the old process' cached config is reused.

  Running Qt apps repaint without a restart because `notify_kde` sends what `plasma-apply-colorscheme` sends: a `ConfigChanged` on `/kdeglobals` (`org.kde.kconfig.notify`) *and* a legacy `notifyChange` on `/KGlobalSettings` (`org.kde.KGlobalSettings`) carrying `PaletteChanged`, `StyleChanged` and `IconChanged` (0, 2, 4). The second one is what actually repaints — plasma-integration's `KHintsSettings` still listens on the KDE4-era interface, and rewriting `kdeglobals` with only the kconfig signal leaves every open window on the old palette. Captured by running `dbus-monitor` against a real `plasma-apply-colorscheme` run, and verified by screenshotting Dolphin across `theme set nord` / `theme set catppuccin-macchiato`.
- **Scripts** (`.local/bin/`): standalone helper scripts, mostly for Sway/Wayland (brightness, volume, window switcher, etc.).
- **Quickshell** (`.config/quickshell/`): the Wayland status bar, built with [Quickshell](https://quickshell.outfoxxed.me/) (QML). It replaces swaybar/i3blocks; sway declares no bar of its own and does not start it directly — `quickshell.service` does, via `sway-session.target` (see the systemd section below). `shell.qml` is the entry point, defining a `PanelWindow` top bar per screen (`modules/bar/Bar.qml`). Colors come from `config/Theme.qml`, which reads the generated `~/.config/quickshell/palette.json` through a `FileView` with `watchChanges`, so a theme switch repaints the bar with no restart; its hardcoded Catppuccin values are only fallbacks for before the file loads. Every colour is still a binding, so `readonly` properties update fine. QML edits hot-reload — but a **new** file (a new singleton especially) needs a full restart, since hot-reload will not register it and the bar dies with "X is not defined". Restarting means `systemctl --user restart quickshell`, and its log is `journalctl --user -u quickshell` rather than sway's `systemd-cat` stream. `swaymsg reload` does not restart the bar, and a theme switch does not reload sway at all.

  The tree is `config/` (`Theme`, `Appearance`, `Paths`, `Icons` — data, no behaviour), `services/` (singletons owning state and `IpcHandler`s, no visuals), `widgets/` (leaf components importing only `config/`), `windows/` (window chrome, adding `services/FocusedScreen`) and `modules/<feature>/`, which may import anything. Quickshell synthesizes a `qmldir` per directory and registers the config root as module `qs`, so `import qs.services` works and singletons auto-register across directories — **do not write a `qmldir` by hand**, which permanently disables synthesis for that directory. `dev.qml` is a second entry point for working on one surface at a time (`quickshell -p ~/.dotfiles/.config/quickshell/dev.qml`); `-p` roots the config at the same directory so `import qs.*` resolves identically. Never instantiate the polkit agent, `SystemTray` or a notification server there — each claims a D-Bus name and would fight the running shell.

  `Theme` is the palette and `Appearance` is the design (fonts, icon sizes, bar height), the same split CLAUDE.md argues for tmux: a theme switch touches only the first. `services/FocusedScreen` resolves the output holding the focused sway workspace and every modal surface binds `screen` to it; it falls back to `Quickshell.screens[0]` because a `PanelWindow` on a null screen fails to map with "no output to auto-assign layer surface to". `windows/ModalOverlay` owns the whole overlay-layer-surface pattern — exclusive keyboard focus, scrim, blocking `MouseArea`, centred card, Escape — and its children become the card's column; `PolkitDialog` and `ThemePicker` are both built on it, along with `widgets/{Button,TextField,ListRow}`. `TextField` is a `FocusScope` so `forceActiveFocus()` on the field reaches the inner `TextInput`.

  Renaming or moving a file here needs `./install` (to create the new link) and leaves a dangling old link that `dot-prune` removes — `install` runs it, but a stale link left in place kills the shell at load. `find ~/.config/quickshell -xtype l` must print nothing.

  Icons are vendored Phosphor SVGs in `icons/`, drawn by `widgets/Icon.qml` as `Icon { name: "bell"; color: Theme.yellow }`. `config/Icons.qml` reads the SVG through a `FileView` and caches it (its `Qt.resolvedUrl("../icons")` is relative to `config/`, not to the config root); `Icon.qml` swaps the file's `#ffffff` placeholder fill for the requested colour and hands the result to `Image` as a `data:` URI. Recolouring has to happen in the SVG markup — tinting the rendered image with `MultiEffect` (either `colorization` or an alpha mask) blows out thin strokes at bar sizes until enclosed shapes fill in solid. To add an icon, drop the file from [Phosphor](https://phosphoricons.com/) (regular weight) into `icons/`, replace its `fill="currentColor"` with `fill="#ffffff"`, and re-run `./install`.

  Workspace icons are named by sway: each `set $wsN` in `.config/sway/config` carries a `<span foreground='...'>icon-name</span>`, and `modules/bar/Workspaces.qml` parses the span for the colour and the icon name. Sway only applies renamed workspaces to newly created ones, so after editing those lines, existing workspaces keep their old names until `swaymsg rename workspace` is run or they are recreated.

  The bar is always visible and reserves its own height via `ExclusionMode.Auto`, so windows start below it.

  `services/ThemeService.qml` holds the theme list read from the generated `themes.json` and owns an `IpcHandler` on target `theme`, so `quickshell ipc call theme toggle` opens the picker from a sway keybind ($mod+Ctrl+t); `modules/bar/ThemeToggle.qml` is the palette icon in the bar. `modules/theme/ThemePicker.qml` is the view, instantiated once in `shell.qml` like `PolkitDialog.qml` and drawn on the focused output. Highlighting a row sets `Theme.preview`, which overrides the loaded palette so the running bar previews that theme; committing runs `theme set <name>` and `ThemeService.hide()` clears the preview. Only quickshell previews live — everything else changes on commit.

  `services/NotificationService.qml` is the session's notification daemon, replacing dunst (stopped and **masked** — `systemctl --user mask dunst`; the local binary, its user unit and its D-Bus service file are left on disk so the rollback is `unmask` + `start`). It owns the `NotificationServer`, the popup queue and a 100-entry history ring buffer persisted to `Quickshell.statePath("notifications.json")`, whose directory is keyed by a hash of the config path — so `dev.qml` gets its own history and cannot clobber the real one. `modules/notifications/NotificationPopups.qml` is the transient stack (bottom-right, overlay layer, on `FocusedScreen.screen`, matching dunst's `follow = keyboard`), `NotificationCentre.qml` the history view on `ModalOverlay`, and `modules/bar/NotificationIndicator.qml` the bell. Sway calls it at `config:297-299` — `$mod+n` invokes the newest notification's default action (what `dunstctl action` did), `$mod+Ctrl+n` opens the centre, `$mod+Alt+n` toggles do-not-disturb.

  Three things about the freedesktop API as Quickshell 0.3.0 exposes it, each established by spike rather than assumed. `Notification.expireTimeout` is **milliseconds** passed straight through from D-Bus, with `-1` meaning "server default" (5s/10s/never by urgency, matching the old `dunstrc`). `notify-send -i <name>` arrives as the `image-path` hint and lands in `notification.image` as an `image://icon/<name>` URL, *not* in `appIcon` — so `image` is the primary icon source and `appIcon` only the fallback. And `trackedNotifications` has not yet been updated when the `notification` signal fires, so the service keeps its own arrays rather than reading that model.

  **Replacing a notification by id mutates the existing `Notification` in place and emits no new `notification` signal.** A record holding a copy of the fields therefore goes stale, which is why `NotificationCard` reads the live object through `entry.notification` and falls back to the stored copy only once the notification is gone (restored from disk, or closed by its sender). `summaryChanged`/`bodyChanged` are the only "this was replaced" signal on offer; they drive re-popping an already-expired notification, moving it back to the top of history, and re-saving.

  The popup cap (5) lives in the view, not the service, so notifications past the cap still expire on their own schedule and are only *hidden* behind an "N more" row — which is what dunst's `indicate_hidden` did. `IpcHandler` functions are `open`/`close`, not `show`/`hide`: `quickshell ipc call <target> show` is swallowed by the CLI's own `ipc show` subcommand (this bites `theme show` too).

  `modules/polkit/PolkitDialog.qml` is the session's polkit authentication agent, replacing `polkit-kde-authentication-agent-1`. It is instantiated once in `shell.qml` (not per screen) and draws a modal dialog on an overlay layer surface with exclusive keyboard focus, on whichever output holds the focused sway workspace. Quickshell's `PolkitAgent` registers on startup, so nothing in the sway config launches an agent. Quickshell does not forward PAM's own failure text — it only logs "Unknown line ... from helper" — so a rejected password is reported from `AuthFlow`'s `authenticationFailed` signal instead.
- **Session services** (`.config/systemd/user/`): the shell runs under systemd, not as a sway `exec`. The sway config starts `sway-session.target`, which `BindsTo` + `PropagatesStopTo` `graphical-session.target` and so pulls in `quickshell.service` (`Restart=always`, `StartLimitBurst=5`) plus the machine-local `poweralertd` and `wayland-pipewire-idle-inhibit` units already sitting in `graphical-session.target.wants/`. This keeps `swaymsg reload` and every theme switch out of the shell's lifecycle, and out of the DRM modeset path described in `.claude/sway-lockup-investigation.md`.

  The user manager never sources `~/.profile`, so the XDG base directories and `~/.local/bin` are declared in `.config/environment.d/10-xdg.conf` — without them `theme` and the `sway-*` scripts are unreachable from any user unit. `environment.d` rather than `Environment=` lines because it covers every unit at once, expands `${HOME}`/`${PATH}`, and applies on a plain `daemon-reload`. Files there merge by filename across all `environment.d` directories, so nix's unprefixed `nix-daemon.conf` sorts after `10-xdg.conf` and re-prepends its own paths. `quickshell.service` keeps only `QT_QPA_PLATFORM=wayland` and `QT_QPA_PLATFORMTHEME=kde`, which are about how the shell renders and used to be inherited from `sway-run` and `sway/profile`.

  `wayland-pipewire-idle-inhibit.service` is tracked here too. Any unit added to this target needs `PartOf=graphical-session.target`, not just `WantedBy=` in `[Install]` — `WantedBy` starts it with the session but never stops it, and a `Restart=always` unit then spins against a dead compositor for the whole logout window.

  The sway side is one quoted `exec` that chains the environment import into the target start: `/etc/sway/config.d/50-systemd-user.conf` imports `SWAYSOCK` in a *separate* `exec`, and sway launches execs asynchronously, so the target can otherwise start before the socket is in the manager's environment. The quotes are load-bearing — unquoted, sway parses `&&` (or a `;`) as the start of a second command and logs `Unknown/invalid command`.

  `PropagatesStopTo` is load-bearing and easy to lose: `BindsTo=B` only stops A when B stops, never the reverse, so without it `systemctl --user stop sway-session.target` leaves `graphical-session.target` and every service under it running — and `sway-run`'s teardown silently does nothing.

  `install` ends with `systemctl --user daemon-reload` and `systemctl --user enable quickshell.service`, guarded on `-d /run/systemd/system` so macOS skips it; symlinking a unit is not enough, `WantedBy=` only applies once enabled. Editing an existing unit still needs a `daemon-reload`.
- **Sway**: expects a system-level `/usr/local/bin/sway-run` launcher (documented in README, not tracked here) that exports Wayland env vars, sources `.config/sway/profile`, and runs sway **without** `exec` so it can `systemctl --user stop sway-session.target` on exit — otherwise quickshell outlives the compositor and `Restart=always` spins.
