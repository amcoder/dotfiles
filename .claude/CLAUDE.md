# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Personal dotfiles for a Linux (Debian, Sway/Wayland) and macOS environment. The repo mirrors `$HOME`: `.config/`, `.local/bin/`, `.profile`, and `.zshenv` are symlinked into the home directory, so edits to files here take effect immediately in the live environment — no build or deploy step. `claude/` is linked in too, to a destination that is not its own path (see Claude Code).

## Commands

- `./install` — symlink all tracked files into `$HOME` (backs up any existing non-symlink files). Must be re-run after adding a **new** file to the repo so its symlink gets created; editing existing files needs nothing. A second loop links `claude/<path>` to `~/.claude/<path>`, which the mirroring loop cannot do.
- `./install --deps` — also install dependencies, **before** the symlink pass rather than after it: a Homebrew bundle from `Brewfile` on macOS, `apt` on Debian/Ubuntu, plus nvm and rustup on both. The ordering is load-bearing — everything after the symlink loop (enabling the quickshell units, `theme apply`) needs those binaries to already exist, so on a fresh machine a `--deps` run that installed last would enable a unit whose binary was still missing. Node and Rust come from nvm and rustup rather than apt because each owns its own toolchain and `.config/zsh/nvm.zsh` switches node per `.nvmrc`; an apt copy would sit in front of whatever those selected. Both installers append PATH lines to a shell profile by default, which here means editing `~/.profile` — **a symlink into this repo** — so both are given their own opt-out (`PROFILE=/dev/null` for nvm, `--no-modify-path` for rustup). nvm additionally refuses to create `$NVM_DIR` anywhere but its own default `~/.nvm`, and this repo puts it under `XDG_DATA_HOME`, so the directory has to exist first.
- `dot-add <file>` — zsh function (defined in `.config/zsh/dot.zsh`) that moves an existing file from `$HOME` into the repo, symlinks it back, and commits it. Prefer this when bringing a new config file under management.
- `dot-prune` — deletes symlinks under the five managed roots (the four mirrored paths plus `~/.claude`) that point into the repo but no longer resolve. `install` runs it after linking, because `ln` never removes anything: renaming a tracked file leaves a dangling link in `$HOME`, and quickshell dies loading one. It only touches links whose target is inside `$DOTFILES_DIR`, so unrelated broken links elsewhere in `~/.config` are left alone.

There are no tests or linters for the repo as a whole. Neovim Lua is formatted with stylua per `.config/nvim/.stylua.toml` (2-space indent, prefer single quotes).

## Structure

- **zsh** (`.config/zsh/`): the root `.zshenv` only sets `ZDOTDIR` to `.config/zsh`; all real config lives there. Plugins are managed by zinit (auto-cloned on first shell start). Load order is documented at the top of `.zshrc`. `install` writes a generated `dotfiles-dir.zsh` (untracked) into `ZDOTDIR` exporting `DOTFILES_DIR`.
- **Neovim** (`.config/nvim/`): kickstart.nvim-style single `init.lua` for options/keymaps, with lazy.nvim loading one plugin spec file per concern from `lua/plugins/`. Add new plugins as a new file in that directory. `lazy-lock.json` pins plugin versions. `init.lua` also holds the theme watcher that follows `theme set` live (see Themes).
- **Claude Code** (`claude/`, repo root — linked into `~/.claude`, not mirrored): Claude Code keeps its config directory at `~/.claude`, which cannot be one of the four mirrored roots, because the repo's own `.claude/` is *this project's* instructions — mirroring it into `$HOME` would lay this file over the user-level `CLAUDE.md`. So the home-level config lives in `claude/` and `install` links it file by file with a second loop mapping `claude/<path>` to `~/.claude/<path>`; `dot-prune` gained `~/.claude` as a fifth root. Only the four things that are configuration are tracked — `settings.json`, `keybindings.json`, `statusline-command.sh` and `rules/`. Everything else in that directory is state (`.credentials.json`, `.claude.json`, `history.jsonl`, `sessions/`, `projects/`, the plugin marketplace clones) and is simply not in the repo, which needs no `.gitignore` support because the repo only ever contains what was put in it.

  The global instructions are **split in two halves**. `~/.claude/CLAUDE.md` is untracked, machine-specific, and currently an empty file: the loader drops any entry whose trimmed content is empty, so an empty file costs no context while keeping the machine-local destination obvious. The shared half is `claude/rules/*.md`, linked into `~/.claude/rules/`. That directory is a first-class Claude Code feature rather than a trick — it is walked recursively, every `.md` under it loads, and the renderer labels an entry by its *type* and not its filename, so a file in `~/.claude/rules/` reaches the context under exactly the same header as `CLAUDE.md` itself ("user's private global instructions for all projects"). Load order is managed → user `CLAUDE.md` → user rules → the project chain. One file per concern is the point: `comments.md`, `memory.md` and `instruction-scope.md` can each be edited, moved or made conditional without touching the others.

  A rules file may carry `paths:` frontmatter, which stops it being always-on and injects it only when a file matching those globs comes into play. **At user scope those globs match the touched path made relative to the cwd**, gitignore-style, and the matcher bails the moment that relative path escapes the cwd (`..`) or stays absolute. So a conditional rule keyed on anything under `$HOME` — `~/.claude/CLAUDE.md`, say — can essentially never fire, because no working session has that inside its cwd. `instruction-scope.md` is unconditional for that reason and for a second one: it has to be read *before* an instruction is written, while a conditional rule fires on file access, which is already too late. `paths:` is for per-language rules inside a project (`**/*.rs`), not for anything about the config directory itself.

  A **new** rules file needs `./install` before it loads, which is easy to miss here because editing an existing one needs nothing. The paths that appear in the loaded context are the **repo** paths (`~/.dotfiles/claude/rules/comments.md`) rather than the `~/.claude/rules/` links, because the loader canonicalises symlinks.

  Two things about `settings.json`, both measured rather than assumed. Claude Code rewrites it whenever a setting changes mid-session — theme, model, voice, plugin enablement — and it does so atomically **and** symlink-safely: it resolves the link first, creates `settings.json.tmp.<pid>.<hex>` in the *resolved* directory, and renames that onto the target. Established by strace of a real write, and by four user-scope mutations against a scratch `CLAUDE_CONFIG_DIR` whose `settings.json` was a symlink — the link survived every one, and a 0600 target stayed 0600. Two consequences: the temp file lands in this repo, hence the `.gitignore` line, and the tracked file changes inode on every write, so anything holding it open keeps reading the old copy. The second thing is that the whole JSON object is rewritten with **no key-order guarantee**, so expect a reordering diff on the first write and ongoing churn from per-session toggles (`model`, `theme`, `voice`) — which are now shared across machines whether that was intended or not. Git records only the exec bit, so the file's 0600 here lands as 0644 on a fresh clone; it holds no secrets, the credentials being in the untracked `.credentials.json`.

  `CLAUDE_CONFIG_DIR` relocates the whole directory, and was considered for moving it under `.config` where the ordinary mirroring loop would cover it with no new machinery. Rejected: it moves the state and the credentials along with the config rather than separating them, and it has to be set in *every* context that starts Claude Code — the terminal CLI, the desktop app (which runs its own bundled build), any user unit — falling back silently to a fresh, logged-out `~/.claude` wherever it is missing.
- **Themes** (`themes/`, repo root — deliberately outside the four paths `install` mirrors): one palette per theme (`catppuccin-macchiato.json`, `nord.json`) plus `templates/`, from which `.local/bin/theme` renders every app-specific config. The selection lives in `$XDG_STATE_HOME/theme/current` and the rendered files land in `~/.config`, so switching themes never dirties the repo; `install` ends by running `theme apply`, defaulting to catppuccin-macchiato. Use `theme list`, `theme current`, `theme set <name>`, `theme apply`.

  Templates are written against a role vocabulary that reuses Catppuccin's 26 colour names as generic roles (`crust`/`mantle`/`base`, `surface0-2`, `overlay0-2`, `subtext0-1`, `text`, and 14 accent names) because it is the superset; themes with fewer colours map several roles to one hex. Placeholders are `{{role}}` (`#rrggbb`), `{{role_raw}}` (bare hex, for swaylock and Qt ARGB) and `{{role_rgb}}` (`r,g,b`, for kdeglobals) — `{{ }}` rather than `$` so sway's own `$var` syntax survives. Adding a theme means one JSON file; adding an app means a template plus an entry in `TARGETS`.

  Generated files go where each app already looks, never to a central directory, so nothing has to resolve a `~` or an absolute path — GTK's `@import` takes a URL with no `~`, and sway resolves a relative `include` against the config's own directory. Each theme also declares `"appearance": "dark" | "light"`, which `theme` applies as real desktop state, not just colours: `gsettings org.gnome.desktop.interface color-scheme` (which xdg-desktop-portal exposes as `org.freedesktop.appearance`, and which is what Electron apps such as Claude desktop follow), plus `gtk-application-prefer-dark-theme` in the generated `gtk-{3,4}.0/settings.ini`. Because it is state rather than a reload, `apply_appearance` runs even under `--no-reload`, so `install` leaves a fresh machine in the right mode. The `gtk-theme` bounce that forces GTK to re-read the palette must pass through a theme of the *same* appearance (`Adwaita-dark` for dark) — bouncing via light `Adwaita` leaves the whole desktop light if the run is interrupted between the two `gsettings` calls.

  The GTK3 palette is not written to `~/.config/gtk-3.0/gtk.css`: GTK3 loads that file exactly once, when the app starts, and re-reads it neither on a file change nor on a theme change, so every running GTK3 app — Chrome above all — kept the palette it launched with until it was restarted. Instead `theme` generates a whole GTK theme at `$XDG_DATA_HOME/themes/dotfiles`, whose `gtk-3.0/gtk{,-dark}.css` is an `@import` of `gtkTheme`'s stylesheet followed by our `@define-color` lines (a later definition wins), and points `gtk-theme` at it. That one GTK re-reads from disk on every `gtk-theme` set, which is what the bounce in `apply_appearance` is for — the generated theme's name never changes, so without the detour through `Adwaita-dark` gsettings emits no change at all. Verified end to end: a running Chrome with the GTK theme selected repaints across macchiato → latte → nord with no restart.

  The theme provider sits *below* `~/.config/gtk-3.0/gtk.css` in GTK's cascade, so that file must not also carry the palette — a stale in-memory copy would mask the generated theme in every app started before the switch. `prune` deletes it from the manifest of an older `theme` run, but a process already holding it needs one restart. GTK4 is unaffected by all this and keeps its palette in `~/.config/gtk-4.0/gtk.css`, because libadwaita ignores GTK themes entirely and reads only that file — GTK4 apps still need a restart.

  `gtkTheme` names the base theme the generated one imports, and must be an existing directory under `~/.themes`, `$XDG_DATA_HOME/themes` or `/usr/share/themes`, exactly — the names are case-sensitive and the installed adw-gtk3 build is lowercase `adw-gtk3-dark`, not `Adw-gtk3-dark`. A name that does not resolve loses the **palette**, not the widget rules — the opposite of what it looks like. The generated theme is then our `@define-color` lines over GTK's built-in Adwaita, and the two vocabularies do not overlap at all: ours is libadwaita's (`window_bg_color`, `accent_bg_color`, `view_bg_color`), Adwaita's is GTK3's own (`theme_bg_color`, `theme_base_color`, `theme_selected_bg_color`). adw-gtk3 is the translation between them, so without it every colour we define is referenced by nothing and apps keep Adwaita's rules *and* Adwaita's grey. Measured on a fresh machine with adw-gtk3 missing: `window_bg_color` read `#1e1e2e` (our base, loaded fine) while `theme_bg_color` — what widgets, and Chrome, actually paint with — read `#353535`. `theme` warns on stderr rather than trusting the string, but that warning is the only symptom and it scrolls past during `install`.

  Debian does not package adw-gtk3, so it is **vendored** at `.local/share/themes/adw-gtk3{,-dark}` (upstream v6.5), the same call as the Phosphor icons and `emoji.txt`. That path needs no `install` support at all: `$XDG_DATA_HOME/themes` is `~/.local/share/themes`, already inside `.local`, so the ordinary symlink loop links it into place before `theme apply` runs on the same pass — which is what makes a fresh machine come up themed in one `./install`, with no `--deps` and no network. Only `index.theme` and `gtk-3.0/` are vendored; upstream's `gtk-4.0/` (864KB, mostly `libadwaita.css`) and the thumbnails are dropped, because nothing ever resolves adw-gtk3 *by name* — the generated theme `@import`s its GTK3 stylesheet by absolute path, and GTK4 reads `~/.config/gtk-4.0/gtk.css` instead. The stylesheets reference their assets relatively (`url("assets/…")`), so `assets/` has to sit beside each `gtk.css`; the two variants' asset sets are byte-identical, as are three of the four stylesheets, so git stores one blob of each. Updating means re-extracting those two parts of the release tarball over these directories and re-running `./install` for any file that is new.

  Where an app has no include mechanism (`kdeglobals`, `gtk-4.0/gtk.css`, `gtk-{3,4}.0/settings.ini`, `swaylock/config`) the whole file is generated and is no longer tracked; the generator unlinks a leftover repo symlink before writing, since `install` never removes stale links. bat reads `BAT_THEME` from the generated `zsh/theme.zsh`, and nvim reads `lua/theme.lua`.

  nvim picks up a switch without restarting, the same way zsh and quickshell do: `init.lua` starts a `vim.uv` fs_event on `~/.config/nvim/lua` and, when `theme.lua` changes, switches to the colorscheme it names. Both colorscheme plugins are start plugins whose `config` runs regardless of which theme is selected (only the `vim.cmd.colorscheme` call is gated), so every colorscheme is already loaded in every instance and the switch needs no plugin load. lualine follows on its own — it registers a `ColorScheme` autocmd that re-runs its own `setup()`, and its `theme` is left at `auto`.

  Four things about that watcher. It watches the **directory**, not the file: `write()` truncates in place most of the time, but it unlinks and recreates when a repo symlink is in the way, and a file watcher dies on that. The callback must `vim.schedule()` — a libuv callback is not a safe place to touch the vim API. It uses `dofile` rather than `require`, so there is no `package.loaded` entry to invalidate. And it compares against `vim.g.colors_name`, so a re-`apply` of the same theme does not redraw — which also means a hand-set `:colorscheme` is overridden by the next `theme apply`. The `fs_event` handle is a file-scope local in a chunk that has finished running, and survives anyway because luv refs an active handle; verified by forcing a full GC over RPC and then switching themes.

  zsh picks up a switch without restarting: `.zshrc` defines `theme-reload`, a precmd hook that watches `theme.zsh`'s mtime (via `zstat`, not a forked `stat`) and, when it changes, re-sources it along with everything derived from it — `FZF_DEFAULT_OPTS` and `$P10K_CONFIG`. Re-sourcing the p10k config is what applies the change, since powerlevel10k runs with `POWERLEVEL9K_DISABLE_HOT_RELOAD=true` and the config file ends by calling `p10k reload` itself. The p10k prompt's rounded caps are drawn in reverse video, so the colour *behind* them cannot be "the default background" — it has to be named, which is what `THEME_P10K_EDGE` (the theme's `base`) is for; it must equal the terminal background or every segment sits in a visible box of the wrong colour. `theme apply` also deletes `$XDG_CACHE_HOME/p10k-instant-prompt-*.zsh`, which bakes the old palette into a prompt snapshot that outlives the theme switch.

  tmux is split so the template carries no layout: `templates/tmux.tmpl` generates `tmux/theme.tmux` as nothing but `set -g @thm_<role>` lines, and the tracked `.config/tmux/statusline.conf` holds the whole status line, referencing only `@thm_*`. `tmux.conf` sources the colours first, then the layout. Follow that split when theming another app — a template should be the palette, not the design.

  `statusline.conf` reproduces what the `catppuccin/tmux` tpm plugin used to render (rounded window style, window number on the right, icon flags, and the application + session status modules), with the plugin's option indirection flattened out. It sets options with `-gF`, so `#{@thm_*}` resolves when the file is sourced while a doubled `##{...}` survives to render time — which is why a theme switch has to re-source `tmux.conf`, not just rewrite `theme.tmux`. The session module's prefix-sensitive colour must stay a render-time `#{E:@thm_red}` reference: tmux cannot parse a raw `#rrggbb` inside a `#{?...}` conditional. `message-style` uses `bg=default` rather than overlay0 because that is what the plugin actually drew — its `%hidden CTP_MESSAGE_BACKGROUND` resolves empty on tmux 3.7 — and `status-{left,right}-length` are left at tmux's defaults for the same fidelity reason, so a long session name can still truncate at 40 columns.

  Equivalence with the plugin was checked by standing up two `tmux -L` servers — one running the real plugin with the old settings, one sourcing `theme.tmux` + `statusline.conf` — and diffing all 19 status/window/pane options. The comparison has to resolve `#{@thm_*}` on both sides first: the plugin defers those references while this layout bakes them at source time, and it keeps its status modules in `@catppuccin_status_{application,session}` rather than in `status-right`. Assert the comparison actually ran (non-empty values, expected option count) — a version that silently compared two empty files reported a false pass.

  btop is the tmux split again, with the palette on the other side of the line: `templates/btop.tmpl` generates `btop/themes/dotfiles.theme` and the tracked `.config/btop/btop.conf` holds every setting, naming only `color_theme = "dotfiles"`. That bare name is what makes the config portable — btop resolves it against `$XDG_CONFIG_HOME/btop/themes` and, measured, writes it back **verbatim** rather than expanding it to the absolute path the theme menu would store, which is what the untracked config used to carry.

  Three more things about btop, each established by spike against a scratch `XDG_CONFIG_HOME` driven through a sized pty (it exits with "Failed to get size of terminal!" under a pipe, and `script` alone does not size the pty). It writes `btop.conf` **through a symlink in place** — same inode across a settings change, so tracking the file is safe. It writes **only when something changed**, so an ordinary run-and-quit leaves it alone and there is less churn than `save_config_on_exit = true` suggests. And it does **not** re-read the theme file while running, so a `theme set` leaves an open btop on its old palette until it is restarted — GTK4's position, not zsh's or nvim's. Verification is by rendering rather than by reading the config back: run btop under a pty and grep the output for the palette's background as an SGR triplet (mocha's `#1e1e2e` is `48;2;30;30;46`), which is the only signal that separates "theme loaded" from "silently fell back to Default".
- **Qt/KDE theming** (`.config/kdeglobals`): `.config/environment.d/20-qt.conf` sets `QT_QPA_PLATFORMTHEME=kde`, so Qt apps load plasma-integration's platform theme, which takes its palette, widget style, icon theme and fonts from the `[Colors:*]`, `[KDE]`, `[Icons]` and `[General]` groups of `kdeglobals`. Both toolkits use Cantarell 11 for UI text and DejaVu Sans Mono 11 for fixed-width, so Qt and GTK render identically. The GTK half lives in gsettings (`org.gnome.desktop.interface font-name`, untracked dconf) rather than in `gtk-3.0/settings.ini`, so changing one side means changing both. When comparing fonts across the two, measure cap height rather than point size — point sizes are not comparable between typefaces. KDE Frameworks apps (Dolphin, etc.) ignore a qt5ct/qt6ct palette entirely and render fully light under `QT_QPA_PLATFORMTHEME=qt5ct`, so the colour scheme has to live in `kdeglobals` (generated from `themes/templates/kdeglobals.tmpl`). The `.config/qt{5,6}ct` configs remain only for Qt5 apps (VLC), which plasma-integration 6 does not cover — launch those with `QT_QPA_PLATFORMTHEME=qt5ct` if they need theming. KDE apps are single-instance, so testing a `kdeglobals` change needs `killall dolphin` first or the old process' cached config is reused. That variable is the whole of whether any of this applies: without it plasma-integration is never loaded, `kdeglobals` is never read, and Dolphin renders in stock Breeze Light no matter what `theme` generated. It lives in `environment.d` and **not** in `.config/uwsm/env` because it is not Wayland-session setup — sway starts as a user unit (`wayland-wm@sway.desktop.service`, under uwsm), so both files reach it, and the split is by what the variable is for. `environment.d` is read by the user manager, and sway being one of its units is what carries the variable into everything sway `exec`s. It applies at manager start, so the change lands at the next login: a `daemon-reload` fixes new *units*, but the running sway's own environment cannot be changed, and apps it launches keep inheriting what it started with.

  Running Qt apps repaint without a restart because `notify_kde` sends what `plasma-apply-colorscheme` sends: a `ConfigChanged` on `/kdeglobals` (`org.kde.kconfig.notify`) *and* a legacy `notifyChange` on `/KGlobalSettings` (`org.kde.KGlobalSettings`) carrying `PaletteChanged`, `StyleChanged` and `IconChanged` (0, 2, 4). The second one is what actually repaints — plasma-integration's `KHintsSettings` still listens on the KDE4-era interface, and rewriting `kdeglobals` with only the kconfig signal leaves every open window on the old palette. Captured by running `dbus-monitor` against a real `plasma-apply-colorscheme` run, and verified by screenshotting Dolphin across `theme set nord` / `theme set catppuccin-macchiato`.
- **Fonts** (`.local/share/fonts/`): SauceCodePro Nerd Font is **vendored**, the same call as adw-gtk3, the Phosphor icons and `emoji.txt` — `.config/alacritty/font.toml` and `.config/Code/User/settings.json` both name it outright, and `vim.g.have_nerd_font` assumes its glyphs, so a fresh machine that has to download it comes up with the wrong font in every terminal. Like adw-gtk3 it needs no `install` support at all: `$XDG_DATA_HOME/fonts` is `~/.local/share/fonts`, already inside `.local`, so the ordinary symlink loop puts it in place.

  Two things make the arrangement work, both established by spike rather than assumed. **fontconfig recurses into subdirectories** of a declared font directory — verified with a face nested two levels deep under a `<dir>` that named only the parent — so the faces can live in their own `SauceCodePro/` subfolder instead of being strewn across `~/.local/share/fonts`. And **fontconfig registers symlinked font files**, which it has to, because `install` links rather than copies. No `fc-cache` call is needed either: fontconfig rescans a directory whose mtime has changed.

  Only the **base family** is vendored — 14 faces, 33MB. Upstream's `NerdFontMono` and `NerdFontPropo` variants (28 more faces, 68MB) are dropped for the reason adw-gtk3's `gtk-4.0/` is: nothing resolves them. Both consumers ask for the family `SauceCodePro Nerd Font`, which is the base. Every weight is kept rather than just the four that render today, so changing `font.toml` to another style does not need a trip back to the nerd-fonts release; alacritty remaps bold to Semibold (`font.bold.style`), so what it actually draws is Regular, Italic, SemiBold and SemiBoldItalic, while the VS Code terminal has no such remap and takes Bold. Adding a face means dropping the `.ttf` in and re-running `./install`. Note that a **copy** rather than a move when vendoring registers every face twice, since `install` then links the repo copy into the directory still holding the original.

- **Scripts** (`.local/bin/`): standalone helper scripts, mostly for Sway/Wayland (brightness, volume, output scaling, etc.).

- **Output configuration** (`.local/bin/sway-outputs`, `sway-outputs.service`): the sway config names no output at all — mode and scale are derived from each panel's EDID at login and on hotplug.

  Sway's own default is the EDID **preferred timing**, and on the Odyssey G9 that is 3840x1080, which is why the config used to carry a hand-written `mode 5120x1440@240Hz`. "Biggest mode" is not the fix either: the same panel advertises 3840x2160 (8.29MP), which beats its native 5120x1440 (7.37MP) on pixel count. Modes are therefore ranked by **aspect ratio first** — against the panel's physical size from the EDID — then pixel count, then refresh. Measured on that monitor: with the aspect term the rule picks 5120x1440@240, without it 3840x2160@60. This is the trap way-displays falls into too (its `mode_max()` compares `width * height`, so `MODE: MAX: TRUE` picks the wrong mode there and you are back to hand-configuring), and kanshi has no best-mode or auto-scale concept at all — which is why neither is installed.

  The scale ladder is **integer**: 2 at or above 165 DPI, 1 below. Fractional scaling costs Xwayland sharpness, and 1/2 is what this setup always used by hand. DPI alone ignores viewing distance, so a 48" desktop panel and a 14" laptop at the same DPI do not want the same scale; `scaleOverrides` and `modeOverrides` at the top of the script are the escape hatch, keyed by either the sway identifier (`make model serial`) or the connector name. Prefer the identifier — **connector names are not stable**: this monitor moved from HDMI-A-1 to DP-2 and silently orphaned both `output` lines and the aspect-toggle script, with no symptom beyond the resolution being wrong.

  Four things the implementation settles, each established by spike:

  - **With no readable EDID, do not guess.** Ranking on pixel count alone is not a neutral fallback — it is what picks this panel's 3840x2160 (8.29MP) over its native 5120x1440 (7.37MP), i.e. exactly the wrong answer, and the one that looks like "it chose a lower resolution". An output with no EDID and no override is left to sway's own preferred-mode choice, and is deliberately *not* added to the seen-set, so a read that failed transiently at startup is retried on the next output event.
  - **Sway's IPC does not report physical size**, so it comes from `/sys/class/drm/card*-<name>/edid` — detailed timing descriptor 1 (whole mm) in preference to the base block (whole cm). The connector directories are **symlinks**, so the glob needs `(-/)` and not `(/)`; and a sysfs binary attribute always stats as **zero bytes**, so the guard is `-r`, never `-s`. Both of those fail silently, leaving every output at aspect 0 and the wrong mode.
  - **`(#b)` backreferences need `setopt extended_glob`**, which a script does not inherit from the interactive shell. Without it every `modeOverrides` value fails to parse.
  - `resolve()` runs inside a command substitution, so a `die()` there exits only the subshell — it is reported once per caller and the script carries on. Overrides are therefore validated up front in the main shell.
  - **A `swaymsg output` is a full modeset**, which is lockup trigger #1 (see `.claude/sway-lockup-investigation.md`), so nothing is ever issued unless it is a real change. `apply` on a correctly configured output prints `(unchanged)` and touches nothing.

  **Applying over IPC is not enough on its own, and this is the central fact about the whole arrangement.** Sway resets an output it has no config for to its EDID preferred mode *and* its default scale on **every** apply — `swaymsg reload` included, which the quickshell power menu offers as "Reload Sway". That is `queue_output_config` in `sway/config/output.c`: with no matching `output_config` supplying `width`/`height` it calls `wlr_output_preferred_mode`, and with none supplying `scale` it calls `compute_default_scale`. So a reload silently dropped this monitor from 5120x1440 to 3840x1080, and the watcher's seen-set (below) meant nothing put it back.

  So what `sway-outputs` resolves is also **written to a generated sway include**, `~/.config/sway/outputs.conf`, which `sway/config` `include`s — the same arrangement as `theme.conf`, and generated into the live config directory rather than the repo, so it is never tracked. Sway then owns the values: they are applied at startup before the first frame, and reasserted on every reload. Entries are keyed by identifier and **merged rather than rewritten**, so a monitor that is currently unplugged keeps its line and comes back correct the instant it is plugged in, before the watcher has even seen the event. `install` writes a one-line stub if the file is absent, since sway parses the `include` before anything has had a chance to generate it. Verified that sway really reads it by putting a bad directive in it and watching `sway --validate` name the file and line.

  A corollary worth knowing: a runtime override (`sway-scale`, `sway-toggle-aspect`) holds until the next reload and is then reverted to the generated value. That is the same behaviour the hand-written `output` line always had.

  `watch` configures an output **once, when it appears**, keyed on the identifier and dropped when it disconnects. It cannot re-apply on every event: a mode or scale set by hand afterwards (`sway-scale`, `sway-toggle-aspect`) fires an output event of its own, and re-applying on that would undo it a frame later. The cost is that a service restart forgets the set and reverts a hand-set value once. `swaymsg -r -m -t subscribe '["output"]'` is the change signal, debounced 300ms because a hotplug arrives as a burst; if that child dies the loop ends and `Restart=always` rebuilds it.

  `sway-outputs show` reports what it resolved for every output; `scale` and `mode` print one field, which is how `sway-scale default` and `sway-toggle-aspect` stay in step with the ladder rather than carrying their own copy of it. `mode` also takes an aspect ratio — `sway-outputs mode DP-2 16:9` — and then returns the best mode at that shape **that still fits inside the native one**. That bound is the whole point of it: the G9's largest 16:9 mode by pixel count is 3840x2160, which the panel cannot display (1440 rows of hardware) and must downscale, while the bounded answer is 2560x1440@240, landing on the native pixel grid exactly.

  `sway-laptop-lid` follows the lid, and names neither the panel nor the lid device — the same portability argument as the rest of this section, since the config is meant to drop onto a second laptop unedited. The panel is any DRM connector of an **internal** type (`eDP`, plus `LVDS` and `DSI` for older machines and tablets) whose `status` reads `connected`, which is also the test for "is this a laptop": logind reports a lid state on machines that have no lid, so gating on the lid would be wrong, while gating on the panel makes the script a no-op on a desktop. The state itself comes from logind's `LidClosed` property rather than `/proc/acpi/button/lid/*/state`, which does not exist on every machine — the ACPI path stays as a fallback, globbed, because the device under it is `LID`, `LID0` or a PNP id depending on the firmware. With no source answering it does nothing rather than guessing.

  Sway's `bindswitch` passes the state explicitly (`lid:on` is **shut**, per `man 5 sway`), and `exec_always sway-laptop-lid` with no argument reads it at startup, which is what picks up a lid that was already closed. `--reload` on both bindings is load-bearing now that outputs.conf exists: a reload re-enables every output the include names, and re-running the binding matching the current lid state is what shuts the panel again. Verified against a fake DRM tree — a connected `eDP-1` and `LVDS-1` are found while a connected external `DP-1` and a disconnected `eDP-2` are not.

  `sway-toggle-aspect` ($mod+Ctrl+backslash) swaps the focused output between those two, and takes an optional `W:H` argument. It replaced `sway-samsung-width`, which halved a hardcoded `HDMI-A-1` — the connector this monitor has not been on for some time. It compares **resolution only** when deciding which way to go, since the refresh in a mode string is rounded, and falls back to native from any third state; on a panel whose native mode already is the requested shape it says so and does nothing.
- **Quickshell** (`.config/quickshell/`): the Wayland status bar, built with [Quickshell](https://quickshell.outfoxxed.me/) (QML). It replaces swaybar/i3blocks; sway declares no bar of its own and does not start it directly — `quickshell.service` does, via `sway-session.target` (see the systemd section below). `shell.qml` is the entry point, defining a `PanelWindow` top bar per screen (`modules/bar/Bar.qml`). Colors come from `config/Theme.qml`, which reads the generated `~/.config/quickshell/palette.json` through a `FileView` with `watchChanges`, so a theme switch repaints the bar with no restart; its hardcoded Catppuccin values are only fallbacks for before the file loads. Every colour is still a binding, so `readonly` properties update fine. QML edits hot-reload — but a **new** file (a new singleton especially) needs a full restart, since hot-reload will not register it and the bar dies with "X is not defined". Restarting means `systemctl --user restart quickshell`, and its log is `journalctl --user -u quickshell` rather than sway's `systemd-cat` stream. `swaymsg reload` does not restart the bar, and a theme switch does not reload sway at all.

  The tree is `config/` (`Theme`, `Appearance`, `Paths`, `Icons` — data, no behaviour), `services/` (singletons owning state and `IpcHandler`s, no visuals), `widgets/` (leaf components importing only `config/`), `windows/` (window chrome, adding `services/FocusedScreen`) and `modules/<feature>/`, which may import anything. Quickshell synthesizes a `qmldir` per directory and registers the config root as module `qs`, so `import qs.services` works and singletons auto-register across directories — **do not write a `qmldir` by hand**, which permanently disables synthesis for that directory. `dev.qml` is a second entry point for working on one surface at a time (`quickshell -p ~/.dotfiles/.config/quickshell/dev.qml`); `-p` roots the config at the same directory so `import qs.*` resolves identically. Never instantiate the polkit agent, `SystemTray` or a notification server there — each claims a D-Bus name and would fight the running shell.

  `Theme` is the palette and `Appearance` is the design (fonts, icon sizes, bar height), the same split CLAUDE.md argues for tmux: a theme switch touches only the first. `services/FocusedScreen` resolves the output holding the focused sway workspace and every modal surface binds `screen` to it; it falls back to `Quickshell.screens[0]` because a `PanelWindow` on a null screen fails to map with "no output to auto-assign layer surface to". `windows/ModalOverlay` owns the whole overlay-layer-surface pattern — exclusive keyboard focus, scrim, blocking `MouseArea`, Escape, and a card that is centred or, given an `anchorItem`, hung under it — and its children become the card's column; `PolkitDialog`, `Launcher`, `WindowSwitcher` and every `BarPopup` are built on it, along with `widgets/{Button,TextField,ListRow,FilterList}`. An anchored card re-measures its position on every open, because bar items shift as their neighbours change width — the notification bell moves the moment its unread count gains a digit. `windows/CountdownDialog` is a `ModalOverlay` too — it lives in `windows/` rather than `widgets/` because a widget may import only `config/`. It is named for what it does rather than `ConfirmDialog`, which stays free for an ordinary wait-for-an-answer dialog.

  `widgets/FilterList` is the search-field-over-a-scored-list behind the launcher, the switcher and the session menu. The caller supplies `source`, a `fields` function returning searchable strings most-significant-first, an additive `weight`, and a full `ListView` delegate that reads `ListView.isCurrentItem` and sets `ListView.view.currentIndex` on hover. Three things it settles that are easy to get wrong:

  - **`fields` falls off multiplicatively** (`fieldFalloff`, 0.55 per position), not by a fixed subtraction. A prefix hit in a long *comment* scores higher than a mid-word hit in a *name*, so a small penalty leaves "chr" ranking some screensaver's description above Google Chrome.
  - **`weight` is added to the score, not used as a tie-break.** Scores are rarely equal, so a tie-break never fires where it matters; adding frecency is what lets a daily-used app outrank an unrelated prefix match. With an empty query every score is 0, so `weight` alone orders the list — which is how the launcher shows frecency order and the switcher MRU order. It also means the *source* order is the final fallback, so `Launcher` sorts its entries by name: unsorted, a fresh install lists apps in `DesktopEntries` scan order.
  - **Home and End are only reachable through `TextField.keyHandlers`.** A `TextInput` accepts them for cursor movement, so a `Keys` handler further up the focus chain never sees them; `keyHandlers` binds `Keys.forwardTo` on the inner input, which gets first refusal on every key. Up/Down/PageUp/PageDown/Ctrl-N/Ctrl-P need no such help — a single-line `TextInput` ignores them and they bubble.

  `searchable: false` drops the field entirely and gives the list focus, which is what frees bare letters for accelerators — `PowerMenu` uses it for its `l`/`w`/`q`/`o`/`s`/`h`/`r`/`p` mnemonics, most of them carried over from the sway `mode $session` block it replaces. `TextField` is a `FocusScope` so `forceActiveFocus()` on the field reaches the inner `TextInput`.

  Renaming or moving a file here needs `./install` (to create the new link) and leaves a dangling old link that `dot-prune` removes — `install` runs it, but a stale link left in place kills the shell at load. `find ~/.config/quickshell -xtype l` must print nothing.

  Icons are vendored Phosphor SVGs in `icons/`, drawn by `widgets/Icon.qml` as `Icon { name: "bell"; color: Theme.yellow }`. `config/Icons.qml` reads the SVG through a `FileView` and caches it (its `Qt.resolvedUrl("../icons")` is relative to `config/`, not to the config root); `Icon.qml` swaps the file's `#ffffff` placeholder fill for the requested colour and hands the result to `Image` as a `data:` URI. Recolouring has to happen in the SVG markup — tinting the rendered image with `MultiEffect` (either `colorization` or an alpha mask) blows out thin strokes at bar sizes until enclosed shapes fill in solid. To add an icon, drop the file from [Phosphor](https://phosphoricons.com/) (regular weight) into `icons/`, replace its `fill="currentColor"` with `fill="#ffffff"`, and re-run `./install`.

  Workspace icons are named by sway: each `set $wsN` in `.config/sway/config` carries a `<span foreground='...'>icon-name</span>`, and `modules/bar/Workspaces.qml` parses the span for the colour and the icon name. Sway only applies renamed workspaces to newly created ones, so after editing those lines, existing workspaces keep their old names until `swaymsg rename workspace` is run or they are recreated. Each value is **double-quoted**, and that is load-bearing: sway names the workspace that already exists at startup after the `workspace number` binding mentioning it (`workspace_next_name`), and that path strips one level of quoting where the runtime `workspace number` command does not. Unquoted, the first workspace comes up as `1: 1 <span foreground=#89b4fa>envelope</span>` — the colour's quotes gone, so the span no longer parses — and the bar shows the icon's *name* as text until you switch away and back, which recreates the workspace through the ordinary path. Quoting in the `bindsym` instead works identically; quoting in both cancels out. `Workspaces.qml` draws the label as `Text.PlainText` so a name that does fail to parse is at least visibly raw markup: under `AutoText` it is rendered as rich text, which is what turned the broken name into a plausible-looking `1 envelope`.

  `modules/bar/Bar.qml` lays out three sections — `left`, `centre`, `right` — each full height, so an item can measure against `parent.height`. A new item goes into whichever section it belongs in. Nothing is drawn between items — the right section's wider `spacing` is what stands in for the separators it used to carry. The centre is positioned against the bar's own centre rather than laid out between the other two, so the clock stays put no matter what grows on either side; it also means the sections can overlap if one ever gets wide enough, which at these widths they do not.

  `left` and `right` are `Row`s, but the **centre is not**: a Row would slide the clock left by half of whatever was added beside it. It is an `Item` spanning the full bar width, with the clock pinned to `horizontalCenter` and everything else anchored off the clock's own edge so it grows outward — measured invariant at the bar's centre line (±0.5px, glyph bearings) while the media item's width moved 184px → 120px across a track change. Spanning the bar shadows nothing, since a bare `Item` takes no input and only the children do.

  The bar is always visible and reserves its own height via `ExclusionMode.Auto`, so windows start below it.

  `services/ThemeService.qml` holds the theme list read from the generated `themes.json` and owns an `IpcHandler` on target `theme`, so `quickshell ipc call theme toggle` opens the picker from a sway keybind ($mod+Ctrl+t); `modules/bar/ThemeToggle.qml` is the palette icon in the bar. `modules/theme/ThemePicker.qml` is the view, a `BarPopup` hung under that palette icon and so instantiated in `ThemeToggle.qml` rather than in `shell.qml`, one per bar with a focused-screen gate. Its `expanded` is *assigned* from a `Connections` on `active` rather than bound to it, because `BarPopup` clears `expanded` on dismiss and an assignment would break a binding for good — the same arrangement the notification centre uses, and for the same reason: both are opened over IPC as well as by their bar item. Those bindings are also what warms `ThemeService`, which is otherwise reached only through a click handler and an `IpcHandler`, and so would never register that handler at all. Highlighting a row sets `Theme.preview` and `Theme.previewWallpaper`, which override the loaded palette so the running bar, the picker's own card and the wallpaper preview that theme. **`commit()` deliberately does not clear the preview** — only `hide()` does, on escape or click-outside. Clearing it at commit drops the desktop back to the old theme for as long as `theme set` takes to write the new palette, which is a blink for the colours and a full-screen flash for the wallpaper; `Theme` ends the preview instead when the new `palette.json` loads. Only quickshell previews live — everything else changes on commit.

  `services/NotificationService.qml` is the session's notification daemon, replacing dunst (stopped and **masked** — `systemctl --user mask dunst`; the local binary, its user unit and its D-Bus service file are left on disk so the rollback is `unmask` + `start`). It owns the `NotificationServer`, the popup queue and a 100-entry history ring buffer persisted to `Quickshell.statePath("notifications.json")`, whose directory is keyed by a hash of the config path — so `dev.qml` gets its own history and cannot clobber the real one. `modules/notifications/NotificationPopups.qml` is the transient stack and `NotificationCentre.qml` the history view; both hang under `modules/bar/NotificationIndicator.qml`'s bell, so both are instantiated there rather than in `shell.qml` and there is one of each per bar. The centre is a `BarPopup`; the stack cannot be one, because a `ModalOverlay` takes exclusive keyboard focus and covers the screen with a click-catcher — every arriving notification would steal the keyboard and swallow the next click. It stays a focus-less `PanelWindow` masked down to its card and borrows only the look, through `widgets/AttachedOutline`. Being per-bar, `screen: FocusedScreen.screen` becomes a gate on the bar's own screen, which is what still matches dunst's `follow = keyboard`; read that screen off the anchor item and **not** off the window's own `screen`, which Quickshell resolves as the window maps and so loops back through `visible`. The centre's `expanded` is *assigned* from a `Connections` on `centreVisible` rather than bound to it, because `BarPopup` clears `expanded` on dismiss and an assignment would break a binding for good. Sway calls it at `config:311-313` — `$mod+n` invokes the newest notification's default action (what `dunstctl action` did), `$mod+Ctrl+n` opens the centre, `$mod+Alt+n` toggles do-not-disturb.

  Three things about the freedesktop API as Quickshell 0.3.0 exposes it, each established by spike rather than assumed. `Notification.expireTimeout` is **milliseconds** passed straight through from D-Bus, with `-1` meaning "server default" (5s/10s/never by urgency, matching the old `dunstrc`). `notify-send -i <name>` arrives as the `image-path` hint and lands in `notification.image` as an `image://icon/<name>` URL, *not* in `appIcon` — so `image` is the primary icon source and `appIcon` only the fallback. And `trackedNotifications` has not yet been updated when the `notification` signal fires, so the service keeps its own arrays rather than reading that model.

  **Replacing a notification by id mutates the existing `Notification` in place and emits no new `notification` signal.** A record holding a copy of the fields therefore goes stale, which is why `NotificationCard` reads the live object through `entry.notification` and falls back to the stored copy only once the notification is gone (restored from disk, or closed by its sender). `summaryChanged`/`bodyChanged` are the only "this was replaced" signal on offer; they drive re-popping an already-expired notification, moving it back to the top of history, and re-saving.

  The popup cap (5) lives in the view, not the service, so notifications past the cap still expire on their own schedule and are only *hidden* behind an "N more" row — which is what dunst's `indicate_hidden` did. `IpcHandler` functions are `open`/`close`, not `show`/`hide`: `quickshell ipc call <target> show` is swallowed by the CLI's own `ipc show` subcommand (this bites `theme show` too).

  `services/LauncherService.qml` + `modules/launcher/Launcher.qml` replace `wofi --show=drun` and `--show=run`, `services/WindowService.qml` + `modules/switcher/WindowSwitcher.qml` replace `window-switcher.py`, and `services/PowerService.qml` + `modules/bar/Power.qml` + `modules/power/PowerMenu.qml` replace `system-menu` and its zenity confirmations. Sway calls all three over IPC — `$mod+Space` (`launcher toggle`), `$mod+Shift+Space` (`launcher run`), `$mod+Alt+Space` (`windows toggle`), `$mod+Shift+Escape` (`power toggle`). wofi, zenity, `system-menu`, `window-switcher.py` and `get-icon` are gone, and with them the last PyGObject/GTK dependency; the wofi and zenity binaries are left installed but unused.

  **Apps are launched with `I3.dispatch("exec …")`, never a `Process`.** Sway runs `exec` through `/bin/sh` (so the argv from `entry.command` has to be shell-quoted back into a line), and the resulting process lands in sway's own session scope rather than `quickshell.service`'s control group — verified by reading `/proc/<pid>/cgroup` and by watching a launched window survive `systemctl --user restart quickshell`. As a quickshell child it would be killed with the shell on every restart. `exec` takes no `--`; `I3.dispatch("exec -- cmd")` silently does nothing.

  Four things about `DesktopEntries` in 0.3.0, each established by spike:

  - **The scan starts on the first read of the model and fills in asynchronously.** Reading `DesktopEntries.applications.values` for the first time inside `show()` returns an empty array and opens an empty launcher; the model is only populated a moment later, entry by entry (`valuesChanged` fires per entry). `LauncherService.applications` is a plain binding for exactly this reason — instantiating `Launcher` in `shell.qml` is what warms it at startup.
  - **`command` is already the `%`-code-stripped, shell-unquoted argv.** `execString` keeps `%u`/`%F` and the quoting; `command` is a real string list with them removed. There is nothing to strip by hand.
  - **`NoDisplay=true` entries are excluded from the model already** (277 files on disk, 228 in `values`, `noDisplay` false for all of them), so filtering on `!noDisplay` is a no-op. **`OnlyShowIn`/`NotShowIn` are not applied, and not exposed either** — see below.
  - **New `.desktop` files are picked up at runtime** — no restart needed.

  Because `DesktopEntry` exposes neither `OnlyShowIn` nor `NotShowIn`, `LauncherService` re-reads the `.desktop` files itself in a one-shot `Process` and keeps the ids to hide in `hidden`. This is not pedantry: 107 xscreensaver hacks ship `OnlyShowIn=MATE;` from `xscreensaver-gl`/`xscreensaver-data` under `/usr/share/applications/screensavers/`, and with the lxqt and GNOME control-centre panels they were **129 of 228 entries** — the launcher shows 99 with the filter on. The id is the path below `applications/` with `/` turned into `-`, which is the spec's desktop-file ID and what `DesktopEntry.id` holds.

  **That embedded script must contain no backslash and no `${…}`.** It lives in a QML template literal, where `\/` collapses to `/` and `\[` to `[` — which turns an awk regex into a syntax error, and since the failure is on stderr the only symptom is that nothing gets filtered. The awk is written with `index()`/`substr()` and string-form regexes for exactly this reason, and the shell side splits `XDG_DATA_DIRS` with `IFS=:` rather than `tr : '\n'`. The scan runs once at startup, so a desktop-restricted entry installed mid-session is not re-checked.

  `Quickshell.iconPath(name, true)` returns `""` when the icon is missing, and `Quickshell.iconPath(name, fallbackName)` returns a URL carrying `?fallback=`, which is what the launcher and switcher use so a missing app icon still renders something. It logs a burst of `qt.svg.draw: The requested buffer size is too big` for a handful of oversized system SVGs on the first open after a restart, then never again — Qt caches per icon.

  **The window switcher takes its list from sway's tree, not `ToplevelManager`**, which has no workspace concept. `Quickshell.I3` exposes only `workspace` and `output` events through `rawEvent`, so `WindowService` runs a `swaymsg -r -t subscribe -m '["window","workspace"]'` of its own (`-r` gives one JSON object per line, which `SplitParser` wants) and re-reads `get_tree` on every event, debounced 40ms. There is no hand-maintained MRU: **sway's per-container `focus` arrays are the focus history**, so walking children in that order yields the MRU list directly and it cannot drift. The switcher preselects row *1*, not 0 — row 0 is always the focused window, so starting below it makes a single press an alt-tab.

  `StdioCollector`'s **`data` is a byte array; the string is `text`.** `JSON.parse(data)` happens to work because it coerces, so a `get_tree` collector reads fine and a `data.split("\n")` on the next one throws `Property 'split' ... is not a function` and silently leaves the list empty. Use `text`.

  Frecency lives in `Quickshell.statePath("launcher.json")` as `{ id: { count, last } }`, weighted by recency bucket (<1d ×4, <7d ×2, <30d ×1, older ×0.5). Desktop actions (`entry.actions`) appear as indented sub-rows, but only once there is a query — with none they would pad the list with rows nobody asked for, which is why wofi hid them outright (`no_actions=true`). Run mode lists every executable on `PATH` and falls back to running the typed line verbatim, so a command with arguments still works.

  "Reload Sway" and "Restart Quickshell" sit between Lock and Log Out. Sway has no restart-in-place, so the first is `swaymsg reload` — which is lockup trigger #1, and which `theme` no longer needs now that it applies colours with targeted `swaymsg client.*` commands, so it is in the menu because it is asked for by hand and not because anything else uses it. Neither confirms: both are recoverable, and a countdown in front of restarting the bar is ceremony. Restarting quickshell from inside quickshell works because the action is dispatched as a sway `exec`, so the `systemctl` client lives in sway's scope rather than the unit being restarted. `windows/CountdownDialog` inverts what zenity did: its `countdown` (seconds, `PowerService.confirmSeconds`, one value for every action) ticks down and fires `accepted` at zero, so waiting confirms rather than cancels and the dialog is an announcement with an escape hatch, not a question. That is also why the actions carry a `confirm` flag rather than a question string — "Are you sure you want to reboot?" above "Reboot in 8 seconds" asks something the dialog then answers itself. The **accept** button holds focus, not Cancel — picking an action in the menu and pressing Return again goes straight through, which is the point of a dialog that was going to proceed anyway. That in turn is why `widgets/Button` ignores `event.isAutoRepeat`: the dialog opens under a Return that may still be held, and at sway's default 600ms repeat delay the repeat would otherwise land on the freshly focused button and skip the countdown entirely. The menu closes before anything is dispatched, so a polkit prompt never contends with it for exclusive keyboard focus. The countdown is `modules/power/PowerConfirm.qml`, instantiated once in `shell.qml` rather than per bar as the menu is: it is a modal on the focused output, and the action it announces is not tied to the bar the menu was opened from.

  `services/{AudioService,BrightnessService,OsdService}` + `modules/osd/Osd.qml` replace `.local/bin/volume` and `.local/bin/brightness`, and with them the notify-send-as-OSD pattern that used to put every volume keypress into notification history. Sway calls them on the media keys — `quickshell ipc call audio up|down|mute|micMute` and `brightness up|down`. pamixer and brightnessctl are left installed but unreferenced.

  There is **one** OSD surface, not one per source: `OsdService` holds only `active` and a `source` name plus the 2s timer, and `Osd.qml` owns the three descriptors, so a volume keypress and a brightness keypress a moment apart replace each other rather than stack. It sits bottom **centre**, out of the way of everything anchored to the bar, and is click-through via `mask: Region {}` — an overlay layer surface otherwise swallows every pointer event in its geometry for its whole lifetime.

  **A QML singleton is created when it is first referenced.** A service reached only over IPC therefore never registers its `IpcHandler` — `AudioService` and `BrightnessService` instantiated nowhere loaded clean and did nothing, with `quickshell ipc show` listing neither target. Referencing them inside a conditional is not enough either, since JS short-circuits; `Osd.qml`'s three descriptors are unconditional bindings, evaluated at completion, and that is what brings both services to life. Anything IPC-only in future needs the same.

  `AudioService` reads Pipewire, and two things about it: `Pipewire.defaultAudioSink` is **null at `Component.onCompleted`** (`ready` false), so every read is `?.`-guarded; and without the `PwObjectTracker` a node reports its defaults rather than real values. `PwNodeAudio.volume` (0..1) is the same scale pamixer printed, so the 0.05 step is exactly the old `pamixer -i 5`. Up and down unmute first, as the script did.

  `BrightnessService` writes `/sys/class/backlight/*/brightness` directly — it is `root:video 0664` and the user is in `video`, so no brightnessctl. The write needs **`atomicWrites: false`**: FileView's default write-to-temp-then-rename is refused by sysfs. `watchChanges` + `onFileChanged: reload()` is what picks up the firmware's own hotkeys, and `onSaveFailed: reload()` is what stops the optimistic `level` in `set()` from lying when a write is refused — a refused write leaves the file unchanged, so nothing else would correct it. The device is discovered asynchronously by a one-shot `ls -1 /sys/class/backlight | head -1`, which works because **a `FileView` with `path: ""` is silent** (no load, no error); until `max_brightness` loads, `available` is false and the keybinds do nothing. The step is brightnessctl's `10%` of the full range, and the floor is one raw unit rather than zero, deliberately: a panel at zero is indistinguishable from a session that has died.

  `widgets/LevelBar` is the read-only fill bar both the OSD and `NotificationCard`'s `-h int:value:` progress draw; `widgets/Slider` is the same bar with a grab, and the caller keeps `value` bound to its own state and writes through the `moved` signal so the binding is never broken.

  `modules/bar/Volume.qml` + `modules/audio/AudioPanel.qml` replace **pasystray** (`config:85`, gone). The bar item is icon + percentage — click toggles the panel, middle-click mutes, wheel adjusts without the OSD, since the number the OSD would show is already on the bar. The panel is output and input level rows, the two device lists, per-app stream volumes, and an "advanced…" link to `pavucontrol` for everything Pipewire exposes that this does not (routing, profiles, moving one app to another device) — which is why the `pavucontrol` floating rule stays.

  `services/BluetoothService.qml` + `modules/bar/Bluetooth.qml` + `modules/bluetooth/BluetoothPanel.qml` replace **blueman-applet** (`config:86`, gone, along with the dead `blueman-services` / `blueman-sendto` window rules; its XDG autostart entry is shadowed, see Autostart). The panel is adapter power, then the paired devices — click to connect or disconnect, hover for a forget `x`, battery percentage where BlueZ offers one. `Quickshell.Bluetooth` reports a freedesktop icon name per device class (`audio-headset`, `input-mouse`, `phone`, …) which `deviceIcons` maps onto vendored Phosphor icons, falling back to `bluetooth`.

  **Quickshell 0.3.0 registers no `org.bluez.Agent1`** — the binary carries `Adapter1`, `Device1` and `Battery1` and nothing else — so it cannot answer a PIN or a confirmation and `pair()` is unreliable by construction. That alone keeps **pairing and discovery out** of the panel; a second reason, that a scan list could not refresh inside a size-locked popup, no longer applies now that `BarPopup` is a layer surface. "advanced…" launches `blueman-manager`; that D-Bus-activates `blueman-applet` (`SystemdService=blueman-applet.service`), which *is* the agent, and both exit when the window closes — verified by killing every blueman process, opening the panel's link, and watching the applet reappear under `user@1000.service` and then go away again. No tray icon comes back with it, so nothing duplicates the bar item.

  The device list is sorted **by label alone**, never connected-first: sorting by state means clicking a device reorders the list under the cursor, sliding the next row — and the forget `x` that appears on hover — under the pointer. Same reasoning as the audio panel's device lists, one degree worse because here the click is what triggers the move.

  `services/NetworkService.qml` + `modules/bar/Network.qml` + `modules/network/NetworkPanel.qml` cover the part of **nm-applet**'s menu that got used: the wifi radio, the access points in range, the wired link, and the saved VPNs, with "advanced…" launching `nm-connection-editor`. The bar item is the signal-strength icon plus a green `shield-check` badge whenever a VPN is up.

  **nm-applet itself keeps running**, now from `/etc/xdg/autostart/nm-applet.desktop` rather than a sway `exec` (see Autostart). It is NetworkManager's *secret agent*, and Quickshell registers none — the binary has zero `SecretAgent` strings — so without it an 802.1x network fails silently and the `Lytx` openconnect VPN cannot connect at all, its cookie, gateway and cert secrets all carrying `flags = 2` (never saved, ask the agent every time). Unlike blueman-applet it has **no D-Bus service file**, so it cannot be summoned on demand the way `blueman-manager` summons the BlueZ agent; it has to be resident. Verified standalone: killing it and starting `app-nm\x2dapplet@autostart.service` alone leaves it running and active. What changes is only that `Tray.qml` now filters its item out by `id` (`"nm-applet"`, read off its SNI `Id` property) so the bar does not show two network indicators. That `hidden` list is the place to drop any other applet kept alive purely for a D-Bus role.

  `scannerEnabled` is off until the panel opens, and the list then goes from 1 entry to all of them over about five seconds. It fills a fixed-height `ListView` (`listRows` × `rowHeight`) that scrolls: originally because a popup could not resize, now because a list that grows under a stationary cursor moves the row you were about to click. Same reason `FilterList` has `fixedHeight`. The password prompt for an unknown WPA network replaces that list inside the same box rather than being appended below it: the card is free to grow, but growing it would shift the rows at the moment one was clicked. Escape is handled on the prompt itself so it puts the list back instead of bubbling to the card and closing the whole panel.

  Access points are sorted **by name alone**, the 8b rule one degree stronger again: signal strength moves on its own every few seconds, so sorting by it slides rows under a stationary cursor with no click involved at all.

  Quickshell 0.3.0's `Networking` has no VPN concept, so that half is nmcli: `nmcli monitor` as the change signal, debounced 200ms into a one-shot `nmcli -t -f NAME,UUID,TYPE,STATE connection show`, filtered to `vpn` and `wireguard`. `-t` escapes a literal colon in a field as `\:` and only the name can contain one, so the fixed trailing fields are split off the **right**. Verified end to end against a throwaway wireguard connection: adding and removing it moved the panel's list live, an external `nmcli up` lit the row and the bar badge, and clicking the row brought it back down.

  Two things about `Quickshell.Networking`, both established by spike:

  - **The model starts loading on the first read and fills in asynchronously**, exactly as `DesktopEntries` does. Read at `Component.onCompleted` it reports `devices: 0`, `wifiEnabled: false` and `connectivity: Unknown`, and is only right a second or two later — so every value is a binding and `Network.qml` in the bar is what warms it at startup.
  - **`networks` holds only the connected AP until `scannerEnabled` is set**, so the visible-network list does not exist until something asks for it.

  **A signal handler written at the instantiation site replaces the component's own**, it does not run alongside it: an `onVisibleChanged` next to `NetworkPanel { … }` in the bar silently overrode the one in `NetworkPanel.qml`, which is why the scan toggle lives in the panel with the prompt reset it shares a handler with.

  `windows/BarPopup` is the chrome behind all three panels: children stack in a column and the card sizes to them. It is a `ModalOverlay` with an `anchorItem` — an overlay layer surface hung under a bar item — and **not** a `PopupWindow`, which is the single most important thing about it.

  It sets `ModalOverlay`'s `attached` mode, which is what makes it read as the bar itself expanding rather than as a box floating under it: the card's top edge is unstroked and its top corners curve the *other* way, flaring `flare` px past each side so the card's walls grow out of the bar's bottom edge. `cardColor` is `Theme.barBackground` rather than `popupBackground` for the same reason — a mantle card under a base bar draws a horizontal seam exactly at the join, which is the one line the whole treatment exists to erase. The outline is `widgets/AttachedOutline`, a `Shape` — a concave corner needs real transparency in the notch, so it cannot be faked with a `Rectangle` and an overlay — and the notification stack draws with it too. The flare overflows the card, so the clip that hides the content during the roll-down sits on an inner `Item`, never on the card; and an anchored card is clamped to keep `flare` px of screen on either side. Opening and closing animate the card's height, which means the surface has to stay mapped through the collapse — hence `expanded` as the state a bar item toggles and `visible: expanded || cardHeight > 0`. It has to be the card's height and not the animation's `running`: `visible` and `revealed` both re-evaluate off `expanded`, and if `visible` goes first the Behavior has not started yet, so `running` reads false and the surface unmaps for a frame in the middle of the collapse. `cardHeight` is still the full height at that instant and only reaches zero once the card has rolled up, so the ordering cannot bite. Anything that used to dismiss a panel with `root.visible = false` must set `root.expanded = false` instead, or it breaks that binding for good. The same `Behavior` also animates content-driven resizes, so the network panel's swap between its list and its password prompt grows the card rather than jumping it.

  **A `PopupWindow` can never hold keyboard focus.** It has only `grabFocus`, which is the pointer grab; keys go to the *parent* layer surface, which is a different window, and Qt delivers key events only to the focused one. A text field inside a popup therefore shows a caret and then never receives a character, Escape never arrives, and — because sway will not honour the popup's grab either — clicks outside it land in whatever is under the bar instead of dismissing it. Measured with `Window.active`, calibrated against the launcher: an open `ModalOverlay` reads `true`, an open `PopupWindow` reads `false` even with its parent bar surface set to `Exclusive`. This is what the panels were originally built on, and it is why the network password prompt could not be typed into.

  **`WlrLayershell.keyboardFocus` is applied when the layer surface is created and ignored on every later change.** Setting the bar to `Exclusive` only while a popup was open changed nothing (`kb=1`, still `active=false`); the same constant set before startup made the bar active immediately. So a surface that wants the keyboard *some* of the time holds a constant `Exclusive` and toggles `visible` — which destroys and recreates the surface — which is exactly what `ModalOverlay` has always done and why the launcher works.

  Two consequences worth keeping. A `PanelWindow` is **visible by default**, so a dropdown must say `visible: false` or it maps at startup as a full-screen overlay and silently swallows every click meant for the bar. And `ModalOverlay`'s card holds `focus: true` itself, so Escape lands even with no `focusItem`; where there is one, focus moves to that child and Escape still bubbles back up.

  Because the card is now an ordinary layer surface it may **resize freely while open**, which an xdg_popup may not: `PopupWindow` takes its geometry when it maps and never again (`implicitHeight` went 762 → 728 across a bluetooth scan while `height` stayed 762, and `reposition()` does not re-send it). That constraint is gone, so the bluetooth scan list kept out of `BluetoothPanel` for this reason could come back, and the network list's fixed height is now a choice rather than a requirement. Being an overlay, an open panel also covers the bar, so a click anywhere outside the card — including on another bar item — dismisses it rather than reaching what is beneath. `AptUpgrade` is on `BarPopup` too, at `cardWidth: 560`; its package list keeps the 20-row cap the old fixed height enforced, but as `Math.min(contentHeight, maxRows * rowHeight)` on the list itself, so the card grows with the list rather than always standing at full height. Its `Keys.onEscapePressed` had been dead code for as long as it was a `PopupWindow`, and works now.

  Three things about `Quickshell.Services.Pipewire`, each established by spike:

  - **A node's `type` is readable untracked; its `audio` values are not.** An untracked node reports `volume: 0` and `ready: false` but its type flags are already right, so `AudioService`'s three lists filter on `type` (`AudioSink` 17, `AudioSource` 9, `AudioOutStream` 21 — a playback stream is `isSink` *and* `isStream`) and the `PwObjectTracker` then tracks what they select. Filtering on `audio` instead is circular: the tracker would have nothing to track and the lists would stay empty for good.
  - **`nodes.values` is registry order, and it is not stable.** A device that re-registers — an HDMI sink following a monitor — comes back at the end of the list, so the rows reshuffle under the cursor between opening the panel and clicking a row. Both device lists are sorted by label.
  - **Writing `preferredDefaultAudioSink` is the whole of "set the default device"**; it lands in wireplumber's `default.configured.audio.sink`. WirePlumber may then decline it — an HDMI output with nothing plugged in stays refused, and `pactl set-default-sink` on the same node is refused identically — so the tick follows the *effective* default rather than what was clicked, which is the honest reading.

  `windows/Wallpaper.qml` is the desktop background, one layer surface per screen, replacing swaybg. It reproduces swaybg's `center` mode exactly — the image at its native size, centred and clipped, over `Theme.crust` — so `sourceSize` is deliberately left unset: `center` means no scaling, and binding it to the screen would silently start resampling. Two stacked `Image`s crossfade on a theme switch, and **both ends animate**, because the wallpapers are not all the same size (nord's is 1920×1080, the rest 3840×2160) and a smaller incoming image would not cover the one it replaces. The fade starts on any `Image.status` that is not `Loading`, so a theme naming no wallpaper (`Null`) or a missing file (`Error`) still fades the old image out instead of stranding it.

  **The layer is `WlrLayer.Bottom`, not `Background`** — which is where swaybg itself sits. Sway draws same-layer surfaces in creation order and `theme set` re-forks swaybg over IPC, so a `Background` surface ends up *under* a solid-colour swaybg started after the shell, and the wallpaper vanishes until the next restart. Established by spike: with both on `Background`, re-running `swaymsg output '*' bg <colour> solid_color` painted the whole screen that colour; on `Bottom` the image survives, and windows still draw above it. `mask: Region {}` keeps it click-through, as swaybg's empty input region was.

  Wallpapers are PNGs in `wallpapers/`, named by the `wallpaper` key of each theme JSON (carried into `themes.json` for the picker) and resolved against `Paths.wallpapers`. **They carry no background of their own** — it is knocked out to transparency, so `Wallpaper`'s `color: Theme.crust` fills both the letterbox and the area behind the artwork and the two cannot disagree. They used to: every Catppuccin wallpaper was painted against `#1e1e2e`, which is *Mocha's `base`* and not any theme's `crust`, so frappé, macchiato, mocha and latte all drew a visibly different rectangle inside the letterbox. Knocking the background out rather than repainting it to each crust keeps the image independent of the palette, so it stays right if a crust ever changes or a new theme points at an existing image.

  The knock-out has to recover alpha, not just replace a colour: a colour replace leaves every antialiased edge still blended against the old background. Treat each pixel as `a*fg + (1-a)*bg` for the known flat `bg` and take the smallest alpha that keeps `fg` in range — the standard unmatting solution — which recomposites over the original background to within 1/255. Write the result paletted when it fits in 256 colours, which four of the five do: `cat-blue-eye.png` was already a PNG8 and saving it as truecolour RGBA tripled it, while paletted output leaves the five within +7% in total. `themes/unmat-wallpaper <in> <out> <#bg>` does all of it — it lives in `themes/` with the palettes rather than in `.local/bin`, since like the templates it is authoring input and is never symlinked into `$HOME`. Adding a wallpaper means running it once with the image's own flat background colour. The picker previews them, and **the crossfade is suppressed while it does** — `previewing` is `Theme.previewWallpaper !== ""`, and a preview swap is instant. The colours preview instantly and cannot be animated in step, so a fading wallpaper lags the highlighted row — arrowing faster than the fade leaves the previous theme's artwork ghosting under the current one, a step behind the selection. The rule that falls out is that **the crossfade is for changes nobody watched happen** — committing from the picker is instant because you already saw it, and a `theme set` from a terminal fades. Decoding is not the constraint it looks like: a cold 3840×2160 PNG is 13-43ms and a re-visited one costs nothing at all, since a cached image produces no `Image.status` transition. `sway.conf.tmpl` ends at `output * bg $background solid_color`, which overrides the Debian default in `/etc/sway/config.d/40-sway-background.conf` and is what shows during a shell restart.

  `quickshell ipc call` costs ~31ms a call, against sway's default 40ms key repeat, so holding a volume key keeps up without a long-lived socket.

  `services/MprisService.qml` + `modules/bar/Media.qml` + `modules/media/MediaPanel.qml` replace **playerctl** (`config:289-291`, now `quickshell ipc call media playPause|next|previous`). The bar item is the track, in the **centre** section immediately right of the clock, and it must hang off the clock rather than sit in a row with it: its width changes on every song, so a row would walk the clock off centre each time one ended, and the right section — being anchored to the right edge — would shift every icon along it instead. The panel is art, the track, a seek bar, the transport, and — only once there is more than one — the players to choose between.

  Four things about `Quickshell.Services.Mpris`, each established by spike:

  - **`Mpris.players` starts empty and fills in asynchronously**, exactly as `DesktopEntries` and `Networking` do, so every value is a binding and the bar item is what warms the singleton.
  - **A binding over `players.values` re-evaluates only when a player appears or disappears**, never when one of them starts playing or changes track. `MprisService` therefore rebuilds its list by hand from an `Instantiator` whose model is `Mpris.players` — the model, *not* `.values` — so one watcher is created per player and survives every state change. `refresh()` compares before assigning, or a title change would hand every list a fresh array and rebuild its rows.
  - **Most players on the bus are not media.** Chrome keeps a stopped, untitled, uncontrollable instance up whenever it is running, and kdeconnect publishes one per remote app whether or not that app has any; `canControl && (canTogglePlaying || trackTitle !== "")` is what leaves the real ones. `activeName` records the last player known to be playing, on the transition **and** on appearance — a player already playing when it appears emits no `isPlayingChanged`, and without that the first track of a session leaves the fallback picking a kdeconnect mirror.
  - **`position` extrapolates on read**, advancing 1.00s per second between fetches, so the panel's 1s poll is a local read rather than a bus round trip. Writing it seeks.

  `modules/calendar/CalendarPopup.qml` is a `BarPopup` under the clock, a hand-rolled 7×6 grid from `Date` rather than `QtQuick.Controls`. It takes today from the bar's own `SystemClock`, so the highlight moves at midnight with no second timer. The grid is **always six rows**, even for the months that fit in five: one that changed height would move the card's own edges as you page through it. The month name is the way back to today, which is otherwise several presses away once you have paged into next year.

  `services/EmojiService.qml` + `modules/emoji/EmojiPicker.qml` replace **bemoji** (`config:308`, now `quickshell ipc call emoji toggle`); `wtype` stays, because picking still copies and then pastes. The `<glyph> <name>` database bemoji downloaded is **vendored** at `.config/quickshell/emoji.txt`, for the same reason the Phosphor icons are. Frecency is the launcher's shape exactly, in `statePath("emoji.json")`. bemoji is not tracked here — it is a loose script in `~/.local/bin` — so it is left on disk unused, as wofi and zenity were.

  **A clipboard write only takes the Wayland selection when it happens inside an input event handler.** `Quickshell.clipboardText` is writable and the value always reads back, but Qt takes the selection using the seat's last input serial: a write from a timer updates Qt's own copy and nothing else, and `wl-paste` goes on reporting the old contents. Measured four ways — no surface (fails), focused overlay + timer (fails, with `Window.active` reading **true**, so it is not a focus problem), focused overlay + key handler (works), and the same followed by hiding the surface (works, and keeps working). Ownership then lasts as long as the shell *process*, surviving the picker closing indefinitely, which is one fewer forked helper than `wl-copy` needed. So `copy()` and `paste()` both run straight from the row's activation handler. Paste is dispatched through sway rather than run as a `Process`, for the same reason the launcher dispatches `exec`, and carries a 100ms sleep the old binding did not need: the overlay is still unmapping when the handler returns, and the keystroke has to land in the window the picker was covering. Testing a paste against a **terminal** proves nothing — alacritty's paste is Ctrl+Shift+V and Ctrl+V is quoted-insert; use a GUI field.

  `modules/polkit/PolkitDialog.qml` is the session's polkit authentication agent, replacing `polkit-kde-authentication-agent-1`. It is instantiated once in `shell.qml` (not per screen) and draws a modal dialog on an overlay layer surface with exclusive keyboard focus, on whichever output holds the focused sway workspace. Quickshell's `PolkitAgent` registers on startup, so nothing in the sway config launches an agent. Quickshell does not forward PAM's own failure text — it only logs "Unknown line ... from helper" — so a rejected password is reported from `AuthFlow`'s `authenticationFailed` signal instead.

  `lock.qml` is the session lock, and it is deliberately a **second process** with its own unit (`quickshell-lock.service`, started on demand by `.local/bin/lock`, never part of the session target). If the shell held the `WlSessionLock` and crashed, sway would keep the session locked — the protocol's guarantee — and leave a black screen with nothing to type into; isolating it means every bar edit and `systemctl --user restart quickshell` is lock-safe. `services/LockService.qml` owns the `PamContext` (`config: "swaylock"`, which on Debian is `@include common-auth`) and `modules/lock/LockSurface.qml` is the per-screen view, instantiated by `WlSessionLockSurface` for a real lock and by one overlay `PanelWindow` under `QS_LOCK_DEMO` — demo mode is where all layout work happens, since Escape always closes it.

  **`Quickshell.env()` returns `null` for an unset variable, not `""`.** `env("QS_LOCK_DEMO") !== ""` is therefore true when the variable is *unset*, which silently put every real lock into demo mode and drew an escapable overlay instead of locking. It is `!!env(…)` now; anything reading an optional env var wants truthiness, not a comparison against `""`.

  **`WlSessionLock.secure` is the "surfaces are up" signal.** `LockService` writes `$XDG_RUNTIME_DIR/quickshell-lock.stamp` on it and `lock` polls for that before returning, so `before-sleep` cannot suspend over a half-mapped surface; `lock` removes the stamp *before* starting the unit, which is what makes waiting for it meaningful. If nothing maps within 2s it falls back to `swaylock -f`, which is why swaylock and `swaylock.conf.tmpl` stay installed. **sway accepts a replacement lock client for an abandoned lock** — `SIGKILL` while locked leaves the session locked, and a fresh client maps and re-confirms `secure` — so `Restart=on-failure` is real crash recovery, and from a VT `systemctl --user start quickshell-lock.service` is the way back to a prompt. The unit sets `StartLimitIntervalSec=0` deliberately: a unit that gives up restarting leaves a locked session nobody can type into.

  `services/IdleService.qml` owns idle policy, which used to be swayidle's `timeout` — dim at 240s (`modules/idle/IdleDim.qml`, click-through so the input that dismisses it still reaches the window underneath), lock at 300s. swayidle survives only as a policy-free adapter for logind's Lock/Unlock/PrepareForSleep signals, which Quickshell 0.3.0 cannot hear itself. **Screen-off is a paint, never a modeset** — `IdleDim`, plus `LockService.blanked` blacking the lock surface after 60s — because `output power off` is lockup trigger #2.

  `IdleMonitor.respectInhibitors` **does** honour other clients' Wayland idle inhibitors (sway enforces it compositor-side), but only when the inhibitor is attached to a visible *view*: one on a layer surface is ignored, so quickshell's own surfaces cannot inhibit idle. It does not see *logind* inhibitors, which is what `.local/bin/noidle` and `InsomniaService`'s third mode create — and neither did swayidle, measured, so those have never prevented the screen locking and only their `sleep` half ever did anything. Now that idle policy shares a process with Insomnia, `IdleService` reads `InsomniaService.mode.inhibitIdle` directly and disarms both monitors. Cross-service references need no import: same directory, same synthesized `qs.services` module.

  Testing a real lock without risking the desktop means a **nested sway** (`sway -c <minimal>` as a window in the session). One trap: the nested compositor's IPC socket is usually found by mtime, and when that sway exits the lookup falls through to the **real** session's socket — so the next `swaymsg exec` locks the desktop you were protecting. Bind the socket once and assert the nested compositor is still alive before each call.
- **Session services** (`.config/systemd/user/`): the shell runs under systemd, not as a sway `exec`. The sway config starts `sway-session.target`, which `BindsTo` + `PropagatesStopTo` `graphical-session.target` and so pulls in `quickshell.service` (`Restart=always`, `StartLimitBurst=5`) and `sway-outputs.service` plus the machine-local `poweralertd` and `wayland-pipewire-idle-inhibit` units already sitting in `graphical-session.target.wants/`. This keeps `swaymsg reload` and every theme switch out of the shell's lifecycle, and out of the DRM modeset path described in `.claude/sway-lockup-investigation.md`.

  The user manager never sources `~/.profile`, so the XDG base directories and `~/.local/bin` are declared in `.config/environment.d/10-xdg.conf` — without them `theme` and the `sway-*` scripts are unreachable from any user unit. `environment.d` rather than `Environment=` lines because it covers every unit at once, expands `${HOME}`/`${PATH}`, and applies on a plain `daemon-reload`. Files there merge by filename across all `environment.d` directories, so nix's unprefixed `nix-daemon.conf` sorts after `10-xdg.conf` and re-prepends its own paths. `quickshell.service` keeps only `QT_QPA_PLATFORM=wayland` and `QT_QPA_PLATFORMTHEME=kde`, which are about how the shell renders and used to be inherited from the `sway-run` launcher uwsm replaced.

  `wayland-pipewire-idle-inhibit.service` is tracked here too. Any unit added to this target needs `PartOf=graphical-session.target`, not just `WantedBy=` in `[Install]` — `WantedBy` starts it with the session but never stops it, and a `Restart=always` unit then spins against a dead compositor for the whole logout window.

  The sway side is one quoted `exec` that chains the environment import into the target start: `/etc/sway/config.d/50-systemd-user.conf` imports `SWAYSOCK` in a *separate* `exec`, and sway launches execs asynchronously, so the target can otherwise start before the socket is in the manager's environment. The quotes are load-bearing — unquoted, sway parses `&&` (or a `;`) as the start of a second command and logs `Unknown/invalid command`.

  `PropagatesStopTo` is load-bearing and easy to lose: `BindsTo=B` only stops A when B stops, never the reverse, so without it `systemctl --user stop sway-session.target` leaves `graphical-session.target` and every service under it running, and the teardown silently does nothing.

  `quickshell-lock.service` is tracked here too but has **no `[Install]` section**: it is started on demand by `lock`, never pulled in by the target. It is `PartOf=graphical-session.target` so it still dies with the session.

  `install` ends with `systemctl --user daemon-reload` and `systemctl --user enable quickshell.service`, guarded on `-d /run/systemd/system` so macOS skips it; symlinking a unit is not enough, `WantedBy=` only applies once enabled. Editing an existing unit still needs a `daemon-reload`.
- **Autostart** (`.config/autostart/`): apps are started by **XDG autostart**, not by a sway `exec` block. uwsm runs it through `wayland-session-xdg-autostart@sway.desktop.target`, and the `sway-run` launcher it replaced never did — so on the first uwsm login a pile of entries under `/etc/xdg/autostart` and `~/.config/autostart` fired for the very first time, several of them into things the bar had already replaced. That is the trap to remember here: **an autostart entry that has "always been fine" may simply never have run.**

  Anything the compositor does not itself need goes here rather than in `sway/config`, so systemd owns the lifecycle — a unit, its own log, a cgroup, and teardown with `graphical-session.target` instead of an orphaned child of the compositor. `sway/config` keeps only what is genuinely sway's: `sway-laptop-lid`, the swayidle adapter, and the one quoted `exec` that starts `sway-session.target`.

  Three mechanisms, in order of preference. A **system entry that already exists** needs nothing — `nm-applet` is started by `/etc/xdg/autostart/nm-applet.desktop` (whose `NotShowIn=KDE;GNOME;` does not exclude `sway:wlroots`), so its sway `exec` line was pure duplication. A **new tracked entry** in `.config/autostart/` covers what ships none: `kdeconnect-indicator.desktop` (there is a system entry for the kdeconnect *daemon*, but not for the indicator) and `calibre.desktop`. And a **`Hidden=true` shadow** suppresses a system entry — a user file of the same name overrides it, `Hidden=true` means "treat as deleted", and the generator then writes no unit at all (confirmed: it reports `not-found`). `blueman.desktop` is the one such shadow, and the reason it is a shadow rather than an `apt remove` is that blueman-applet is the BlueZ pairing agent Quickshell does not provide.

  Two things measured rather than assumed. **A duplicate start is silent, not an error**: while both paths were live, `app-1password@autostart.service` ran, found sway's instance, logged `1Password is already running, closing`, and exited `Result=success` — 517ms of CPU and an 88MB peak with nothing to show for it, and a unit sitting `inactive` that looks like it never ran. And **ordering does not matter for tray apps**, unlike `poweralertd`: an SNI item owns its own bus name and the watcher picks it up whenever it appears, so an applet starting before quickshell is fine.

  `poweralertd.service.d/wait-for-notifications.conf` is the counter-example, and the one unit here that *does* need ordering. poweralertd sends a notification the instant it starts and exits 1 if the call fails, so under uwsm it and quickshell race off `graphical-session.target` — measured at one login: poweralertd started at `22:13:09.009`, failed three times in 0.67s, and hit the stock 5-in-10s `StartLimitBurst` at `22:13:09.676`, while quickshell only started at `22:13:11.182`. The fix is an **`ExecStartPre` that blocks on the bus name** — `gdbus wait --session --timeout 30 org.freedesktop.Notifications` — because the name being claimed is the only thing that is true at the right moment. It returns in 7ms when the name is already owned, so it is free in the normal case, and exits non-zero after the timeout so a quickshell that never appears fails the unit once instead of leaving it spinning. gdbus is `libglib2.0-bin`, which `install` already pulls in for `theme`.

  Two other routes were tried first, and both are worth knowing because both look right. **`After=quickshell.service` deadlocks**: poweralertd carries `Requires=graphical-session.target` and quickshell is ordered `After=` that same target, so the edge closes a cycle; systemd breaks a cycle by deleting a job, and it picked poweralertd's own `start`. The unit then never ran, never failed, and never appeared in `--state=failed` — strictly worse than the race, since the boot looks clean and the battery alerts are simply gone. **A retry budget alone does not work at any size**: `RestartSec` is *not honoured while the session is coming up*, where systemd logs `Scheduled restart job immediately on client request` and restarts with no delay, so 20 attempts burned in 0.35s against a quickshell that started 0.9s later. That one is invisible from a hand-started unit, where `RestartSec` applies normally and the same config passes a manual test — which is exactly how it shipped. Verify a startup race across a real reboot, not by starting the unit by hand.

  `~/.config/autostart/1password.desktop` is deliberately **not** tracked: 1Password writes it itself and it is 0600. The `polkit-kde-authentication-agent-1.desktop` symlink there is inert — it carries `OnlyShowIn=KDE;` against uwsm's `XDG_CURRENT_DESKTOP=sway:wlroots`, so no unit is generated and nothing contends with Quickshell's own polkit agent. Worth knowing, because a second agent would be hard to diagnose.

- **Sway**: starts under **uwsm** as a systemd user unit — `wayland-wm@sway.desktop.service`, `ExecStart=/usr/bin/uwsm aux exec -- %I`, where the instance is the Desktop Entry ID (`sway.desktop`) and not the bare binary. Nothing in this repo launches the compositor: the greeter runs `uwsm start -- sway.desktop` (see Login), and from a VT `uwsm start default` does the same by hand, resolving through `~/.config/uwsm/default-id`. Both machines are on this path.

  It replaced a hand-written `/usr/local/bin/sway-run` launcher, which exported the Wayland variables itself, sourced a `.config/sway/profile` that no longer exists, and ran sway **without** `exec` so it could `systemctl --user stop sway-session.target` on the way out. Nothing references either any more. The trap while the two paths coexisted is worth keeping in mind when reading older notes: `sway/profile` was sourced by `sway-run` and by nothing else, so `QT_QPA_PLATFORMTHEME=kde` living in it was simply absent from the whole uwsm session, which is what left Dolphin unthemed.

  Under uwsm the session environment comes from `.config/uwsm/env` (tracked), which uwsm sources from `/usr/libexec/uwsm/prepare-env.sh` on the way up — a plain `. "$file"` behind an `-f`/`-r` test, so the symlink `install` leaves is sourced normally. It also reads a per-compositor `env-<desktop>` beside it and an `env.d/` directory, neither of which is used.

  **`~/.profile` does reach the uwsm session, and that is not obvious.** `prepare-env.sh` sources `/etc/profile` and `~/.profile` itself, then uwsm diffs the environment and pushes the result into the systemd user manager with `SetEnvironment` — so profile-only variables (`MBOX`, `NVM_DIR`, `DOCKER_CONFIG`, `EDITOR`, …) land in sway, in everything sway `exec`s, **and** in every user unit, quickshell included. That is strictly more than `sway-run` gave, where the user manager saw none of it — which is the whole reason `10-xdg.conf` exists. Do not read `environment.d`'s comment as meaning the graphical session lacks the profile; it means the *manager* does not source it, and under uwsm something else does.

  It is conditional, but **not on there being a login shell** — an earlier version of this note said it was, and that was wrong. `__LOAD_PROFILE__` comes from `have_env_login`, which is simply whether `uwsm start` itself ran and left a non-empty environment behind: `save_env("env_login")` dumps `os.environ` just before uwsm replaces itself with the signal handler, and `prepare-env` reads it back (`/usr/share/uwsm/modules/uwsm/main.py`, around lines 2652 and 4836). So a greeter that execs `uwsm start` directly still loads the profile, which is what makes the gtkgreet flow below safe; what *would* lose it is starting the compositor unit without going through `uwsm start` at all. Confirm from the journal rather than assuming — the preloader prints `Loading shell profile.` when it did, under the `uwsm_env-preloader` identifier.

  So `environment.d` is the floor, not the main path: it carries the XDG base directories the units would lose if the greeter ever started the compositor without going through `uwsm start`, plus session-wide non-shell settings like `QT_QPA_PLATFORMTHEME` that are not Wayland setup and so do not belong in `uwsm/env`. Everything else — tool configuration, `PATH`, editors — stays in `~/.profile` and already arrives; duplicating it into `environment.d` only creates two places to drift. Genuinely Wayland-session setup goes in `.config/uwsm/env`.

  One measurement to save repeating: a directory missing from the session's `PATH` is usually not a bug in any of this. `~/.profile` guards each entry with `[ -d ]` and runs once at login, so a toolchain installed mid-session is absent until the next one — `~/.local/share/cargo/bin`, created two hours after login, read exactly like a broken export and was not.

  uwsm sets `XDG_SESSION_TYPE`, `XDG_SESSION_DESKTOP`, `XDG_CURRENT_DESKTOP` (as `sway:wlroots`, not bare `sway`) and the XDG base directories itself, so `.config/uwsm/env` carries only what it does not: `MOZ_ENABLE_WAYLAND`, `QT_QPA_PLATFORM`, `SDL_VIDEODRIVER`, `_JAVA_AWT_WM_NONREPARENTING` and the cursor theme. Two variables `sway-run` exports are deliberately **not** carried over. `ELECTRON_OZONE_PLATFORM_HINT=auto` is unnecessary — measured, every Electron and Chromium app in the session (Chrome, Claude, Slack, Spotify) is already a native Wayland client without it, Claude with no flags at all. `ADW_DISABLE_PORTAL=1` is actively wrong here: it stops libadwaita reading the portal, and the portal's `org.freedesktop.appearance` is exactly how `theme`'s dark/light switch reaches GTK4 and Electron apps (see Themes).

  uwsm also owns the teardown that `sway-run`'s missing `exec` was for — `wayland-wm@sway.desktop.service` propagates its stop to `graphical-session.target` — so the compositor cannot outlive the session either way.

- **Login** (`system/greetd/`, `system/install-greetd`): login goes through **greetd** on VT7, which runs a bare sway hosting **gtkgreet**; picking a session there starts `uwsm start -- sway.desktop`, which is byte-for-byte what `uwsm start default` resolved to when it was typed by hand (`~/.config/uwsm/default-id` holds `sway.desktop`). Both machines are on it, and neither autologins — the laptop's greetd used to carry an `[initial_session]` running `sway-run`, and dropping it is what put the two on the same config.

  `system/` is the third repo root outside the four paths `install` mirrors, after `themes/` and `claude/`, and for a harder reason than either: these files are root-owned and live in `/etc`, so they are **copied, not linked** — `sudo ./system/install-greetd` after any edit, or the change does nothing. That script is also where the non-file steps live (the `_greetd` group hedge, `sway --validate` on the greeter config, `systemctl enable greetd`), so it is the whole procedure rather than a `cp` wrapper.

  **`sway --validate` brings the backend up before it parses the config**, which makes it near-useless where you most want it — under `sudo`, from a text console. It aborts outright on the unset `XDG_RUNTIME_DIR` that sudo does not pass through, and faking that one is worse than useless: it then spends ten seconds failing to open a DRM session and exits 1 for a good config and a bad one alike, a check that can never pass and that reads as "my config is broken". `WLR_BACKENDS=headless` plus a throwaway `XDG_RUNTIME_DIR` skips DRM and seat management entirely and leaves just the parse — measured at exit 0 on a good config and 1 with a real error message on a bad one, in 0.07s, with no display and no session. Note also that a typo'd *identifier* is not a parse error: `input typ:keyboard { … }` validates clean, because sway reads it as a device identifier that happens to match nothing.

  **gtkgreet does not read `wayland-sessions` desktop entries** — it reads `/etc/greetd/environments`, a newline-separated list of raw command lines. That is a simplification worth knowing, because the obvious design (a `/usr/local/share/wayland-sessions/sway-uwsm.desktop` wrapper, per uwsm's own README) buys nothing here and would leave the packaged `sway.desktop` sitting next to it in every picker as a session that silently skips uwsm. The second line in `environments` is `zsh -lc sway`, a deliberate rescue: a login shell so `~/.profile` still runs, since with uwsm out of the picture nothing else would source it.

  `source_profile = false` in `config.toml` is deliberate and is the one setting to not "fix". greetd's default is `true`, and uwsm sources `/etc/profile` and `~/.profile` itself — but `~/.profile` *prepends* to `PATH` with no re-entry guard, so letting both do it duplicates every entry. Turning it off is safe only because the session still inherits systemd's default `PATH` through greetd: `/etc/environment` is empty on this machine and `common-session` carries no `pam_env`, so nothing else would supply one and an empty `PATH` was the failure mode to rule out.

  The greeter's sway config **must not** `include /etc/sway/config.d/*` the way the packaged `/etc/greetd/sway-config` did. The only drop-in there is `50-systemd-user.conf`, which imports the environment into the systemd *user* manager — as `_greetd` that starts a user manager for the greeter account with nothing to manage. It carries an `output` line keyed by sway **identifier** (not connector — see the output section) matching the mode `sway-outputs` will pick, so login → session is not a second modeset; on any other machine the identifier matches nothing and the line is inert.

  Two things about `_greetd` that look like they should break and do not. It reaches the GPU by **logind ACL**, not group membership: `getfacl /dev/dri/card0` shows `user:<active user>:rw-` granted to whoever holds the active seat0 session, and greetd's greeter is one. `install-greetd` adds `_greetd` to `video` and `render` anyway as a hedge for the window before the session goes active. And it cannot read *anything* under `~` — `$HOME` is 0700 — which is why the wallpaper is copied to `/etc/greetd/wallpaper.png` and why `sway-config` sets `GTK_THEME=Adwaita:dark` rather than relying on the generated dotfiles GTK theme under `~/.local/share/themes`.

  `gtkgreet.css` is **hand-written and static** — it is not in `theme`'s `TARGETS` and `theme set` does not touch it. That is a choice, not an oversight: the generated files all land under `~/.config`, and reaching `/etc` would mean `theme` needing root, which it has never needed. The palette in it is Catppuccin Mocha, and it tracks nothing — the install-time default is macchiato, and changing themes leaves the login screen where it is. gtkgreet's own widget ids are `#body`, `#clock`, `#input-field` and `#command-selector` (read off the binary, they are not documented); everything else in the file is plain GTK3, and a stylesheet passed with `--style` layers *over* the GTK theme rather than replacing it.

  The way back in if the greeter ever fails is `Ctrl+Alt+F2`: `greetd.service` takes VT7 alone (`Conflicts=getty@tty7.service`) and tty1–tty6 keep their gettys. greetd gives up after 5 restarts in 30s, so a broken greeter leaves VT7 blank rather than looping forever. Test a change by switching to a getty **first** and restarting greetd from there — restarting it kills the graphical session either way, and from a getty you are already somewhere useful when it does not come back.
