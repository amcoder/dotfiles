# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Personal dotfiles for a Linux (Debian, Sway/Wayland) and macOS environment. The repo mirrors `$HOME`: `.config/`, `.local/bin/`, `.profile`, and `.zshenv` are symlinked into the home directory, so edits to files here take effect immediately in the live environment — no build or deploy step. `claude/` is linked in too, to a destination that is not its own path (see Claude Code).

## Commands

- `./install` — symlink all tracked files into `$HOME` (backs up any existing non-symlink files). Must be re-run after adding a **new** file to the repo so its symlink gets created; editing existing files needs nothing. A second loop links `claude/<path>` to `~/.claude/<path>`, which the mirroring loop cannot do.
- `./install --deps` — also install dependencies, **before** the symlink pass rather than after it: a Homebrew bundle from `Brewfile` on macOS, `apt` on Debian/Ubuntu, plus nvm and rustup on both. The ordering is load-bearing — everything after the symlink loop (enabling the quickshell units, `theme apply`) needs those binaries to already exist, so on a fresh machine a `--deps` run that installed last would enable a unit whose binary was still missing. Node and Rust come from nvm and rustup rather than apt because each owns its own toolchain and `.config/zsh/nvm.zsh` switches node per `.nvmrc`; an apt copy would sit in front of whatever those selected. Both installers append PATH lines to a shell profile by default, which here means editing `~/.profile` — **a symlink into this repo** — so both are given their own opt-out (`PROFILE=/dev/null` for nvm, `--no-modify-path` for rustup). nvm additionally refuses to create `$NVM_DIR` anywhere but its own default `~/.nvm`, and this repo puts it under `XDG_DATA_HOME`, so the directory has to exist first.
- `dot-add <file>` — zsh function (defined in `.config/zsh/dot.zsh`) that moves an existing file from `$HOME` into the repo, symlinks it back, and commits it. Prefer this when bringing a new config file under management.
- `dot-prune` — deletes symlinks under the five managed roots (the four mirrored paths plus `~/.claude`) that point into the repo but no longer resolve. `install` runs it after linking, because `ln` never removes anything: renaming a tracked file leaves a dangling link in `$HOME`, and quickshell dies loading one. It only touches links whose target is inside `$DOTFILES_DIR`, so unrelated broken links elsewhere in `~/.config` are left alone.

There are no tests or linters for the repo as a whole. Neovim Lua is formatted with stylua per `.config/nvim/.stylua.toml` (2-space indent, prefer single quotes).

## Structure

- **zsh** (`.config/zsh/`): the root `.zshenv` only sets `ZDOTDIR` to `.config/zsh`; all real config lives there. Plugins are managed by zinit (auto-cloned on first shell start). Load order is documented at the top of `.zshrc`. `install` writes a generated `dotfiles-dir.zsh` (untracked) into `ZDOTDIR` exporting `DOTFILES_DIR`.
- **Neovim** (`.config/nvim/`): kickstart.nvim-style single `init.lua` for options/keymaps, with lazy.nvim loading one plugin spec file per concern from `lua/plugins/`. Add new plugins as a new file in that directory. `lazy-lock.json` pins plugin versions. `init.lua` also holds the theme watcher that follows `theme set` live (see Themes).
- **Claude Code** (`claude/`, repo root — linked into `~/.claude`, not mirrored): Claude Code keeps its config directory at `~/.claude`, which cannot be one of the four mirrored roots, because the repo's own `.claude/` is *this project's* instructions — mirroring it into `$HOME` would lay this file over the user-level `CLAUDE.md`. So the home-level config lives in `claude/` and `install` links it file by file with a second loop mapping `claude/<path>` to `~/.claude/<path>`; `dot-prune` gained `~/.claude` as a fifth root. Only the four things that are configuration are tracked — `settings.json`, `keybindings.json`, `statusline-command.sh` and `rules/`. Everything else in that directory is state (`.credentials.json`, `.claude.json`, `history.jsonl`, `sessions/`, `projects/`, the plugin marketplace clones) and is simply not in the repo, which needs no `.gitignore` support because the repo only ever contains what was put in it.

  The global instructions are **split in two halves**. `~/.claude/CLAUDE.md` is untracked, machine-specific, and currently an empty file: the loader drops any entry whose trimmed content is empty, so an empty file costs no context while keeping the machine-local destination obvious. The shared half is `claude/rules/*.md`, linked into `~/.claude/rules/`. That directory is a first-class Claude Code feature rather than a trick — it is walked recursively, every `.md` under it loads, and the renderer labels an entry by its *type* and not its filename, so a file in `~/.claude/rules/` reaches the context under exactly the same header as `CLAUDE.md` itself ("user's private global instructions for all projects"). Load order is managed → user `CLAUDE.md` → user rules → the project chain. One file per concern is the point: `comments.md`, `debugging.md`, `memory.md` and `instruction-scope.md` can each be edited, moved or made conditional without touching the others.

  A rules file may carry `paths:` frontmatter, which stops it being always-on and injects it only when a file matching those globs comes into play. **At user scope those globs match the touched path made relative to the cwd**, gitignore-style, and the matcher bails the moment that relative path escapes the cwd (`..`) or stays absolute. So a conditional rule keyed on anything under `$HOME` — `~/.claude/CLAUDE.md`, say — can essentially never fire, because no working session has that inside its cwd. `instruction-scope.md` is unconditional for that reason and for a second one: it has to be read *before* an instruction is written, while a conditional rule fires on file access, which is already too late. `paths:` is for per-language rules inside a project (`**/*.rs`), not for anything about the config directory itself.

  A **new** rules file needs `./install` before it loads, which is easy to miss here because editing an existing one needs nothing. The paths that appear in the loaded context are the **repo** paths (`~/.dotfiles/claude/rules/comments.md`) rather than the `~/.claude/rules/` links, because the loader canonicalises symlinks.

  Two things about `settings.json`, both measured rather than assumed. Claude Code rewrites it whenever a setting changes mid-session — theme, model, voice, plugin enablement — and it does so atomically **and** symlink-safely: it resolves the link first, creates `settings.json.tmp.<pid>.<hex>` in the *resolved* directory, and renames that onto the target. Established by strace of a real write, and by four user-scope mutations against a scratch `CLAUDE_CONFIG_DIR` whose `settings.json` was a symlink — the link survived every one, and a 0600 target stayed 0600. Two consequences: the temp file lands in this repo, hence the `.gitignore` line, and the tracked file changes inode on every write, so anything holding it open keeps reading the old copy. The second thing is that the whole JSON object is rewritten with **no key-order guarantee**, so expect a reordering diff on the first write and ongoing churn from per-session toggles (`model`, `theme`, `voice`) — which are now shared across machines whether that was intended or not. Git records only the exec bit, so the file's 0600 here lands as 0644 on a fresh clone; it holds no secrets, the credentials being in the untracked `.credentials.json`.

  `CLAUDE_CONFIG_DIR` relocates the whole directory, and was considered for moving it under `.config` where the ordinary mirroring loop would cover it with no new machinery. Rejected: it moves the state and the credentials along with the config rather than separating them, and it has to be set in *every* context that starts Claude Code — the terminal CLI, the desktop app (which runs its own bundled build), any user unit — falling back silently to a fresh, logged-out `~/.claude` wherever it is missing.
- **Themes** (`themes/`, repo root — deliberately outside the four paths `install` mirrors): one palette per theme (`catppuccin-macchiato.json`, `nord.json`) plus `templates/`, from which `.local/bin/theme` renders every app-specific config. The selection lives in `$XDG_STATE_HOME/theme/current` and the rendered files land in `~/.config`, so switching themes never dirties the repo; `install` ends by running `theme apply`, defaulting to catppuccin-macchiato. Use `theme list`, `theme current`, `theme set <name>`, `theme apply`.

  Templates are written against a role vocabulary that reuses Catppuccin's 26 colour names as generic roles (`crust`/`mantle`/`base`, `surface0-2`, `overlay0-2`, `subtext0-1`, `text`, and 14 accent names) because it is the superset; themes with fewer colours map several roles to one hex. Placeholders are `{{role}}` (`#rrggbb`), `{{role_raw}}` (bare hex, for swaylock and Qt ARGB) and `{{role_rgb}}` (`r,g,b`, for kdeglobals) — `{{ }}` rather than `$` so sway's own `$var` syntax survives. Adding a theme means one JSON file; adding an app means a template plus an entry in `TARGETS`.

  Generated files go where each app already looks, never to a central directory, so nothing has to resolve a `~` or an absolute path — GTK's `@import` takes a URL with no `~`, and sway resolves a relative `include` against the config's own directory. Each theme also declares `"appearance": "dark" | "light"`, which `theme` applies as real desktop state, not just colours: `gsettings org.gnome.desktop.interface color-scheme` (which xdg-desktop-portal exposes as `org.freedesktop.appearance`, and which is what Electron apps such as Claude desktop follow), plus `gtk-application-prefer-dark-theme` in the generated `gtk-{3,4}.0/settings.ini`. Because it is state rather than a reload, `apply_appearance` runs even under `--no-reload`, so `install` leaves a fresh machine in the right mode. The `gtk-theme` bounce that forces GTK to re-read the palette must pass through a theme of the *same* appearance (`Adwaita-dark` for dark) — bouncing via light `Adwaita` leaves the whole desktop light if the run is interrupted between the two `gsettings` calls.

  The GTK3 palette is not written to `~/.config/gtk-3.0/gtk.css`: GTK3 loads that file exactly once, when the app starts, and re-reads it neither on a file change nor on a theme change, so every running GTK3 app — Chrome above all — kept the palette it launched with until it was restarted. Instead `theme` generates a whole GTK theme at `$XDG_DATA_HOME/themes/dotfiles`, whose `gtk-3.0/gtk{,-dark}.css` is an `@import` of `gtkTheme`'s stylesheet followed by our `@define-color` lines (a later definition wins), and points `gtk-theme` at it. That one GTK re-reads from disk on every `gtk-theme` set, which is what the bounce in `apply_appearance` is for — the generated theme's name never changes, so without the detour through `Adwaita-dark` gsettings emits no change at all. Verified end to end: a running Chrome with the GTK theme selected repaints across macchiato → latte → nord with no restart.

  The theme provider sits *below* `~/.config/gtk-3.0/gtk.css` in GTK's cascade, so that file must not also carry the palette — a stale in-memory copy would mask the generated theme in every app started before the switch. `prune` deletes it from the manifest of an older `theme` run, but a process already holding it needs one restart. GTK4 is unaffected by all this and keeps its palette in `~/.config/gtk-4.0/gtk.css`, because libadwaita ignores GTK themes entirely and reads only that file — GTK4 apps still need a restart.

  `gtkTheme` names the base theme the generated one imports, and must be an existing directory under `~/.themes`, `$XDG_DATA_HOME/themes` or `/usr/share/themes`, exactly — the names are case-sensitive and the installed adw-gtk3 build is lowercase `adw-gtk3-dark`, not `Adw-gtk3-dark`. A name that does not resolve loses the **palette**, not the widget rules — the opposite of what it looks like. The generated theme is then our `@define-color` lines over GTK's built-in Adwaita, and the two vocabularies do not overlap at all: ours is libadwaita's (`window_bg_color`, `accent_bg_color`, `view_bg_color`), Adwaita's is GTK3's own (`theme_bg_color`, `theme_base_color`, `theme_selected_bg_color`). adw-gtk3 is the translation between them, so without it every colour we define is referenced by nothing and apps keep Adwaita's rules *and* Adwaita's grey. Measured on a fresh machine with adw-gtk3 missing: `window_bg_color` read `#1e1e2e` (our base, loaded fine) while `theme_bg_color` — what widgets, and Chrome, actually paint with — read `#353535`. `theme` warns on stderr rather than trusting the string, but that warning is the only symptom and it scrolls past during `install`.

  Debian does not package adw-gtk3, so it is **vendored** at `.local/share/themes/adw-gtk3{,-dark}` (upstream v6.5), the same call as the Phosphor icons and `emoji.txt`. That path needs no `install` support at all: `$XDG_DATA_HOME/themes` is `~/.local/share/themes`, already inside `.local`, so the ordinary symlink loop links it into place before `theme apply` runs on the same pass — which is what makes a fresh machine come up themed in one `./install`, with no `--deps` and no network. Only `index.theme` and `gtk-3.0/` are vendored; upstream's `gtk-4.0/` (864KB, mostly `libadwaita.css`) and the thumbnails are dropped, because nothing ever resolves adw-gtk3 *by name* — the generated theme `@import`s its GTK3 stylesheet by absolute path, and GTK4 reads `~/.config/gtk-4.0/gtk.css` instead. The stylesheets reference their assets relatively (`url("assets/…")`), so `assets/` has to sit beside each `gtk.css`; the two variants' asset sets are byte-identical, as are three of the four stylesheets, so git stores one blob of each. Updating means re-extracting those two parts of the release tarball over these directories and re-running `./install` for any file that is new.

  Where an app has no include mechanism (`kdeglobals`, `gtk-4.0/gtk.css`, `gtk-{3,4}.0/settings.ini`, `swaylock/config`) the whole file is generated and is no longer tracked; the generator unlinks a leftover repo symlink before writing, since `install` never removes stale links. bat reads `BAT_THEME` from the generated `zsh/theme.zsh`, and nvim reads `lua/theme.lua`.

  nvim picks up a switch without restarting, the same way zsh and quickshell do: `init.lua` starts a `vim.uv` fs_event on `~/.config/nvim/lua` and, when `theme.lua` changes, switches to the colorscheme it names. Both colorscheme plugins are start plugins whose `config` runs regardless of which theme is selected (only the `vim.cmd.colorscheme` call is gated), so every colorscheme is already loaded in every instance and the switch needs no plugin load. lualine follows on its own — it registers a `ColorScheme` autocmd that re-runs its own `setup()`, and its `theme` is left at `auto`.

  Four things about that watcher. It watches the **directory**, not the file: `write()` truncates in place most of the time, but it unlinks and recreates when a repo symlink is in the way, and a file watcher dies on that. The callback must `vim.schedule()` — a libuv callback is not a safe place to touch the vim API. It uses `dofile` rather than `require`, so there is no `package.loaded` entry to invalidate. And it compares against `vim.g.colors_name`, so a re-`apply` of the same theme does not redraw — which also means a hand-set `:colorscheme` is overridden by the next `theme apply`. The `fs_event` handle is a file-scope local in a chunk that has finished running, and survives anyway because luv refs an active handle; verified by forcing a full GC over RPC and then switching themes.

  zsh picks up a switch without restarting: `.zshrc` defines `theme-reload`, a precmd hook that watches `theme.zsh`'s mtime (via `zstat`, not a forked `stat`) and, when it changes, re-sources it along with everything derived from it — `FZF_DEFAULT_OPTS` and `$P10K_CONFIG`. Re-sourcing the p10k config is what applies the change, since powerlevel10k runs with `POWERLEVEL9K_DISABLE_HOT_RELOAD=true` and the config file ends by calling `p10k reload` itself. The p10k prompt's rounded caps are drawn in reverse video, so the colour *behind* them cannot be "the default background" — it has to be named, which is what `THEME_P10K_EDGE` (the theme's `base`) is for; it must equal the terminal background or every segment sits in a visible box of the wrong colour. `theme apply` also deletes `$XDG_CACHE_HOME/p10k-instant-prompt-*.zsh`, which bakes the old palette into a prompt snapshot that outlives the theme switch.

  tmux is split so the template carries no layout: `templates/tmux.tmpl` generates `tmux/theme.tmux` as nothing but `set -g @thm_<role>` lines, and the tracked `.config/tmux/statusline.conf` holds the whole status line, referencing only `@thm_*`. `tmux.conf` sources the colours first, then the layout. Follow that split when theming another app — a template should be the palette, not the design.

  `statusline.conf` reproduces what the `catppuccin/tmux` tpm plugin used to render (rounded window style, window number on the right, icon flags, and the application + session status modules), with the plugin's option indirection flattened out. It sets options with `-gF`, so `#{@thm_*}` resolves when the file is sourced while a doubled `##{...}` survives to render time — which is why a theme switch has to re-source `tmux.conf`, not just rewrite `theme.tmux`. The session module's prefix-sensitive colour must stay a render-time `#{E:@thm_red}` reference: tmux cannot parse a raw `#rrggbb` inside a `#{?...}` conditional. `message-style` uses `bg=default` rather than overlay0 because that is what the plugin actually drew — its `%hidden CTP_MESSAGE_BACKGROUND` resolves empty on tmux 3.7 — and `status-{left,right}-length` are left at tmux's defaults for the same fidelity reason, so a long session name can still truncate at 40 columns.

  Equivalence with the plugin was checked by standing up two `tmux -L` servers — one running the real plugin with the old settings, one sourcing `theme.tmux` + `statusline.conf` — and diffing all 19 status/window/pane options. The comparison has to resolve `#{@thm_*}` on both sides first: the plugin defers those references while this layout bakes them at source time, and it keeps its status modules in `@catppuccin_status_{application,session}` rather than in `status-right`. Assert the comparison actually ran (non-empty values, expected option count) — a version that silently compared two empty files reported a false pass.

  btop is the tmux split again, with the palette on the other side of the line: `templates/btop.tmpl` generates `btop/themes/dotfiles.theme` and the tracked `.config/btop/btop.conf` holds every setting, naming only `color_theme = "dotfiles"`. That bare name is what makes the config portable — btop resolves it against `$XDG_CONFIG_HOME/btop/themes` and, measured, writes it back **verbatim** rather than expanding it to the absolute path the theme menu would store, which is what the untracked config used to carry.

  Three more things about btop, each established by spike against a scratch `XDG_CONFIG_HOME` driven through a sized pty (it exits with "Failed to get size of terminal!" under a pipe, and `script` alone does not size the pty). It writes `btop.conf` **through a symlink in place** — same inode across a settings change, so tracking the file is safe. It writes **only when something changed**, so an ordinary run-and-quit leaves it alone and there is less churn than `save_config_on_exit = true` suggests. And it does **not** re-read the theme file while running, so a `theme set` leaves an open btop on its old palette until it is restarted — GTK4's position, not zsh's or nvim's. Verification is by rendering rather than by reading the config back: run btop under a pty and grep the output for the palette's background as an SGR triplet (mocha's `#1e1e2e` is `48;2;30;30;46`), which is the only signal that separates "theme loaded" from "silently fell back to Default".
- **Qt/KDE theming** (`.config/kdeglobals`): `.config/environment.d/20-qt.conf` sets `QT_QPA_PLATFORMTHEME=kde`, so Qt apps load plasma-integration's platform theme, which takes its palette, widget style, icon theme and fonts from the `[Colors:*]`, `[KDE]`, `[Icons]` and `[General]` groups of `kdeglobals`. Both toolkits use Cantarell 11 for UI text and DejaVu Sans Mono 11 for fixed-width, so Qt and GTK render identically. The GTK half lives in gsettings (`org.gnome.desktop.interface font-name`, untracked dconf) rather than in `gtk-3.0/settings.ini`, so changing one side means changing both. When comparing fonts across the two, measure cap height rather than point size — point sizes are not comparable between typefaces. KDE Frameworks apps (Dolphin, etc.) ignore a qt5ct/qt6ct palette entirely and render fully light under `QT_QPA_PLATFORMTHEME=qt5ct`, so the colour scheme has to live in `kdeglobals` (generated from `themes/templates/kdeglobals.tmpl`). The `.config/qt{5,6}ct` configs remain only for Qt5 apps (VLC), which plasma-integration 6 does not cover — launch those with `QT_QPA_PLATFORMTHEME=qt5ct` if they need theming. KDE apps are single-instance, so testing a `kdeglobals` change needs `killall dolphin` first or the old process' cached config is reused. That variable is the whole of whether any of this applies: without it plasma-integration is never loaded, `kdeglobals` is never read, and Dolphin renders in stock Breeze Light no matter what `theme` generated. It lives in `environment.d` and **not** in `.config/uwsm/env` because it is not Wayland-session setup — sway starts as a user unit (`wayland-wm@sway.desktop.service`, under uwsm), so both files reach it, and the split is by what the variable is for. `environment.d` is read by the user manager, and sway being one of its units is what carries the variable into everything sway `exec`s. It applies at manager start, so the change lands at the next login: a `daemon-reload` fixes new *units*, but the running sway's own environment cannot be changed, and apps it launches keep inheriting what it started with.

  Running Qt apps repaint without a restart because `notify_kde` sends what `plasma-apply-colorscheme` sends: a `ConfigChanged` on `/kdeglobals` (`org.kde.kconfig.notify`) *and* a legacy `notifyChange` on `/KGlobalSettings` (`org.kde.KGlobalSettings`) carrying `PaletteChanged`, `StyleChanged` and `IconChanged` (0, 2, 4). The second one is what actually repaints — plasma-integration's `KHintsSettings` still listens on the KDE4-era interface, and rewriting `kdeglobals` with only the kconfig signal leaves every open window on the old palette. Captured by running `dbus-monitor` against a real `plasma-apply-colorscheme` run, and verified by screenshotting Dolphin across `theme set nord` / `theme set catppuccin-macchiato`.
- **Fonts** (`.local/share/fonts/`): SauceCodePro Nerd Font is **vendored**, the same call as adw-gtk3, the Phosphor icons and `emoji.txt` — `.config/alacritty/font.toml` and `.config/Code/User/settings.json` both name it outright, and `vim.g.have_nerd_font` assumes its glyphs, so a fresh machine that has to download it comes up with the wrong font in every terminal. Like adw-gtk3 it needs no `install` support at all: `$XDG_DATA_HOME/fonts` is `~/.local/share/fonts`, already inside `.local`, so the ordinary symlink loop puts it in place.

  Two things make the arrangement work, both established by spike rather than assumed. **fontconfig recurses into subdirectories** of a declared font directory — verified with a face nested two levels deep under a `<dir>` that named only the parent — so the faces can live in their own `SauceCodePro/` subfolder instead of being strewn across `~/.local/share/fonts`. And **fontconfig registers symlinked font files**, which it has to, because `install` links rather than copies. No `fc-cache` call is needed either: fontconfig rescans a directory whose mtime has changed.

  Only the **base family** is vendored — 14 faces, 33MB. Upstream's `NerdFontMono` and `NerdFontPropo` variants (28 more faces, 68MB) are dropped for the reason adw-gtk3's `gtk-4.0/` is: nothing resolves them. Both consumers ask for the family `SauceCodePro Nerd Font`, which is the base. Every weight is kept rather than just the four that render today, so changing `font.toml` to another style does not need a trip back to the nerd-fonts release; alacritty remaps bold to Semibold (`font.bold.style`), so what it actually draws is Regular, Italic, SemiBold and SemiBoldItalic, while the VS Code terminal has no such remap and takes Bold. Adding a face means dropping the `.ttf` in and re-running `./install`. Note that a **copy** rather than a move when vendoring registers every face twice, since `install` then links the repo copy into the directory still holding the original.

- **Scripts** (`.local/bin/`): standalone helper scripts, mostly for Sway/Wayland (brightness, volume, output scaling, etc.).

- **Claude desktop** (`.local/bin/claude-desktop`): a wrapper that adds `--password-store=gnome-libsecret`, and it has to be a wrapper of that exact name. Chromium picks its secret backend from `XDG_CURRENT_DESKTOP`, and `sway:wlroots` lands on `basic_text`, which Electron reports as no encryption at all; the app then logs `[safeStorage] isEncryptionAvailable=false … session will not persist` and declines to save its OAuth tokens. The claude.ai cookie still survives (basic_text encrypts, just weakly), so relaunches looked fine, and every start re-derived the tokens from the cookie with a fresh `/authorize`, which the server refuses with `session_stale_relogin` once the cookie is about a day old: measured, the four re-login demands in the log were each the first start 43h-3d after the previous login, and a start 23h after one was not. With the flag the encrypted `oauth:tokenCacheV2` lands in `config.json`.

  The flag cannot live in a desktop file: the app rewrites `~/.local/share/applications/com.anthropic.Claude.desktop` from the packaged entry on every start (`X-Claude-Generated=true`) and keeps only the first word of `Exec=` for its actions. Every path in (`Exec`, the actions, the `claude://` handler) resolves `claude-desktop` through `PATH`, where `~/.local/bin` precedes `/usr/bin` in sway's environment, so the wrapper catches all of them. The app reads the switch itself (`app.commandLine.getSwitchValue("password-store")`), so it is a path it anticipates.

- **File manager over D-Bus** (`.local/share/dbus-1/services/org.freedesktop.FileManager1.service`): Chrome's "Show in folder", and anything else that calls `org.freedesktop.FileManager1.ShowItems`, never reads `inode/directory` from `mimeapps.list`. It activates whatever owns that bus name, and three system service files claim it: nautilus, nemo and dolphin. Which of several same-named files in one directory wins is arbitrary, and it was nemo. The user service directory is searched before the system ones, so this file pins it to Nautilus. It only takes effect once the current owner exits, so after changing it kill that process (`busctl --user status org.freedesktop.FileManager1` names it) and reload the bus config.

  nemo is not something anyone asked for: it arrived with the whole Cinnamon desktop in the bootstrap `apt install`. `blueman` depends on the virtual `notification-daemon`, `network-manager-applet` on `polkit-1-auth-agent`, and nothing installed provided either one, since Quickshell is invisible to apt. `cinnamon` provides both, so apt satisfied the two of them with it. Purging it means installing some other provider of each first.

- **Output configuration** (`.local/bin/sway-outputs`, `sway-outputs.service`): the sway config names no output at all — mode and scale are derived from each panel's EDID at login and on hotplug.

  Sway's own default is the EDID **preferred timing**, and on the Odyssey G9 that is 3840x1080, which is why the config used to carry a hand-written `mode 5120x1440@240Hz`. "Biggest mode" is not the fix either: the same panel advertises 3840x2160 (8.29MP), which beats its native 5120x1440 (7.37MP) on pixel count. Modes are therefore ranked by **aspect ratio first** — against the panel's physical size from the EDID — then pixel count, then refresh. Measured on that monitor: with the aspect term the rule picks 5120x1440@240, without it 3840x2160@60. This is the trap way-displays falls into too (its `mode_max()` compares `width * height`, so `MODE: MAX: TRUE` picks the wrong mode there and you are back to hand-configuring), and kanshi has no best-mode or auto-scale concept at all — which is why neither is installed.

  The scale ladder is **integer**: 2 at or above 165 DPI, 1 below. Fractional scaling costs Xwayland sharpness, and 1/2 is what this setup always used by hand. DPI alone ignores viewing distance, so a 48" desktop panel and a 14" laptop at the same DPI do not want the same scale; `scaleOverrides` and `modeOverrides` at the top of the script are the escape hatch, keyed by either the sway identifier (`make model serial`) or the connector name. Prefer the identifier — **connector names are not stable**: this monitor moved from HDMI-A-1 to DP-2 and silently orphaned both `output` lines and the aspect-toggle script, with no symptom beyond the resolution being wrong.

  Four things the implementation settles, each established by spike:

  - **With no readable EDID, do not guess.** Ranking on pixel count alone is not a neutral fallback — it is what picks this panel's 3840x2160 (8.29MP) over its native 5120x1440 (7.37MP), i.e. exactly the wrong answer, and the one that looks like "it chose a lower resolution". An output with no EDID and no override is left to sway's own preferred-mode choice, and is deliberately *not* added to the seen-set, so a read that failed transiently at startup is retried on the next output event.
  - **Sway's IPC does not report physical size**, so it comes from `/sys/class/drm/card*-<name>/edid` — detailed timing descriptor 1 (whole mm) in preference to the base block (whole cm). The connector directories are **symlinks**, so the glob needs `(-/)` and not `(/)`; and a sysfs binary attribute always stats as **zero bytes**, so the guard is `-r`, never `-s`. Both of those fail silently, leaving every output at aspect 0 and the wrong mode.
  - **`(#b)` backreferences need `setopt extended_glob`**, which a script does not inherit from the interactive shell. Without it every `modeOverrides` value fails to parse.
  - `resolve()` runs inside a command substitution, so a `die()` there exits only the subshell — it is reported once per caller and the script carries on. Overrides are therefore validated up front in the main shell.
  - **A `swaymsg output` is a full modeset**, which is lockup trigger #1 (see `.claude/sway-lockup-investigation.md`), so nothing is ever issued unless it is a real change. `apply` on a correctly configured output prints `(unchanged)` and touches nothing.

  **Applying over IPC is not enough on its own, and this is the central fact about the whole arrangement.** Sway resets an output it has no config for to its EDID preferred mode *and* its default scale on **every** apply — `swaymsg reload` included, which the quickshell power menu offers as "Reload Sway". That is `queue_output_config` in `sway/config/output.c`: with no matching `output_config` supplying `width`/`height` it calls `wlr_output_preferred_mode`, and with none supplying `scale` it calls `compute_default_scale`. So a reload silently dropped this monitor from 5120x1440 to 3840x1080, and the watcher's seen-set (below) meant nothing put it back.

  So what `sway-outputs` resolves is also **written to a generated sway include**, `~/.config/sway/outputs.conf`, which `sway/config` `include`s — the same arrangement as `theme.conf`, and generated into the live config directory rather than the repo, so it is never tracked. Sway then owns the values: they are applied at startup before the first frame, and reasserted on every reload. Entries are keyed by identifier and **merged rather than rewritten**, so a monitor that is currently unplugged keeps its line and comes back correct the instant it is plugged in, before the watcher has even seen the event. `install` writes a one-line stub if the file is absent, since sway parses the `include` before anything has had a chance to generate it. Verified that sway really reads it by putting a bad directive in it and watching `sway --validate` name the file and line.

  A corollary worth knowing: a runtime override (`sway-scale`, `sway-toggle-aspect`) holds until the next reload and is then reverted to the generated value. That is the same behaviour the hand-written `output` line always had.

  `watch` configures an output **once, when it appears**, keyed on the identifier and dropped when it disconnects. It cannot re-apply on every event: a mode or scale set by hand afterwards (`sway-scale`, `sway-toggle-aspect`) fires an output event of its own, and re-applying on that would undo it a frame later. The cost is that a service restart forgets the set and reverts a hand-set value once. `swaymsg -r -m -t subscribe '["output"]'` is the change signal, debounced 300ms because a hotplug arrives as a burst; if that child dies the loop ends and `Restart=always` rebuilds it.

  `sway-outputs show` reports what it resolved for every output; `scale` and `mode` print one field, which is how `sway-scale default` and `sway-toggle-aspect` stay in step with the ladder rather than carrying their own copy of it. `mode` also takes an aspect ratio — `sway-outputs mode DP-2 16:9` — and then returns the best mode at that shape **that still fits inside the native one**. That bound is the whole point of it: the G9's largest 16:9 mode by pixel count is 3840x2160, which the panel cannot display (1440 rows of hardware) and must downscale, while the bounded answer is 2560x1440@240, landing on the native pixel grid exactly.

  `sway-laptop-lid` follows the lid, and names neither the panel nor the lid device — the same portability argument as the rest of this section, since the config is meant to drop onto a second laptop unedited. The panel is any DRM connector of an **internal** type (`eDP`, plus `LVDS` and `DSI` for older machines and tablets) whose `status` reads `connected`, which is also the test for "is this a laptop": logind reports a lid state on machines that have no lid, so gating on the lid would be wrong, while gating on the panel makes the script a no-op on a desktop. The state itself comes from logind's `LidClosed` property rather than `/proc/acpi/button/lid/*/state`, which does not exist on every machine — the ACPI path stays as a fallback, globbed, because the device under it is `LID`, `LID0` or a PNP id depending on the firmware. With no source answering it does nothing rather than guessing.

  Sway's `bindswitch` passes the state explicitly (`lid:on` is **shut**, per `man 5 sway`), and `exec_always sway-laptop-lid` with no argument reads it at startup, which is what picks up a lid that was already closed. `--reload` on both bindings is load-bearing now that outputs.conf exists: a reload re-enables every output the include names, and re-running the binding matching the current lid state is what shuts the panel again. Verified against a fake DRM tree — a connected `eDP-1` and `LVDS-1` are found while a connected external `DP-1` and a disconnected `eDP-2` are not.

  `sway-toggle-aspect` ($mod+Ctrl+backslash) swaps the focused output between those two, and takes an optional `W:H` argument. It replaced `sway-samsung-width`, which halved a hardcoded `HDMI-A-1` — the connector this monitor has not been on for some time. It compares **resolution only** when deciding which way to go, since the refresh in a mode string is rounded, and falls back to native from any third state; on a panel whose native mode already is the requested shape it says so and does nothing.
- **Quickshell** (`.config/quickshell/`): the whole desktop shell, written in QML with [Quickshell](https://quickshell.outfoxxed.me/): bar, notifications, launcher, window switcher and cycler, OSD, the audio/bluetooth/network/media/calendar/emoji panels, wallpaper, polkit agent and lock screen. It replaced swaybar, dunst, wofi, zenity, swaybg, pasystray, blueman-applet, playerctl, bemoji and polkit-kde. Its working rules are in `.claude/rules/quickshell.md`, which loads whenever a file under `.config/quickshell/` is opened, and the full notes behind them are in `.claude/quickshell-reference.md`. What matters from outside it:

  - It runs as `quickshell.service` under `sway-session.target`, not as a sway `exec`: restart it with `systemctl --user restart quickshell`, and its log is `journalctl --user -u quickshell`. `swaymsg reload` and theme switches do not restart it.
  - Sway reaches it only through `quickshell ipc call <target> <function>`. An IPC call exits 0 even when it did not land.
  - The lock screen is a separate process, `quickshell-lock.service`, started by `.local/bin/lock`. swayidle (`swayidle.service`) owns every idle timeout, and the shell only draws the dim.
  - nm-applet still runs (it is NetworkManager's secret agent) and blueman-applet is D-Bus activated as the BlueZ pairing agent: neither is a leftover. dunst is masked, not removed.
  - Adding, renaming or moving a file under it needs `./install`, and a dangling old link kills the shell at load.
- **Screencasting** (`.config/xdg-desktop-portal-wlr/config`, `.local/bin/screencast-chooser`, `services/ScreencastService.qml`, `modules/screencast/`): sway 1.12 and wlroots 0.20 can share a **single window** rather than a whole output, and xdg-desktop-portal-wlr 0.8.4 speaks the `ext_foreign_toplevel_list_v1` and `ext_image_copy_capture_v1` needed for it. What was missing was the picker: with no `chooser_cmd` configured xdpw walks a built-in list of dmenu-alikes and lands on **wmenu**, a one-line list of raw labels with the toplevel's identifier hanging off the end of each. `screencast-chooser` replaces it with a Quickshell grid of live thumbnails.

  **The chooser is a protocol, not a program.** `chooser_type=dmenu` means xdpw forks `chooser_cmd` through `/bin/sh -c` with a pipe on each end, writes one label per line to its stdin, closes it, then **`waitpid`s for the process to exit before reading a single line back** from its stdout. So a chooser cannot stream an answer and stay alive: it blocks until the user picks, prints one line, exits. The reply must be a label xdpw itself produced — it regenerates each one and `strcmp`s it — so labels are echoed back byte for byte and never rebuilt. Printing nothing is a cancel, and the whole exchange happens during **`SelectSources`**, not `Start`.

  The labels are `Monitor: <name> <description>` and `Window: <title> (<identifier>)`. Parse a window label **from the right**: titles routinely contain " (" themselves, as in `Messages - (1) Google Messages for web`. That identifier is the hinge the whole feature turns on — it is `ext_foreign_toplevel_list_v1`'s, and it is the same string in three places: sway's IPC tree exposes it per container as `foreign_toplevel_identifier`, and `grim -T <identifier>` captures by it. Matching on title would have been ambiguous between two windows of the same name; matching on the identifier cannot be.

  **Quickshell 0.3.0 cannot capture a toplevel, so the thumbnails are grim's.** `ScreencopyView` looks like the obvious answer and is not: its three backends are `IccOutputSourceManager` (ext-image-copy-capture), `WlrScreencopyManager` and `HyprlandScreencopyManager`, and only the Hyprland one takes a window. Handed a wlr `Toplevel` on sway it logs `Capture source set to non captureable object` and draws nothing — measured across all 13 open windows, every one `hasContent: false`, `sourceSize: -1x-1`. The binary does carry the string `ext_foreign_toplevel_image_capture_source_manager_v1`, which makes it look supported; no class binds it.

  grim does bind it. `grim -T <identifier>` captures a window **that is not visible** — occluded, or on another workspace — which is exactly the case that matters, since a region grab of the window's rect would return whatever is painted on top of it. Measured on 13 windows: 12 succeeded including seven on other workspaces, and one Electron window (Claude) failed with `Invalid stride`, so a failed capture is expected rather than exceptional and the picker falls back to the app icon. All of them in parallel cost ~320-500ms at `-s 0.25 -l 1`. Scale is computed per window from sway's rect against a 640px target rather than fixed. Debian's grim is built **without jpeg** (`jpeg support disabled`), so PNG is not a preference.

  **`grim -T` hangs on a toplevel xdpw is already capturing** — which is precisely the window that matters, the one just shared. Measured on one window: 162/161/160ms with nothing streaming, then, while xdpw held a capture session on it, one 161ms run followed by two still running at 6s, with a different window captured at the same instant in 6ms. It does not hang on *every* attempt, and that intermittency is what makes a per-capture timeout the wrong shape: the first re-share looks fine and the next two do not. With a per-capture timeout of 8s the picker appeared **8.4s** after the share button on every re-share (8419ms and 8471ms, against 469ms for the first share of a session). Thumbnails are therefore bounded by a budget for the *whole batch* (`CAPTURE_BUDGET`), and whatever has not arrived by then falls back to the app icon.

  **xdpw services nothing while the chooser runs**, and this is the thing to keep in mind before putting any work in it. Its event loop is single-threaded and sits in `waitpid`: asked for a D-Bus property it replies in 0ms before and after the picker, and not at all — two 5s timeouts — while the picker is open. So every second the chooser spends is a second an *already running* screencast is frozen, which is why the hung capture above was worse than a slow picker and why re-sharing while presenting was the case that broke. Anything slow belongs outside the chooser, or bounded.


  **A shared window that is not repainting delivers no frames, so the app sits forever on "Starting presentation".** This is the one to know, because every symptom it produces points somewhere else. xdpw's toplevel capture only hands PipeWire a frame when the client commits a new buffer, and a static window commits none — so the consumer waits for a first frame that never arrives. Anything that makes the window repaint starts it instantly: focusing it, moving the mouse over it, or the window animating on its own. A window containing an animated GIF **never** hangs, which is the control case that proves it.

  It is not the chooser and not the thumbnails. Measured by disabling thumbnail capture entirely, so the chooser opened no capture session on any toplevel: the hangs continued unchanged. Everything the chooser does is finished and correct before the failure begins — it answers, exits, and only then does xdpw's capture fail to produce.

  This also explains why `grim -T` hangs on a toplevel xdpw is streaming, recorded above as a capture-session conflict. The likelier reading is the same damage rule: a single-shot capture gets the compositor to composite the toplevel on demand, while a second, concurrent session waits for damage that a static window never produces. The batch budget is the right fix either way, but do not trust the "already capturing" explanation for it.

  Two dead ends worth not repeating. **Making the window *visible* is not enough** — switching to its workspace left the stream just as dead, because visibility is not repainting. And **`pw-top` cannot tell a working share from a hung one**: both show `QUANT=0 RATE=0 W/Q ???` on the video nodes, since those columns are meaningless for nodes that are not clock-driven. The link shows `active` and the format negotiated in both cases too. The only reliable signal is whether the picture appears.

  **A wedged screencast is cleared by restarting the portal, not the browser** — `systemctl --user restart xdg-desktop-portal-wlr`. Once, every share hung at Firefox's "Starting presentation", consistently and across a Firefox restart, and came back on the next xdpw restart with no code change. The chooser was not implicated: it ran and produced a valid label, which its replay state file records on every pick. The mechanism was never established, so this is a recovery procedure and not an explanation.

  Two things that look like they would diagnose it and do not, both learned the hard way. **A portal handshake test proves nothing**: a client that drives `CreateSession`/`SelectSources`/`Start` and stops there never consumes the stream, so it reports success whether or not frames are flowing — which is exactly the failure being investigated. And **xdpw logs nothing at all while a share is live**, even at `-l TRACE`; measured across a known-good share and a hung one, both zero lines between the session-start and session-close bursts, so the journal cannot separate them either. What does show it is `pw-top`, or `pw-dump` filtered to xdpw's node, which report whether the node is actually producing; both ship with pipewire and are installed.

  Two things about `quickshell ipc call`, both of which cost a debugging session:

  - **It interprets an argument that looks like JSON** instead of passing it through. An array sent inline came back with its outer brackets stripped and parsed as a bare object, whose `length` is `undefined` — so the picker opened with every target filtered away and showed "No matches". The targets go over a **file** now, and only paths cross the IPC boundary. Anything structured wants the same treatment.
  - **It exits 0 when the call did not land**, printing `Target not found.` or `Function not found.` on *stdout*. The exit code is only meaningful for a shell that is not running at all, which is 255 with `No running instances`. The chooser therefore tests both, and on either falls back to xdpw's own chooser list — a broken bar must not take screensharing down with it.

  The answer comes back over a **FIFO** in the chooser's own temp directory, because `quickshell ipc call` returns as soon as the QML function does and cannot wait on a user. The chooser opens the read end *before* asking the shell, so the writer can never arrive first; `O_NONBLOCK` is what allows that open with no writer yet, and a writer that opens and closes without writing arrives as a readable end-of-file, which is the cancel. Every path that fails to show the picker must still answer that FIFO — a `FileView` that will not load included — or the chooser blocks, and xdpw's `waitpid` blocks behind it, wedging every later screenshare until the portal is restarted. `PICK_TIMEOUT` is the backstop for a shell that dies mid-pick.

  The thumbnails are pictures of the user's windows, so the temp directory is removed on the way out and a `SIGTERM` handler turns a kill into a `SystemExit` so that cleanup actually runs.

  **Chrome asks more than once for a single share, so the chooser replays its answer.** Measured at TRACE over one Google Meet share: **three** `CreateSession`/`SelectSources` rounds in nine seconds, every one of them `types: 2`. The first ran to completion and returned PipeWire node 123, which Chrome then closed; the second was abandoned without ever calling `Start`; only the third became the stream. Nothing in the portal path failed — the chooser answered all three correctly with the same label — so this is Chrome's own flow, and wmenu did it too. Teams is Chrome as well, so it behaves identically.

  With the replay in place, four consecutive Meet shares were **exactly three rounds each**, every one of them one real pick followed by two replays: the pick took 1.3-7.3s of the user deliberating, and the two replays 22-43ms with no picker drawn. The gap from an answer to the next round is ~1.5s and then ~5ms, consistently. The third round of every share offers one *more* label than the first two (14 against 13) — that is Chrome's own sharing-indicator window appearing — which is exactly why the replay guard checks that the remembered label is still on offer rather than that the list is unchanged.

  **A cancel is the case that most needs this.** Declining a share produced **six** further rounds at roughly half-second intervals, all of which the replay answered as cancels. Without remembering the cancel, saying no once would mean saying no seven times.

  `screencast-chooser` therefore records its last answer in `$XDG_RUNTIME_DIR/screencast-chooser.last` and replays it to a repeat request inside `REPLAY_WINDOW` (5s), refreshing the timestamp each time so a *chain* of rounds keeps replaying rather than only the one after the pick. Across every round measured the gap from one answer to the next request was at most 2.0s, which is the evidence the window is generous enough while staying well below the time it takes a person to stop a share and deliberately start another — a genuine second share, twelve seconds after the previous answer, correctly fell outside it and drew the picker. The guard is that the remembered label must still appear in what xdpw just offered: the source list changes between rounds (13, 13, then 14 labels, as Chrome's own sharing-indicator window appears), and replaying a label xdpw did not just produce would come back as `selected unknown target` and drop the session. A cancel is remembered too, so declining a share declines the rounds behind it instead of asking once per round. The replay is answered *before* the thumbnails are grabbed, so a repeat costs ~55ms and never flashes a picker.

  This is the one part of the arrangement that is a workaround rather than a mechanism, so it is worth knowing what it would look like if it misfired: a share started within five seconds of the previous pick would silently reuse that pick. Nothing observed comes close to that, but raising `REPLAY_WINDOW` is what would make it reachable.

  The picker itself is a grid rather than the shell's usual `FilterList`, since what is being chosen is a picture; it reuses `Fuzzy` directly for the search field but not `FilterList`, which is a `ListView` at heart. It is instantiated once in `shell.qml` rather than per bar, like `PolkitDialog` — and that instantiation is load-bearing for the usual reason: `ScreencastService` is reached only over IPC, so without a `visible: ScreencastService.active` binding to warm it the singleton would never be created and its `IpcHandler` never registered.

  Testing this without a meeting client means driving the portal over D-Bus directly: `CreateSession` → `SelectSources` (`types: 3` for monitors and windows) → `Start`, watching the `Response` signal on each `Request` path. A window selection comes back as `source_type: 2` with a PipeWire node id. Raising xdpw's log level needs a systemd drop-in (`ExecStart=/usr/libexec/xdg-desktop-portal-wlr -l TRACE`), since it is D-Bus activated and takes no arguments otherwise.

- **Screen recording** (`.local/bin/record-region`, `services/RecordingService.qml`, `modules/bar/Recording.qml`): `$mod+Ctrl+p` toggles a wf-recorder capture, sitting beside the two grimshot screenshot binds it is the moving-picture half of. Files land in `$(xdg-user-dir VIDEOS)/Recordings`, timestamped with dashes rather than `date -Ins`'s colons, which are legal in a filename and a nuisance in every app the file is later dragged into. Video only — wf-recorder's `-a` is what would add audio.

  **Left to itself wf-recorder follows the output's refresh rate**, which on the G9's 240Hz mode is a 240fps recording that nothing wants, so `RecordingService.framerate` pins it at 60. Measured over the same 8s capture of one window: the default produced 1853 frames and 1.5MB, `-r 60` 478 frames and 396KB, `-r 30` 239 and 236KB. The duplicate-DTS warnings a 240fps file drew from `ffmpeg -f null` did **not** reproduce across that comparison, so they are not the framerate and remain unexplained; every one of the three decoded clean.

  The selection is **`grimshot anything`'s, exactly**: every visible window's rect goes to slurp on stdin and `-o` adds one more per output, so a click picks a window or a whole screen and a drag picks an arbitrary area. It stays a script rather than moving into the service because the jq filter is full of backslashes, which a QML string eats — the same trap `LauncherService`'s embedded awk is written around.

  **wf-recorder finalises its container on SIGTERM and not only on SIGINT, and that is what lets the recorder be a quickshell `Process`.** Measured with a SIGKILL control, since exit status alone proves nothing here — all three exit 0: SIGINT and SIGTERM both leave a `moov` atom and a playable file, SIGKILL leaves a 48-byte `ftyp`/`free`/`mdat` stub with no `moov`. So `running = false` saves the recording, and a `systemctl --user restart quickshell` **stops** one rather than truncating it. This is the deliberate exception to the rule that apps are launched with `I3.dispatch("exec …")` and never as a `Process`: that rule is about surviving a shell restart, and here being stopped by one is the correct behaviour, since the indicator that stops a recording goes away with the shell.

  **The `exec` in the recorder's `sh -c` is load-bearing.** Without it the shell stays the process and takes the SIGTERM, leaving wf-recorder orphaned and the container never finalised; with it the recorder is a direct child of quickshell, which is how to check it (`ps -o ppid=` on the wf-recorder pid).

  **wf-recorder writes limited-range YUV and tags it full-range**, so every recording came out washed out until the file was tagged for what it actually contains: `-p color_range=tv -p colorspace=bt709 -p color_primaries=bt709 -p color_trc=bt709`. Left alone it produces `yuvj420p` with `color_range=pc` while the samples occupy 16-235, so a player that honours the tag does no expansion and blacks sit at ~22 instead of 0.

  The reason this is worth writing down is that **it presents as a player bug and is not one**: mpv honours the tag and looked washed out, VLC guesses limited range and looked correct, so the file appeared fine in half the places it was opened. mpv is the honest reporter here.

  Measured against a `grim` capture of the same frame, which is the ground truth for this — record a region, grab it with grim while recording, extract the frame and difference the two. Mean per-channel error over the frame, rendered **by mpv**: 23.18 before, 0.79 after. The fitted transfer on the broken file was `0.8328*ref + 16.40` against the textbook limited-range squeeze of `0.8588*ref + 16`, and expanding by `(v-16)*255/219` by hand took the error from 14.02 to 1.01, which is what identified the mechanism. `-x yuv420p` does **not** help — wf-recorder overrides it and the file is still tagged `pc`. `-F "scale=out_range=full"` is the other repair, making the data match the existing full-range tag, and it measured slightly worse (1.55) as well as leaving a full-range h264 file that anything ignoring the flag will crush.

  **wf-recorder also converts with BT.601 whatever the frame size**, which is a second and subtler mismatch, since the file is HD and any player guessing a matrix by resolution guesses BT.709. Measured directly by pushing pure red through the same conversion: Y comes out 81 (BT.601) at 320x240, 1280x720 and 1280x1408 alike, where BT.709 would be 63. So it does not vary with the monitor or the mode — and the default codec is software libx264, not anything the GPU picks, so it does not vary with hardware either. `-F "scale=out_color_matrix=bt709"` converts with the right matrix, which is better than re-tagging the file BT.601 because it leaves the samples and the tags and the resolution guess all saying the same thing. wf-recorder confirms it took the filter by logging `Using video filter: scale=out_color_matrix=bt709,fps=60`.

  Confirmed end to end against a deliberately colourful, motionless page (`|BT.601-BT.709|` luma averaging 3.45 across the frame against 0.3 for the usual dark desktop, and zero motion between two `grim` grabs two seconds apart — both worth checking before trusting a run of this). The control and the fix come out mirror images: with no filter the Y plane matches BT.601 at 0.963 against BT.709's 3.486, with it BT.709 at 1.020 against BT.601's 3.499, and over the 632k pixels where the matrices actually disagree the split is 1.4 vs 9.9 and 9.8 vs 1.6. Rendered by mpv the whole-frame error halves, 3.70 to 1.74, and on saturated pixels falls 8.13 to 2.94.

  **Do not test a matrix with a whole-frame colour average.** An earlier pass concluded from one that the data was already BT.709 and tagged it so, which was wrong: on a dark, low-saturation desktop the two matrices never predict a luma more than 3 apart, so the average has no power to separate them and simply reported noise. The test with power is the **Y plane**, which 4:2:0 does not subsample — predict luma from a `grim` capture under each matrix and difference it against the actual plane. That gave BT.601 a mean error of 0.313 (median 0.115, i.e. rounding) against BT.709's 0.647, on the same frame where the colour average had preferred BT.709.

  **wf-recorder does not exit on a region it cannot capture.** Handed one outside any output it prints `Invalid region to capture: must be completely inside the output`, falls back to `selected region 0,0 0x0`, and goes on running — so a drag spanning two outputs would otherwise report a saved file with nothing in it. The service reads stderr with a `SplitParser` and not a `StdioCollector`, which buffers until the stream ends while this message is printed with the process still running, then stops the recorder, deletes the file and notifies. Exercised with a synthetic off-screen geometry rather than a real cross-output drag, this machine having one output.

  The bar item is a red Phosphor `record` icon and the elapsed time, shown only while recording and clicking to stop, and its `visible: RecordingService.active` binding is also what warms the singleton — reached otherwise only over IPC, it would never be created and its `IpcHandler` never register. It hangs off the clock's **left** edge in the centre section, mirroring the media item on the right, so it grows outward rather than displacing anything: measured across the indicator appearing, the columns from the clock's left edge rightward are byte-identical, and only the 70px to its left change. Park the pointer before comparing two `grim` captures of the bar — the cursor is composited into the capture and lands right where the clock is.

- **Privacy indicators** (`.local/bin/camera-watch`, `services/PrivacyService.qml`, `modules/bar/Privacy.qml`, `modules/privacy/PrivacyPanel.qml`): a webcam and a microphone icon in red, in the centre section left of the clock, shown only while something is capturing — so a camera or a mic that is live when nothing should be is visible rather than inferred. The two icons are **one** item with one `BarPopup` behind them, because they raise the same question and it has a single answer: the card names the processes holding each device, with the pid, which is what turns "something is listening" into something answerable. It is a report and not a control — stopping a capture belongs to the app doing it.

  The two halves share nothing but the question. **The microphone is Pipewire's to report**, and the discriminator is the *link*, not the node: a capture is a `Stream/Input/Audio` node, and so is a desktop-audio capture — a screenshare with audio, `wf-recorder -a` — which is fed by the `Audio/Sink` where a microphone capture is fed by an `Audio/Source`. Measured both ways round: `pw-record` on the mic linked from the source, and `PIPEWIRE_PROPS='{ stream.capture.sink = true }' pw-record --target=<sink>` linked from the sink, on the same node type. A stream with no link at all is connected to nothing and is not use either, which is what keeps an idle stream dark for free. Node `type` and link ends are both readable **untracked**, so this needs no `PwObjectTracker` — and `properties` on an untracked node reads `{}` rather than empty strings, so nothing here can name the app.

  **V4L2 exposes no in-use flag**, so the webcam half is which processes hold a `/dev/video*` node open. inotify `open`/`close` on the device nodes is the trigger — it works on devtmpfs, measured at 17ms from open to event — and `fuser` is the read, at 64ms. A shell loop over `/proc/*/fd` is not an alternative: measured at **15.2s**, and slow enough that it walks past a holder that has since closed, which is what a first pass mistook for the device not being held at all. The 250ms settle before each read is what keeps an app *enumerating* devices from flashing the indicator — measured, an open followed immediately by a close reports nothing at all, while a real hold is reported 340ms in and its release 320ms after. `fuser` sees only this user's processes, so a camera opened by a root process reads as idle.

  The bar's centre grew a **Row** for it: everything hanging off the clock's left edge shares one, because `Recording` measures a non-zero width even while hidden (its elapsed time is still `0:00`), so two individually anchored indicators would each hold a gap open beside the clock. A positioner drops an invisible child entirely, spacing included. Verified byte-exact against `grim`: across idle, mic, camera and both, every column from the date rightward is identical and only the columns left of the clock change, growing outward.

  Naming the microphone's user is the one thing here that costs a `PwObjectTracker`: an untracked node reports `properties` as `{}`, so `PrivacyService` tracks the streams its filter already selected and reads `application.name` and `application.process.id`, falling back to the node name. The camera's names come from `camera-watch`, which reports `idle` or `active` followed by one tab-separated `<command> (<pid>)` per holder; `/proc/<pid>/comm` is the command, so what appears is the process rather than the app — Chrome's webcam holder is its `VideoCaptureService` utility process, showing as `chrome`.

  The watcher's outer loop is what makes it self-healing: kill its `inotifywait` and the pipe ends, the loop restarts it two seconds later and re-reports the state from scratch, which is why a repeat of the current state is expected on the wire and ignored by the reader. Verified by killing it under the running shell — the indicator lit and cleared again afterwards.

  Phosphor's `video-camera` is vendored for this; `video` is a screen with a play triangle and `eye` is already the Insomnia indicator.

- **Idle inhibitors** (`services/IdleInhibitService.qml`, `modules/bar/IdleInhibit.qml`, `modules/idle/IdleInhibitPanel.qml`): a coffee cup left of the clock, shown only while something is holding the session awake, whose popup names what. Two mechanisms answer that question and both are listed — a Wayland `zwp_idle_inhibitor_v1` on a window, and a logind idle inhibitor on a process — and **both now really do hold idle off**, since swayidle honours each (see Quickshell, above). Insomnia's third mode appears in the logind half, since that is how it takes its lock. This indicator is load-bearing rather than informational: it is what makes the deliberate absence of any ceiling on inhibitor-held idle acceptable.

  **An inhibitor existing is not the same as it holding idle off**, and the icon follows sway's own rule rather than the object's presence. Sway reports `idle_inhibitors: {application, user}` per container in `get_tree`, and an `application` inhibitor counts only while that view is `visible`; each `inhibit_idle` mode has a test of its own (`open` always, `visible`/`fullscreen` on visibility, `focus` on the view or a child being focused), which is why the config's `for_window [con_mark="no idle"] inhibit_idle open` is picked up. Verified as a mirror-image A/B: with Chrome and Claude visible and both holding an `application` inhibitor the cup shows, and with the same two inhibitor *objects* still reported on a hidden workspace and no logind inhibitor it is gone, the rest of the bar unmoved in both. Sway's attribution of an inhibitor to a particular view has been seen to be misleading, so a *row* may name the wrong window even though the aggregate is right.

  Neither side has a change signal, so it polls at 5s: sway emits no IPC event when a client takes or drops an inhibitor, and logind's `BlockInhibited` says only whether *something* holds idle, not what. Both reads cost ~7ms. The logind half is `busctl --json=short call … ListInhibitors`, whose rows are `[what, who, why, mode, uid, pid]`; **logind refuses a delay-mode idle inhibitor** ("Delay inhibitors only supported for shutdown and sleep"), so every row naming idle is a block and there is no mode to filter on.

  Two naming traps. `children` is a **read-only property on every QML object**, so a singleton defining `function children(...)` fails to load with "Invalid property assignment" and takes the whole shell down with it — the tree walk is `childNodes`. And the bar item is `IdleInhibit`, not `IdleInhibitor`, because `Bar.qml` instantiates Quickshell's own `IdleInhibitor` type and a same-directory component of that name would shadow it.

- **System monitor** (`.local/bin/sysmon-watch`, `services/SystemMonitorService.qml`, `modules/bar/SystemMonitor.qml`, `modules/sysmon/SystemMonitorPanel.qml`, `widgets/{GaugeIcon,HistoryGraph}`): a CPU and a memory gauge in the right section between Insomnia and the display item, one clickable unit opening a `BarPopup` with a minute of CPU, memory and network history, every core, swap, load, uptime and the top processes, with `gnome-system-monitor` as "advanced…". `GaugeIcon` is the glyph as its own gauge: drawn in `surface2`, with a copy in the level colour (`barStatusline`, yellow from 70%, red from 90%) clipped from the bottom up. The fill spans the glyph's *ink* and not the square, so each icon carries `glyphTop`/`glyphBottom` read off the Phosphor path (cpu 16-240 of 256, memory 56-208); without that a 10% reading fills nothing visible and 90% looks full.

  `sysmon-watch` is a persistent Python process emitting one JSON line a second, read with a `SplitParser` and restarted by the same 10s timer `camera-watch` has. The per-process scan is the only part that costs anything, so it runs only while `detail on` has arrived on stdin (`Process.stdinEnabled` + `write()`), which the panel sends on `expanded` and re-sends from `onStarted` so a restarted watcher comes back in the right mode. Measured on the 28-core desktop: 1-2ms/s with the panel closed, ~19ms/s with it open. History is uniform because the interval never changes; only the scan is gated. The first scan after `detail on` takes a baseline and emits no list, since an all-zero CPU column would sort by pid; kernel threads (RSS 0) are dropped; a process's `cpu` is its share of *all* cores so the column sums consistently with the total. Network counts only interfaces with a `/sys/class/net/<name>/device`, which leaves out `lo` and bridges. The panel's process list is fixed at eight rows so the list arriving two seconds after the card opens does not grow it, and sorting by CPU or memory is client-side over a union of the watcher's top twelve by each.

- **Display panel** (`services/DisplayService.qml`, `modules/bar/Display.qml`, `modules/display/DisplayPanel.qml`): a monitor icon left of the volume item, opening a `BarPopup` with every output: an enable switch, the resolutions on offer with the refresh rates at the current one, the scale, and on an ultrawide a "Shape" pair swapping between the native mode and the best 16:9 mode inside it, which is `sway-toggle-aspect` as a click. Everything it sets is a sway `output` directive over `I3.dispatch`, and it holds exactly as long as a hand-run `swaymsg output` does: until the next `swaymsg reload`, when sway reasserts `outputs.conf`. The "reset" link beside an output that is off its defaults applies that same value now, mode and scale in one commit. Two switches under the header toggle **adaptive sync and HDR** (`output <name> adaptive_sync|hdr on|off`), shown only where `get_outputs`' `features` object reports the capability; both are connector properties, not modes, so neither is a modeset. Each is bound to the state sway reports rather than to its own click, so a refused `hdr on` (a renderer without HDR) leaves the switch off, and `hdr-run` or a terminal `swaymsg` moves it live.

  The service reads two things and derives the rest. `swaymsg -t get_outputs` is the state and the mode list; `sway-outputs json` (new subcommand, one call for every output, ~20ms) is what the ladder resolves, so "native", "default" and the 16:9 candidate come from the same code that configures the outputs at login and never need a second copy here. An output the script cannot resolve (no EDID) is simply absent from that answer and the panel shows it without a native marker, a default scale or a shape row. A modeset or a hotplug arrives as a burst of output events, so the `subscribe '["output"]'` reader settles 300ms before re-reading, and the panel re-reads on open besides.

  **No command is ever issued that is not a change.** Every setter compares against the current state first, and a same-value `swaymsg output DP-2 scale 1` was measured to produce an output event, so it is a real commit and not a no-op on sway's side; a commit is the modeset path in `.claude/sway-lockup-investigation.md`. Verified by clicking the already-selected shape, refresh and scale chips under a subscription: zero events. Ultrawide is a native mode at least twice as wide as tall (`ultrawideAspect`), which catches 21:9 and 32:9 and leaves 16:10 alone. The shape comparison is on resolution alone, as `sway-toggle-aspect`'s is, while "reset" compares the whole mode so a native-resolution output at a lower refresh still gets one.

  The last active output cannot be disabled from the panel: the switch is dimmed and `setEnabled` refuses, because sway carries on with nowhere to draw and the bar goes with everything else. Enable and disable are otherwise untested on this machine, which has one output. `native` is a reserved word in QML, in a `const` inside a function as much as in a property name, and the parser reports it only as "Expected token `identifier'" with a line number, which is why the field is `nativeMode`.

- **Gaming** (`.config/gamemode.ini`, `.config/MangoHud/MangoHud.conf`, `output * adaptive_sync on` in `sway/config`): what the gaming distros (CachyOS, Bazzite) do that is worth having here, measured on demise rather than assumed. Most of the kernel side is already in Debian's kernel: `PREEMPT_DYNAMIC` + `PREEMPT_LAZY`, `NO_HZ_FULL`, `sched_ext` support, ntsync as a module, `vm.max_map_count` at 1048576. The two things that measurably mattered were both userland: a daemon to flip the CPU governor while a game runs, and the ntsync module being loaded. A custom kernel (1000Hz, BORE), an x86-64-v3 userland, zram, THP `always` and ananicy were all deliberately not done; the first because it would mean rebuilding the NVIDIA module against a third-party kernel on a machine whose driver is held at 610 for a reason, the rest because they are for 16G handhelds or measure as a wash.

  **gamemode** is the governor switch, on demand. `gamemoded` is D-Bus activated (`gamemoded.service`, nothing to enable) and `gamemoderun` is only `LD_PRELOAD=libgamemodeauto.so.0`; a Steam launch option of `gamemoderun mangohud %command%` is the whole integration. While a client is registered it sets the governor to `performance` (EPP `performance` under `intel_pstate`), `kernel.split_lock_mitigate=0`, and renices the game to -4, and restores every one of them on exit. It is measured to do nothing else: an ordinary run-and-quit leaves the governor at `powersave` and split lock at 1. The day-to-day setting stays `powersave`/`balance_performance`, which on a desktop is a heat and noise question rather than a battery one, and the governor only matters for bursty per-frame loads, which is exactly the case the daemon covers.

  Three things about Debian's package, each of which looks like gamemode not working. **The `gamemode` group does not exist until `systemd-sysusers` runs** (the postinst does not), and the polkit policy has `allow_active=no` for all four helpers, granting them only through `rules.d/gamemode.rules` to that group; without membership the governor switch prompts or fails. Membership works for polkit immediately, since polkit resolves groups from NSS rather than from the process. **The renice needs `Max nice priority` above 0 in the daemon**, which comes from `limits.d/10-gamemode.conf` (`@gamemode - nice -10`) via `pam_limits`, and that is in the `systemd-user` PAM stack but **not** in greetd's (Debian's `common-session` carries no `pam_limits`; only `/etc/pam.d/login` does). So the daemon gets it and terminals never do, which is fine because `setpriority` checks the caller's limit and the caller is the daemon. But the daemon inherits it from `user@1000.service`, and with **linger on (rootless Docker needs it) that manager survives logout**, so a re-login changes nothing: measured, the same `gamemoded` pid with the old groups and limit 0 was still running after a logout and login. A reboot fixes it; without one, `sudo prlimit --pid <user@ pid> --nice=30:30` then `systemctl --user restart gamemoded` does the same. And **gamemode refuses to renice a process that is not at nice 0** (`prio was (5) but we expected (0)`) or whose ioprio is not the default, as a safety check; Claude's Bash tool starts children at a non-zero nice, so renice and ioprio can never be verified from there, only from a real terminal or a Steam launch. The group, the limits and the module load below are machine-local state, not tracked, the same as the dunst mask.

  `inhibit_screensaver=0` because nothing on this session bus provides `org.freedesktop.ScreenSaver` (a cinnamon one is activatable and must not be), so the call would only log a failure; Steam and SDL games take a Wayland idle inhibitor themselves, which swayidle honours and the coffee cup shows. `igpu_power_threshold=-1` because the KF has no iGPU. The daemon re-reads the file every `reaper_freq` (5s), so edits need no restart, but a running client keeps the settings it registered with.

  **`pin_cores` is the one setting the right answer depends on the game, and it is `no`.** gamemode detects the 14700K's hybrid layout correctly (affinity 0-15, the eight P-cores with their SMT siblings, verified against `lscpu`). Measured on Cyberpunk's built-in benchmark, three runs per configuration at a mixed CPU/GPU-bound profile, 1% low fps: nothing 95.7, gamemode pinned 174.0, **gamemode unpinned 194.0**, a control run afterwards 100.1. Pinning cost 10% on the lows because the game has enough worker threads to use all 28; the E-cores are worth having. Measured on Factorio (`--benchmark`, flame_Sla 10k belt module, interleaved cycles on an idle machine), ms/update: nothing 6.86, `taskset` to P-cores under `powersave` 4.90, gamemode unpinned 4.17, gamemode pinned 3.90. Opposite sign, +6% from pinning, because Factorio's update is one serial thread that only wants the fastest core; under `powersave` the scheduler lets it land on E-cores often enough to cost 29% and triple the variance, and `performance` mostly cures that by itself. The config is global, so it follows the many-threaded case where the lows are felt; `taskset -c 0-15` in a launch option is the per-game override for a serial game.

  **The governor is where nearly all of gamemode's value is.** Cyberpunk's 1% low doubled (96 to 194) and its 0.1% low doubled (65 to 154) from the bundle with pinning off, with the GPU going from 88% to 97% busy and the CPU total *falling* from 50% to 33%: the GPU had been starved between frames by threads that were stalling. Factorio put the governor alone at 39%. Proton-GE (GE-Proton11-7, in `~/.steam/root/compatibilitytools.d/`) measured identical to Proton Experimental on Cyberpunk, so it stays installed for games that need its codecs or a fix and is not the default.

  **Two traps in benchmarking this.** A game the user has running under `gamemoderun` puts the whole machine in `performance` for the duration, so a "baseline" run at the same time is nothing of the kind: two sequential Factorio baselines disagreed by 8% for exactly this reason, and `journalctl --user -u gamemoded` (`Entering Game Mode` / `Leaving Game Mode`) is the check before trusting any number. And interleave configurations (A B C A B C) rather than running each as a block, so drift lands on all of them equally; the Cyberpunk sets were blocks and needed the control run afterwards to stand. Cyberpunk's benchmark is a fixed camera path, so `Left Shift+F2` at the start of the flythrough with `log_duration=60` logs the same segment every run; noise there is about 1% on the average and 5% on the 1% low over three runs. `~/.local/state/MangoHud/summarise.py` reads the CSVs.

  **MangoHud from Debian is the DFSG build with NVML stripped out**, so on this card the GPU rows read 0% / 0°C / 0 MHz, which is worse than no row. It is rebuilt locally with NVML (`0.8.4+dfsg-1+nvml1`, held: `apt-mark hold mangohud mangohud:i386 mangohudctl mangoplot`, the debs kept in `~/.local/share/mangohud-nvml/`). The recipe: `dpkg-source -x` on the Debian source (fetched from the pool with curl; there is no `deb-src` line for sid), upstream's `include/nvml.h` from the matching tag restored (**the CUDA 13 header does not work**, it already defines the `nvmlProcessInfo_v1_t` typedef that MangoHud's loader adds itself), `-Dwith_nvml=enabled` and `-Dwith_xnvctrl=disabled` in `debian/rules` with `libxnvctrl-dev` dropped from `Build-Depends` (its dev package is version-locked to the 615 driver held back here, and XNVCtrl is X11-only anyway), a `+nvml1` changelog entry, `dpkg-buildpackage -us -uc -b`. `mangohud` is `Multi-Arch: same`, so the i386 instance (32-bit games) must be the identical version with byte-identical shared files: it is built natively in an `i386/debian:sid` container on the rootless Docker (no emulation, a 32-bit userland on the 64-bit kernel) from a copy of the same tree, and `cmp` over the files both packages ship is the check before installing. Build-deps went in with `apt install --mark-auto` so `autoremove` takes them back out. NVML is `dlopen`ed from the driver's `libnvidia-ml.so.1` at runtime, so only the header is needed at build time.

  Three more things about MangoHud. **`MANGOHUD_CONFIG` replaces the config file rather than adding to it**, so a test that sets one option through the environment tests the default layout, not ours; `MANGOHUD_CONFIGFILE` pointing at a copy is how to test the real file plus a line. `cpu_power` can never work unprivileged (Intel RAPL's `energy_uj` is root-only since the Platypus fix) and the logger tries to initialise it regardless, so the `Failed to initialize CPU power data` lines are noise. And `no_display` is set: the layer is in every game's launch options all the time (its idle cost is a timestamp per frame), `Right Shift+F12` shows it and `Left Shift+F2` logs 60s to `~/.local/state/MangoHud/` whether it is shown or not, which is what makes a stutter answerable without relaunching. **The `GAMEMODE` line is not the daemon's state**: it is `lib_loaded("gamemode")` over the process's own `map_files`, checked once at startup, so it reads ON for a `gamemoderun` launch (the preloaded `libgamemodeauto`) and OFF for a client that registered over D-Bus, which is how Prism Launcher's checkbox does it; `gamemoded -s` is the truth, and the journal names the client pid.

  **ntsync** is `/etc/modules-load.d/ntsync.conf` (machine-local); the kernel gives `/dev/ntsync` mode 0666 itself, no udev rule needed. **Proton Experimental uses it whenever the device exists**, no launch option: the implementation is in `wineserver` (`/dev/ntsync`, `ntsync: up and running.`), which checks `PROTON_NO_NTSYNC` itself, so a grep of `ntdll.so` and the `proton` script finds nothing and wrongly concludes it is absent. Proton-GE is the same, with `WINENTSYNC=1` set in its script. MangoHud's `winesync` line is the confirmation. Measured on Cyberpunk with `PROTON_NO_NTSYNC=1` as the A/B: fsync 1% low 173.4 against ntsync 194.0, 0.1% low 131.0 against 153.6, frametime sd doubled, and **the CPU total at 57% against 38%** for the same frames, which is the mechanism: fsync emulates Windows waits with futexes and spinning, ntsync hands them to a kernel object. Against the expectation that ntsync is a wash versus fsync, it is not on this game.

  **HDR** works, for a game and for a film, through three pieces that each have to be in place. **The gate is the renderer**: wlroots' HDR (and its 10-bit output and `color_profile`) is Vulkan-only, and wlroots defaults to GLES2, so `.config/uwsm/env` exports `WLR_RENDERER=vulkan`, gated to demise because the laptop's Intel path is untested. Sway does not log which renderer it chose at the default log level and the loaded libraries do not tell either (both `libEGL_nvidia` and `libGLX_nvidia`, which is also the Vulkan ICD, are mapped under both), so **the renderer test is `swaymsg output DP-2 hdr on`**: refused on GLES2, and on Vulkan `drm_info` shows the connector at `Colorspace = BT2020_RGB` with an `HDR_OUTPUT_METADATA` blob, with VRR still enabled beside it. The G9's EDID carries the HDR static metadata block (PQ, BT.2020) with a declared max luminance of ~400 nits against the HDR1000 marketing, so the game's peak-brightness slider is set by eye against a highlight, not from either number. `.local/bin/hdr-run` turns HDR on for every output, runs its arguments, and turns it off on any exit; it is a script receiving `"$@"` and **not** a `sh -c` wrapper, because Steam expands `%command%` with each argument single-quoted (the game lives in `…/Cyberpunk 2077/`) and those quotes terminate a single-quoted `sh -c` string, so the launcher got a broken path and the trailing `hdr off` became stray arguments that never ran. Launch options are therefore `hdr-run env PROTON_ENABLE_WAYLAND=1 PROTON_ENABLE_HDR=1 gamemoderun mangohud %command%`, with `env` because the variables are arguments to a script rather than shell assignments.

  **HDR stays off at the desktop, and the reason is not what it looks like.** With `hdr on` the desktop looks the same, since wlroots maps SDR to a fixed reference white inside the PQ signal; what changes is every *capture* of it. Measured: `grim` reads the bar background as `(24, 24, 37)`, the theme's `mantle` exactly, with HDR off, and `(40, 40, 53)` with it on, because the capture is the PQ-encoded framebuffer read out as sRGB, so every dark tone is lifted. The same applies to `wf-recorder` and the screencast portal, so a screenshare with HDR on shows the other side a grey, washed-out desktop. Per-program is the shape: `hdr-run mpv film.mkv` for a film (mpv 0.41 needs nothing else: `gpu-next`, Vulkan and `target-colorspace-hint=auto` are its defaults on Wayland, and `.config/mpv/mpv.conf` only adds `hwdec=auto-safe` so a 4K HEVC decodes on NVDEC rather than in software). Browsers do not output HDR on Linux and the streaming services cap Linux at 1080p SDR anyway, so HDR film means local files.

  **Proton Experimental cannot do HDR**: its Wine ships only `winex11.so`, so every game under it is an XWayland client and X11 has no HDR. Proton-GE ships the Wayland driver (`PROTON_ENABLE_WAYLAND=1`) and `PROTON_ENABLE_HDR=1` sets `DXVK_HDR=1`, which is what makes Cyberpunk's HDR toggle appear. Under the Wayland driver the game is a native `xdg_shell` window with a locked pointer; the log line `MESA-EGL: egl: failed to create dri2 screen` for the NVIDIA device is Wine trying Mesa's EGL first and falling through, not a failure.

  **`seat * hide_cursor when-typing enable` breaks every locked-pointer game and is gone from the config.** In sway 1.12 every key press calls `cursor_notify_key_press()`, which with that setting calls `cursor_hide()`, which does `wlr_seat_pointer_notify_clear_focus()`; from then on relative motion and the button release go to no surface. The idle hide (`hide_cursor 5000`) guards against a held button (`cursor_get_timeout()` returns 0 while `pressed_button_count > 0`), the typing hide has no such check, and while a button is held sway is in `seatop_down`, which has no rebase handler, so nothing re-enters the surface until the button is released, at which point the release itself has already been lost. Symptom: hold any button, move (works), press any key, motion stops until the button is released, and the game never sees the release. Identical in Minecraft (XWayland) and Cyberpunk (native Wayland), which is what placed it in the compositor. The fix upstream would be the same guard in `cursor_notify_key_press()`.

  **Cyberpunk on this card at 5120x1440**, measured on the built-in benchmark, rendered rate with frame generation off: RT Ultra + DLSS Quality 56.8 avg / 47.3 1% low, which sits on the 48 Hz VRR floor; RT Lighting High + DLSS Balanced 71.0 / 55.4, which is the profile. Frame generation works under Proton (NVAPI initialises, the driver's `nvngx_dlssg.dll` loads, a `sl.dlssg` thread appears) and presents at 1.6x rather than 2x because generating costs GPU time on a GPU already at its cap: 108.3 avg / 85.5 1% low from that profile. MangoHud counts presented frames, so the only way to know whether FG is engaged is a run with it off. VKD3D-Proton's RT cost ran 25-30% above the Windows figures the estimates came from, which rules path tracing out here. "Throttling: power" on the overlay is the card at its 320 W limit with a steady clock and 67°C, the normal state of a GPU-bound profile and not a fault.

  **Adaptive sync** is on for every output. The G9 advertises 48-240 Hz in both its range-limits descriptor and an AMD FreeSync block; sway 1.12's `adaptive_sync` is unconditional (no fullscreen gate, unlike Hyprland's), and `drm_info` is the check that the NVIDIA driver committed it (`vrr_capable = 1` on the connector, `VRR_ENABLED = 1` on the CRTC), since `swaymsg` only reports what sway asked for. It is a connector property, not a modeset. Nothing is visible at the desktop when it works; the failure mode is brightness flicker on this VA panel in dark static content as the rate swings, and the fix for that is off, there is no tuning. A runtime `swaymsg output DP-2 adaptive_sync off|on` is the per-game escape for an engine whose frame limiter dislikes it. MangoHud cannot see VRR at all: it logs when frames are rendered, VRR changes when they are shown, so that one is judged by eye on the benchmark's slow pans.

- **Session services** (`.config/systemd/user/`): the shell runs under systemd, not as a sway `exec`. The sway config starts `sway-session.target`, which `BindsTo` + `PropagatesStopTo` `graphical-session.target` and so pulls in `quickshell.service` (`Restart=always`, `StartLimitBurst=5`), `swayidle.service` and `sway-outputs.service` plus the machine-local `poweralertd` and `wayland-pipewire-idle-inhibit` units already sitting in `graphical-session.target.wants/`. This keeps `swaymsg reload` and every theme switch out of the shell's lifecycle, and out of the DRM modeset path described in `.claude/sway-lockup-investigation.md`.

  The user manager never sources `~/.profile`, so the XDG base directories and `~/.local/bin` are declared in `.config/environment.d/10-xdg.conf` — without them `theme` and the `sway-*` scripts are unreachable from any user unit. `environment.d` rather than `Environment=` lines because it covers every unit at once, expands `${HOME}`/`${PATH}`, and applies on a plain `daemon-reload`. Files there merge by filename across all `environment.d` directories, so nix's unprefixed `nix-daemon.conf` sorts after `10-xdg.conf` and re-prepends its own paths. `quickshell.service` keeps only `QT_QPA_PLATFORM=wayland` and `QT_QPA_PLATFORMTHEME=kde`, which are about how the shell renders and used to be inherited from the `sway-run` launcher uwsm replaced.

  `wayland-pipewire-idle-inhibit.service` is tracked here too. Any unit added to this target needs `PartOf=graphical-session.target`, not just `WantedBy=` in `[Install]` — `WantedBy` starts it with the session but never stops it, and a `Restart=always` unit then spins against a dead compositor for the whole logout window.

  The sway side is one quoted `exec` that chains the environment import into the target start: `/etc/sway/config.d/50-systemd-user.conf` imports `SWAYSOCK` in a *separate* `exec`, and sway launches execs asynchronously, so the target can otherwise start before the socket is in the manager's environment. The quotes are load-bearing — unquoted, sway parses `&&` (or a `;`) as the start of a second command and logs `Unknown/invalid command`.

  `PropagatesStopTo` is load-bearing and easy to lose: `BindsTo=B` only stops A when B stops, never the reverse, so without it `systemctl --user stop sway-session.target` leaves `graphical-session.target` and every service under it running, and the teardown silently does nothing.

  `quickshell-lock.service` is tracked here too but has **no `[Install]` section**: it is started on demand by `lock`, never pulled in by the target. It is `PartOf=graphical-session.target` so it still dies with the session.

  `install` ends with `systemctl --user daemon-reload` and `systemctl --user enable quickshell.service`, guarded on `-d /run/systemd/system` so macOS skips it; symlinking a unit is not enough, `WantedBy=` only applies once enabled. Editing an existing unit still needs a `daemon-reload`.
- **Autostart** (`.config/autostart/`): apps are started by **XDG autostart**, not by a sway `exec` block. uwsm runs it through `wayland-session-xdg-autostart@sway.desktop.target`, and the `sway-run` launcher it replaced never did — so on the first uwsm login a pile of entries under `/etc/xdg/autostart` and `~/.config/autostart` fired for the very first time, several of them into things the bar had already replaced. That is the trap to remember here: **an autostart entry that has "always been fine" may simply never have run.**

  Anything the compositor does not itself need goes here rather than in `sway/config`, so systemd owns the lifecycle — a unit, its own log, a cgroup, and teardown with `graphical-session.target` instead of an orphaned child of the compositor. `sway/config` keeps only what is genuinely sway's: `sway-laptop-lid` and the one quoted `exec` that starts `sway-session.target`. swayidle moved out of it into a unit for the reason everything else did — it is now the single point of failure for every lock path, and an `exec_always` has no supervision at all.

  Three mechanisms, in order of preference. A **system entry that already exists** needs nothing — `nm-applet` is started by `/etc/xdg/autostart/nm-applet.desktop` (whose `NotShowIn=KDE;GNOME;` does not exclude `sway:wlroots`), so its sway `exec` line was pure duplication. A **new tracked entry** in `.config/autostart/` covers what ships none: `kdeconnect-indicator.desktop` (there is a system entry for the kdeconnect *daemon*, but not for the indicator) and `calibre.desktop`. And a **`Hidden=true` shadow** suppresses a system entry — a user file of the same name overrides it, `Hidden=true` means "treat as deleted", and the generator then writes no unit at all (confirmed: it reports `not-found`). `blueman.desktop` is the one such shadow, and the reason it is a shadow rather than an `apt remove` is that blueman-applet is the BlueZ pairing agent Quickshell does not provide.

  Two things measured rather than assumed. **A duplicate start is silent, not an error**: while both paths were live, `app-1password@autostart.service` ran, found sway's instance, logged `1Password is already running, closing`, and exited `Result=success` — 517ms of CPU and an 88MB peak with nothing to show for it, and a unit sitting `inactive` that looks like it never ran. And **ordering does not matter for tray apps**, unlike `poweralertd`: an SNI item owns its own bus name and the watcher picks it up whenever it appears, so an applet starting before quickshell is fine.

  `poweralertd.service.d/ignore-startup-events.conf` is the counter-example, and the one unit here whose startup ordering mattered at all. poweralertd sends a state-update notification the instant it starts and exits 1 if the call fails, so under uwsm it and quickshell race off `graphical-session.target` — measured at one login: poweralertd started at `22:13:09.009`, failed three times in 0.67s, and hit the stock 5-in-10s `StartLimitBurst` at `22:13:09.676`, while quickshell only started at `22:13:11.182`.

  The fix is **`poweralertd -s`**, which ignores the events at startup, so there is no notification to fail and the daemon need not exist yet. Measured with quickshell stopped: bare `poweralertd` exits 1 immediately, `poweralertd -s` runs indefinitely. Later events still notify. The lesson generalises past this unit — **read the daemon's own options before reaching for unit ordering**, because three ordering fixes were tried first, each looking right and each worse than the last:

  1. **`After=quickshell.service` deadlocks at parse time.** poweralertd carries `Requires=graphical-session.target` and quickshell is ordered `After=` that same target, so the edge closes a cycle; systemd breaks a cycle by deleting a job, and it picked poweralertd's own `start`. The unit then never ran, never failed, and never appeared in `--state=failed` — worse than the race, since the boot looks clean and the battery alerts are simply gone.
  2. **A retry budget alone does not work at any size.** `RestartSec` is *not honoured while the session is coming up*, where systemd logs `Scheduled restart job immediately on client request` and restarts with no delay, so 20 attempts burned in 0.35s against a quickshell that started 0.9s later. It is invisible from a hand-started unit, where `RestartSec` applies normally — so verify a startup race across a real reboot, never by starting the unit by hand.
  3. **`gdbus wait` as an `ExecStartPre` deadlocks the whole session**, and is much the worst of the three. `ExecStartPre` blocks the start *job*; `graphical-session.target` is ordered after poweralertd and quickshell is ordered after that target, so poweralertd waited 30s for a quickshell that could not start until poweralertd finished, timed out, restarted immediately, and waited again — ten minutes with no bar, no wallpaper and no notification daemon. Recovery is `systemctl --user stop poweralertd.service`, which releases the target at once. The same wait moved *inside* `ExecStart` is safe, because a `Type=simple` unit is active as soon as it forks — but with `-s` none of it is needed.

  `kde-baloo.service` is **masked** (`systemctl --user mask kde-baloo.service`), machine-local like the dunst mask rather than tracked. Debian's preset enables it `WantedBy=graphical-session.target`, but `baloo_file` exits 0 immediately with "Baloo File Indexing has been disabled", so it does nothing except get re-activated by whatever KIO worker asks next — and those activations occasionally bunch up enough to trip the stock 5-in-10s start limit and report a failed unit. It is **not** a uwsm regression, which is worth knowing before chasing it: it started 4, 14 and 4 times on the three boots *before* the migration and simply never crossed the limit there.

  `~/.config/autostart/1password.desktop` is deliberately **not** tracked: 1Password writes it itself and it is 0600. The `polkit-kde-authentication-agent-1.desktop` symlink there is inert — it carries `OnlyShowIn=KDE;` against uwsm's `XDG_CURRENT_DESKTOP=sway:wlroots`, so no unit is generated and nothing contends with Quickshell's own polkit agent. Worth knowing, because a second agent would be hard to diagnose.

- **Sway**: starts under **uwsm** as a systemd user unit — `wayland-wm@sway.desktop.service`, `ExecStart=/usr/bin/uwsm aux exec -- %I`, where the instance is the Desktop Entry ID (`sway.desktop`) and not the bare binary. Nothing in this repo launches the compositor: the greeter runs `uwsm start -- sway.desktop` (see Login), and from a VT `uwsm start default` does the same by hand, resolving through `~/.config/uwsm/default-id`. Both machines are on this path.

  It replaced a hand-written `/usr/local/bin/sway-run` launcher, which exported the Wayland variables itself, sourced a `.config/sway/profile` that no longer exists, and ran sway **without** `exec` so it could `systemctl --user stop sway-session.target` on the way out. Both are gone from disk now that a boot has come up clean on uwsm, and nothing references either. The trap while the two paths coexisted is worth keeping in mind when reading older notes: `sway/profile` was sourced by `sway-run` and by nothing else, so `QT_QPA_PLATFORMTHEME=kde` living in it was simply absent from the whole uwsm session, which is what left Dolphin unthemed.

  Under uwsm the session environment comes from `.config/uwsm/env` (tracked), which uwsm sources from `/usr/libexec/uwsm/prepare-env.sh` on the way up — a plain `. "$file"` behind an `-f`/`-r` test, so the symlink `install` leaves is sourced normally. It also reads a per-compositor `env-<desktop>` beside it and an `env.d/` directory, neither of which is used.

  **`~/.profile` does reach the uwsm session, and that is not obvious.** `prepare-env.sh` sources `/etc/profile` and `~/.profile` itself, then uwsm diffs the environment and pushes the result into the systemd user manager with `SetEnvironment` — so profile-only variables (`MBOX`, `NVM_DIR`, `DOCKER_CONFIG`, `EDITOR`, …) land in sway, in everything sway `exec`s, **and** in every user unit, quickshell included. That is strictly more than `sway-run` gave, where the user manager saw none of it — which is the whole reason `10-xdg.conf` exists. Do not read `environment.d`'s comment as meaning the graphical session lacks the profile; it means the *manager* does not source it, and under uwsm something else does.

  It is conditional, but **not on there being a login shell** — an earlier version of this note said it was, and that was wrong. `__LOAD_PROFILE__` comes from `have_env_login`, which is simply whether `uwsm start` itself ran and left a non-empty environment behind: `save_env("env_login")` dumps `os.environ` just before uwsm replaces itself with the signal handler, and `prepare-env` reads it back (`/usr/share/uwsm/modules/uwsm/main.py`, around lines 2652 and 4836). So a greeter that execs `uwsm start` directly still loads the profile, which is what makes the gtkgreet flow below safe; what *would* lose it is starting the compositor unit without going through `uwsm start` at all. Confirm from the journal rather than assuming — the preloader prints `Loading shell profile.` when it did, under the `uwsm_env-preloader` identifier.

  So `environment.d` is the floor, not the main path: it carries the XDG base directories the units would lose if the greeter ever started the compositor without going through `uwsm start`, plus session-wide non-shell settings like `QT_QPA_PLATFORMTHEME` that are not Wayland setup and so do not belong in `uwsm/env`. Everything else — tool configuration, `PATH`, editors — stays in `~/.profile` and already arrives; duplicating it into `environment.d` only creates two places to drift. Genuinely Wayland-session setup goes in `.config/uwsm/env`.

  One measurement to save repeating: a directory missing from the session's `PATH` is usually not a bug in any of this. `~/.profile` guards each entry with `[ -d ]` and runs once at login, so a toolchain installed mid-session is absent until the next one — `~/.local/share/cargo/bin`, created two hours after login, read exactly like a broken export and was not.

  uwsm sets `XDG_SESSION_TYPE`, `XDG_SESSION_DESKTOP`, `XDG_CURRENT_DESKTOP` (as `sway:wlroots`, not bare `sway`) and the XDG base directories itself, so `.config/uwsm/env` carries only what it does not: `MOZ_ENABLE_WAYLAND`, `QT_QPA_PLATFORM`, `SDL_VIDEODRIVER`, `_JAVA_AWT_WM_NONREPARENTING` and the cursor theme. Two variables `sway-run` exports are deliberately **not** carried over. `ELECTRON_OZONE_PLATFORM_HINT=auto` is unnecessary — measured, every Electron and Chromium app in the session (Chrome, Claude, Slack, Spotify) is already a native Wayland client without it, Claude with no flags at all. `ADW_DISABLE_PORTAL=1` is actively wrong here: it stops libadwaita reading the portal, and the portal's `org.freedesktop.appearance` is exactly how `theme`'s dark/light switch reaches GTK4 and Electron apps (see Themes).

  uwsm also owns the teardown that `sway-run`'s missing `exec` was for — `wayland-wm@sway.desktop.service` propagates its stop to `graphical-session.target` — so the compositor cannot outlive the session either way.

- **Login** (`system/greetd/`, `system/install-greetd`): login goes through **greetd** on VT7, which runs a bare sway hosting **gtkgreet**; picking a session there starts `uwsm start -- sway.desktop`, which is byte-for-byte what `uwsm start default` resolved to when it was typed by hand (`~/.config/uwsm/default-id` holds `sway.desktop`). Both machines are on it, and neither autologins — the laptop's greetd used to carry an `[initial_session]` running `sway-run`, and dropping it is what put the two on the same config.

  `system/` is the third repo root outside the four paths `install` mirrors, after `themes/` and `claude/`, and for a harder reason than either: these files are root-owned and live in `/etc`, so they are **copied, not linked** — `sudo ./system/install-greetd` after any edit, or the change does nothing. That script is also where the non-file steps live (the `_greetd` group hedge, `sway --validate` on the greeter config, `systemctl enable greetd`), so it is the whole procedure rather than a `cp` wrapper.

  **`sway --validate` brings the backend up before it parses the config**, which makes it near-useless where you most want it — under `sudo`, from a text console. It aborts outright on the unset `XDG_RUNTIME_DIR` that sudo does not pass through, and faking that one is worse than useless: it then spends ten seconds failing to open a DRM session and exits 1 for a good config and a bad one alike, a check that can never pass and that reads as "my config is broken". `WLR_BACKENDS=headless` plus a throwaway `XDG_RUNTIME_DIR` skips DRM and seat management entirely and leaves just the parse — measured at exit 0 on a good config and 1 with a real error message on a bad one, in 0.07s, with no display and no session. Note also that a typo'd *identifier* is not a parse error: `input typ:keyboard { … }` validates clean, because sway reads it as a device identifier that happens to match nothing.

  **gtkgreet does not read `wayland-sessions` desktop entries** — it reads `/etc/greetd/environments`, a newline-separated list of raw command lines. That is a simplification worth knowing, because the obvious design (a `/usr/local/share/wayland-sessions/sway-uwsm.desktop` wrapper, per uwsm's own README) buys nothing here and would leave the packaged `sway.desktop` sitting next to it in every picker as a session that silently skips uwsm. The second line in `environments` is `zsh -lc sway`, a deliberate rescue: a login shell so `~/.profile` still runs, since with uwsm out of the picture nothing else would source it.

  `source_profile = false` in `config.toml` is deliberate and is the one setting to not "fix". greetd's default is `true`, and uwsm sources `/etc/profile` and `~/.profile` itself — but `~/.profile` *prepends* to `PATH` with no re-entry guard, so letting both do it duplicates every entry. Turning it off leaves the greeter with **no `PATH` at all** — measured off a real greeter, the environment greetd hands its child contains none, because `/etc/environment` is empty on this machine and `common-session` carries no `pam_env`. That is survivable rather than fine: `sh(1)` falls back to `confstr(_CS_PATH)` for the lookups on the `command` line, which is how `env` finds `sway`. Anything the greeter runs that does its **own** `PATH` search instead of leaving it to `sh` must use an absolute path — `strace` is one such, and a diagnostic wrapper reading `strace … gtkgreet` died with `Cannot find executable 'gtkgreet'`, exec'd nothing, and looped the greeter into greetd's start limit until VT7 was a bare cursor.

  The greeter's sway config **must not** `include /etc/sway/config.d/*` the way the packaged `/etc/greetd/sway-config` did. The only drop-in there is `50-systemd-user.conf`, which imports the environment into the systemd *user* manager — as `_greetd` that starts a user manager for the greeter account with nothing to manage. It carries an `output` line keyed by sway **identifier** (not connector — see the output section) matching the mode `sway-outputs` will pick, so login → session is not a second modeset; on any other machine the identifier matches nothing and the line is inert.

  That last reasoning is half wrong, and it cost 30–60 seconds at every login until it was measured. **`pam_systemd` starts `user@105.service` for `_greetd` regardless** — it is in `common-session`, and `/run/user/105` comes up holding a session bus, pipewire, gnupg, keyring and gcr, for a login screen. Skipping the drop-in therefore does not avoid a user manager; it only leaves that manager with no `WAYLAND_DISPLAY`. gtkgreet calls `org.freedesktop.host.portal.Registry.Register` **synchronously inside `gtk_init`**, so until it returns nothing is drawn at all — not the wallpaper, not the clock, not the entry — and the screen sits on sway's solid background with a live cursor, looking like a healthy session with a missing greeter. That call activates `org.freedesktop.portal.Desktop`, which picks a backend by matching `XDG_CURRENT_DESKTOP` (unset here) against the `UseIn=` lines in `/usr/share/xdg-desktop-portal/portals/*.portal`, matches nothing, and falls back to `gtk.portal`. `xdg-desktop-portal-gtk.service` is `Type=dbus`, so systemd waits for it to claim its `BusName` — but it is itself a GTK app started by that display-less user manager, so it never does, and dbus-daemon gives up one `service_start_timeout` (25s) later. xdg-desktop-portal then retries, which is why this presented as "30 to 60 seconds" rather than a constant: attempts were captured at 25s, 50s and 75s.

  The fix is `DBUS_SESSION_BUS_ADDRESS=unix:path=/nonexistent` on greetd's `command`, taking the greeter's session bus away on purpose — **25.14s to first paint with the bus, 0.07s without**. It costs the greeter nothing, because gtkgreet reaches greetd over `GREETD_SOCK` and wants no session bus, no accessibility bridge, no gvfs and no portals; verified with the bus gone that the stylesheet, the wallpaper and the `/etc/greetd/environments` session list all still render. Suppressing the portal from the *client* side does **not** work, and the numbers are kept in `config.toml` so nobody retries them: `GTK_USE_PORTAL=0` measures 25.08s, adding `NO_AT_BRIDGE=1` and `GIO_USE_VFS=local` 25.10s, and `XDG_CURRENT_DESKTOP=sway` 25.10s (`wlr.portal` advertises only Screenshot and ScreenCast, so the lookup still falls back to the gtk backend). None of them gate that `Register` call.

  Two things about diagnosing this class of bug. greetd's journal carries **no sway or gtkgreet output at all**, so a misbehaving greeter is invisible until `command` is given a `> /tmp/…log 2>&1` redirect — greetd 0.10.3 does run the line through `sh(1)`, so the redirect works. And instrumenting the login path is the wrong way round, since a wrong wrapper leaves an unbootable greeter: `systemctl start user@105.service` plus `setpriv --reuid=105 --regid=114` runs gtkgreet as `_greetd` against a real systemd-activated session bus inside a headless nested sway, entirely outside the login path, which is where every number above came from. A hand-started `dbus-daemon` is **not** equivalent — the portal and a11y service files carry `SystemdService=`, so the real bus delegates activation to systemd while a private one exec's the binary directly, a different code path that does not reproduce the hang. `dbus-monitor` on that bus is what named the call; strace alone only showed an anonymous futex timeout.

  Two things about `_greetd` that look like they should break and do not. It reaches the GPU by **logind ACL**, not group membership: `getfacl /dev/dri/card0` shows `user:<active user>:rw-` granted to whoever holds the active seat0 session, and greetd's greeter is one. `install-greetd` adds `_greetd` to `video` and `render` anyway as a hedge for the window before the session goes active. And it cannot read *anything* under `~` — `$HOME` is 0700 — which is why the wallpaper is copied to `/etc/greetd/wallpaper.png` and why `sway-config` sets `GTK_THEME=Adwaita:dark` rather than relying on the generated dotfiles GTK theme under `~/.local/share/themes`.

  `gtkgreet.css` is **hand-written and static** — it is not in `theme`'s `TARGETS` and `theme set` does not touch it. That is a choice, not an oversight: the generated files all land under `~/.config`, and reaching `/etc` would mean `theme` needing root, which it has never needed. The palette in it is Catppuccin Mocha, and it tracks nothing — the install-time default is macchiato, and changing themes leaves the login screen where it is. gtkgreet's own widget ids are `#body`, `#clock`, `#input-field` and `#command-selector` (read off the binary, they are not documented); everything else in the file is plain GTK3, and a stylesheet passed with `--style` layers *over* the GTK theme rather than replacing it.

  The way back in if the greeter ever fails is `Ctrl+Alt+F2`: `greetd.service` takes VT7 alone (`Conflicts=getty@tty7.service`) and tty1–tty6 keep their gettys. greetd gives up after 5 restarts in 30s, so a broken greeter leaves VT7 blank rather than looping forever. Test a change by switching to a getty **first** and restarting greetd from there — restarting it kills the graphical session either way, and from a getty you are already somewhere useful when it does not come back.

- **NAS mounts** (`system/mounts/`, `system/install-mounts`): the two Synology shares — `//beedle/media` and `//beedle/backup` — are **CIFS automounts**, mounted on first access at `~/beedle/{media,backup}` and unmounted after 10 minutes idle. Like `system/greetd/` these are root-owned files in `/etc`, so they are **copied, not linked**: `sudo ./system/install-mounts` after any edit, or the change does nothing. That script also owns the non-file steps — creating `/etc/cifs/beedle.cred`, `daemon-reload`, and `enable --now` on the two `.automount` units.

  They replaced unprivileged **sshfs** `.mount` units in `~/.config/systemd/user`, which were `WantedBy=default.target` and so tried to mount at user-manager start — before wifi associates and before 1Password's agent socket exists. A `.mount` unit that fails once is failed for the whole session with no retry, which is why every login ended with two failed units. **That is structural, not incidental: mounting a network filesystem at login is the bug.** An `.automount` unit nobody touches cannot fail, and one that is touched retries on the next access.

  Three things the units settle. A `.mount` unit's name must be the escaped form of its `Where=` or systemd refuses it at `daemon-reload` with a mismatch, so `install-mounts` checks that with `systemd-escape --path --suffix=` first, where the message can name the offending file. `x-systemd.idle-timeout` is an **fstab** option and is silently ignored in a native unit — the equivalent is `TimeoutIdleSec` in the `.automount`'s `[Automount]` section. And the mount points are deliberately not created by the installer: creating them under `sudo` leaves them root-owned, and autofs will not adopt a directory the accessing user cannot traverse.

  CIFS rather than NFS or sshfs, for a laptop that sleeps and roams: `uid=1000,gid=1000` maps ownership client-side, so the NAS's `uid 1026` never has to line up with the local one; `soft` is mount.cifs's default, so a mount attempt against an absent NAS fails instead of hanging; and it reconnects across suspend where NFS wedges. The cost is a password on disk — `/etc/cifs/beedle.cred`, 0600 under `/etc/cifs` 0700, **never in the repo**, written as a `CHANGEME` template on first install so a missing credential fails with an auth error rather than a missing-file one. `actimeo=30` is what makes browsing a large library bearable; `mfsymlinks` is for the backup share, whose rsync `--link-dest` tree carries a `latest` symlink.

  The one thing to know about putting an automount inside `$HOME`: autofs triggers on **stat of the mount point**, not just on entry, so `ls -l ~` pokes the NAS, and an `rg`/`fd` rooted at `$HOME` will descend into the whole media library. That was equally true of the sshfs mounts it replaces, and the idle timeout bounds it. Mounting at `/mnt/beedle/*` with symlinks from `~/beedle/*` is the way out if it ever bites — stat'ing a symlink does not trigger.

  **Diagnosing this class of failure: the reset happens before the SSH banner.** sshfs reports a failure to reach the NAS as `read: Connection reset by peer`, which reads like an authentication problem and is not one. The discriminator is a raw socket that connects and *sends nothing*: if the server closes with zero bytes before the client has spoken, nothing about keys, agents or usernames is involved. Measured that way, this laptop got a bare FIN while `hestu` on the same LAN got a banner and a completed pubkey login **using this laptop's own agent over `ProxyJump`** — so same client, same key, same instant, differing only in source IP. The cause was DSM's **Auto Block** list (Control Panel → Security → Protection), and its signature is exactly this: DSM 7's sshd checks the block DB right after `accept()` and closes without a banner, while the web UI on 5001 keeps serving pages, because auto-block gates *logins* and not page fetches. So "SSH is refused but DSM answers" is evidence *for* an auto-block, not against it. `/etc/hosts.{allow,deny}` stay stock and empty — the list is in the root-only `/etc/synoautoblock.db`, whose mtime is readable and did fall inside the failure window.

  **What earns the block is `Host *  IdentityAgent`.** With every key in the 1Password agent and no `IdentitiesOnly`, ssh offers all of them to every host, and each offer is a *failed login* the NAS counts. `beedle-back` was the worst case: six agent keys ahead of its own `IdentityFile`, against sshd's default `MaxAuthTries` of 6, which never reaches the right key and reports `Too many authentication failures`. `~/.ssh/config` (untracked — `.ssh` is not one of the four mirrored roots) now pins `IdentitiesOnly yes` plus a single `IdentityFile` per NAS host; pointing it at a **`.pub`** file selects one identity out of the agent without putting a private key on disk. Verified by counting `Offering public key` lines: three before, one after. Note that under `-J`/`ProxyJump` the jump host's own offers interleave into the same `-v` stream, so count with the proxy quieted (`-o 'ProxyCommand=ssh -q -W %h:%p <jump>'`) or the fix looks like it did nothing.

- **Backup** (`.local/bin/backup`, `.config/systemd/user/backup-{daily,weekly,yearly}.{service,timer}`): an rsync-over-ssh snapshot of `$HOME` to `backup@beedle:/volume1/backup/impa/amcoder`, rotated `--link-dest` style against `latest`. It runs as **systemd timers**, having previously run under a user-level **anacron** (`@hourly` in the user crontab, jobs in `~/.anacron/etc/anacrontab`, now commented out with a pointer).

  The move off anacron is not cosmetic: anacron mails its output, and **mail on this machine is broken**, so the job failed silently for eighteen months. `sendmail.service` is `disabled; preset: enabled` with nothing listening on 127.0.0.1:25, and ~4000 messages sit in `/var/spool/mqueue-client` as `Deferred: Connection refused by [127.0.0.1]`. The last delivery into `/var/mail/amcoder` was 2026-06-13, days after the sendmail unit file was replaced on 2026-06-09. **So the mailbox is not a complete record of anything** — it held 334 anacron failures and zero successes, but stopped in May 2026 until the queue was flushed; it now runs to 2026-09-04. Ground truth for whether a backup ran is the NAS: the `latest` symlink and the `daily.N` mtimes, which showed the last success was 2026-04-17 and only three in the preceding fourteen months. Anacron's own spool timestamps prove nothing either — it records the date whether the job succeeded or failed.

  The failures show **one root cause producing two symptoms in a cycle**, and the mail is what dates it. Through Jan 2026 it was `kex_exchange_identification: read: Connection reset by peer`, the DSM auto-block (see NAS mounts). From Jan 2026 it was `Too many authentication failures` — the same `Host *  IdentityAgent` problem wearing a different hat: six agent keys offered ahead of `beedle-back`'s own `IdentityFile`, against `MaxAuthTries 6`, so ssh never reached the right key. The changeover is when the keys moved into 1Password. From Jul 2026 the two **interleave in the same months** (Jul: 16 blocked / 17 auth, Aug: 25 / 10), which is the loop closing: six offers a run accumulate failed logins, those trip the auto-block, the block produces pre-banner resets until it lapses, and it starts over. That interleaving is why the block was never continuous — a successful sshfs mount on 2026-08-23 sits in the middle of it — and it is what makes "the key offers earned the block" evidenced rather than merely plausible. `IdentitiesOnly` cuts the loop at its source.

  Three things about the units. `OnFailure=backup-failed@%n.service` sends a desktop notification through quickshell's notification daemon, and the handler must interpolate **`%i`, never `%I`** — `%n` is inserted unescaped, so unescaping it again turns `backup-daily.service` into `backup/daily.service` and hands you a `journalctl` line that does not work. **A NAS that is not on this network is not a failure**, so an `ExecCondition` probes `beedle:22` first; it has to normalise the probe to exit 1, because ExecCondition treats 1–254 as *skip* and 255 as *failure*, and 255 is exactly what ssh returns for a connection error — hence `nc -z` rather than `ssh true`. And `LogRateLimitIntervalSec=0` is set because `rsync -v` is a line per transferred file, which on a first run is enough to trip journald's rate limit and drop the very error the unit exists to report; for the same reason the script's rsync flags lost `-P` (progress, which had no consumer once output stopped going to mail) while keeping `--partial`.

  `Persistent=true` gives the catch-up-after-downtime behaviour anacron provided — which also means **enabling a timer with `--now` fires an immediate catch-up run**, so do not do it while a backup is already in flight.

  **A non-zero rsync exit discards the whole backup**, and that is the second bug behind the eighteen-month gap — independent of ssh, and one that would have kept failing every night after the auth fix. The script `exit`s on any non-zero code, so the rotation never runs: the temp directory is never renamed to `daily.0` and `latest` is never moved. Measured on the first repaired run: rsync sent 8.62G of 189G (21.91x speedup off `--link-dest`) and returned **23** — partial transfer — because of exactly 32 files under `projects/jbt/jbt-db/db-data/`, owned by uid 10001 inside a container and mode `rw-r-----`, which `amcoder` cannot read. A 99.99%-complete backup was thrown away. That is also what left six `daily-tmp-2025-02-22T*` directories on the NAS. The 86G `db-data` tree is now excluded — raw files of a live database are not a consistent snapshot anyway — and **code 24 is tolerated** (source files vanished mid-transfer, routine on a live `$HOME`) while 23 deliberately still fails, so a *new* unreadable path is loud rather than silent.

  `fumon` — uwsm's "failed units monitor", running as `fumon.service` — already notifies on any user unit that fails, which is how the failed sshfs mounts were visible at all. It is *why* moving the backup onto systemd fixes the reporting even before `OnFailure`: under anacron the job was not a unit, so nothing watched it. The `backup-failed@` handler is kept anyway because it names the unit and the `journalctl` line to run, where fumon reports only that something failed.

  **`backup_exclude` is a deny-list, and the failure mode of a deny-list is silence** — a new app drops a cache somewhere and it is backed up until somebody notices. Two things address that, and inverting to an allow-list is deliberately not one of them: it trades "backed up some junk" for "silently did not back up your data", which for a backup is the worse failure.

  The first is **writing patterns by class rather than by path**. The list used to be path-specific (`projects/*/bin/`, `.config/Slack`), which matches exactly one location at exactly one depth — a nested repo's `target/` was invisible to it. Depth-independent patterns (`**/target/debug/`, `**/Library/`, `**/.venv/`, `**/obj/`) catch new instances anywhere without anyone noticing them. Measured over a real dry-run: 90.6G in 327,896 files before, **70.2G in 158,967 files after**. The file count matters as much as the bytes, because `--link-dest` carries every inode into every snapshot.

  The second is `.local/bin/backup-audit` on a weekly timer — an `rsync -an` dry-run through the real exclude file, aggregated two path components deep, diffed against the previous run's baseline in `$XDG_STATE_HOME/backup-audit/baseline.tsv`. It notifies through quickshell when a directory arrives, or grows, past `BACKUP_AUDIT_THRESHOLD` (1G). It reports the *delta*, not the standing list, or it would restate the same large directories every week and be ignored. `rsync -F` per-directory `.rsync-filter` files are the escape hatch for one-off junk that needs no central edit.

  Two things about the exclude file's syntax. **`+ ` lines are includes and order decides**, first match wins, so carving `.local/share/keyrings` (gnome-keyring, 76K, unrecoverable) out of the blanket `.local/` exclude needs the parent directories included first and an explicit `- /.local/share/*` after — five rules for one carve-out, and worth verifying by dry-run rather than by reading. And **a pattern with no interior slash matches at any depth**: the old `.local/` line was also excluding `~/.dotfiles/.local/`, so the dotfiles backup was silently missing its own vendored fonts and adw-gtk3 theme. Anchoring it as `- /.local/*` is what fixed that, and it is the same trap in reverse from the one the class patterns exploit.

  One latent bug left alone: the `if [ "$?" = 0 ]` after the rsync error check tests the exit status of the preceding `if`, not rsync, so it is always true and the `else` branch renaming a stalled temp directory to `-failed-` is unreachable. Harmless — the earlier `exit $code` handles a real rsync failure — but it is why six `daily-tmp-2025-02-22T*` directories from a stalled run are still on the NAS with nothing to clean them up.

  **The key's authority is restricted on the NAS, not only on this end.** `backup@beedle`'s `authorized_keys` entry carries `restrict,from="192.168.42.0/23"`, which turns off pty allocation, port forwarding, agent forwarding and X11 while still permitting command execution — all the script needs, since `ssh host "cmd"` and rsync never ask for a pty. Verified on fresh connections with multiplexing disabled so each exercised real pubkey auth: rsync transferred, `touch`/`mv`/`ln -s`/`rm -rf` all ran, `tty` reported `not a tty`, a remote forward was refused outright, and `SSH_AUTH_SOCK` came back empty on the far side. The previous unrestricted line is kept at `~/.ssh/authorized_keys.bak` on beedle. Hold a `ControlMaster` open while editing that file — it survives a broken key and is the difference between a mistake being a retry and being a trip to the DSM web UI.

  **`command=` is ruled out rather than overlooked**, which is worth knowing because it is the usual answer for an unattended rsync key. `backup:39-57` runs `rm -rf`, `mv`, `ln -s` and `touch` on the far side, so the key needs arbitrary remote command execution and cannot be pinned to a forced command without moving the whole rotation server-side. Upstream `rrsync` would not run there in any case — it is perl, and beedle has `bash`, `sh` and `python3` but no perl.

  **The `from=` netmask is a /23, not a /24.** The LAN is `192.168.42.0/23` and hosts land in both halves — beedle is 192.168.42.2 while demise is 192.168.43.36 and impa 192.168.43.29 — so the obvious `192.168.42.0/24` would have locked both clients out of their own backups. Take a host's prefix from `ip -4 -o addr show scope global` rather than inferring it from the NAS's address.

  **`backup` is a member of `administrators`, deliberately.** DSM 7 permits SSH login only to that group and offers no per-user toggle for it — SSH is not one of the per-user "Applications", that list being AFP, DSM, FTP, File Station, SFTP, SMB, Universal Search and rsync. The membership is compensated by per-user rules, which beat the group's Allow (DSM resolves conflicts as NA > RW > RO for shares, Deny > Allow for applications): Read/Write on `backup` and `homes` only, No Access on the other eight, rsync allowed and everything else denied including DSM itself, and no passwordless sudo. The application denials are orthogonal to shell access — SFTP is denied and `ssh beedle-back 'cmd'` works fine, which is what the whole arrangement runs on. Do not "fix" the group membership; removing it locks the backup out.

  **What no key restriction can do is stop the key deleting backups, because deleting old snapshots is the job.** The `backup` user can write to every machine's tree under `/volume1/backup` — `demise`, `impa`, `home-assistant`, `ctr-x1` and the `mipha.sparsebundle` Time Machine bundle — so a stolen plaintext key reaches all of them. The control for that is **immutable Btrfs snapshots** of the `backup` share, from DSM's Snapshot Replication package: scheduled daily, timed clear of both machines' timers (`OnCalendar=daily` with `RandomizedDelaySec=15m`, so runs start 00:00-00:15), with a retention policy and a WORM lock the NAS enforces against everyone, a DSM administrator included. Splitting the key per machine behind a forced command would confine each client to its own subdirectory and is the remaining unimplemented option, but it is second in value to the snapshots, which also cover a client destroying its *own* backups. Note the snapshots pin extents the rotation has deleted, so space is not reclaimed until they expire — noise against ~70G of data and 5.4T free, but it is the mechanism to remember if the volume tightens.

- **Backup indicator and browser** (`.local/bin/backup-record`, `.local/bin/backup-browse`, `.local/bin/backup-browser`, `services/BackupService.qml`, `modules/bar/Backup.qml`, `modules/backup/`, `backups.qml`): a clock-running-backwards icon in the right section between the theme and insomnia items, blue and pulsing while a backup runs, red when the last run failed, yellow when nothing has succeeded for 48 hours. Its `BarPopup` shows what is running and for how long, how the last run ended, when the last success was and what rsync moved, and when the next timer fires, with "Back up now" / "Stop" and "Browse…"; `quickshell ipc call backup toggle|start|browse` reaches the same three.

  **The units record their own state, so the shell watches one file and talks to systemd for nothing.** Each `backup-*.service` carries `ExecStartPre=backup-record start <interval>` and `ExecStopPost=backup-record finish <interval>`, which keep `$XDG_STATE_HOME/backup/status.json` (`state`, `current`, `last`, `lastSuccess`). `ExecStopPost` runs on **every** outcome, measured with transient units: `$SERVICE_RESULT` reads `success`, `exit-code`, `exec-condition` (the NAS probe skipped it, and there was no `ExecStartPre` run) and `timeout` (with `EXIT_STATUS=TERM`), so `finish` is the one place a run's fate is decided. The rsync figures come from a `--log-file` the script now writes with `--log-file-format=''`, which is measured to carry only the `--stats` summary and none of the per-file lines; the per-file listing still goes to the journal. systemd's unit signals were considered and rejected: a passive `busctl monitor` did receive `PropertiesChanged` for the units, but only because something else on the bus (uwsm's `fumon`) holds a `Subscribe()`, which is not a thing to depend on.

  A stop from the panel is `systemctl --user stop`, and the script's TERM trap removes the half-built `*-tmp-*` directory from the NAS on the way out (verified: none left behind). It exits 143, which the units list in `SuccessExitStatus` so a deliberate stop does not fire `OnFailure`'s notification; `backup-record` turns `success` + `143` into `stopped`, which the panel reports and the icon does not colour. Note that a manual run rotates `daily.N` like any other, so each "Back up now" costs a daily slot.

  Two things about `FileView` here, both measured. **A watch on a path that does not exist never fires when the file appears** -- the shell started before the first record showed "No backup recorded yet" through a whole run -- so a failed load is retried on a 30s timer until the file exists. And **the watch survives `os.replace`**: `backup-record` writes through a temp file and rename, and the panel followed every write. `BackupService` also checks a `running` record against `systemctl is-active` on load and every 30s, since a power cut mid-backup leaves a record nobody finishes.

  The browser is **its own quickshell process**, `backups.qml` over a `FloatingWindow` (app_id `org.quickshell`, floated by a sway rule on its title), started by `backup-browser`: the panel launches it through `I3.dispatch("exec …")` so it lands in sway's scope, and a second launch first tries `quickshell -p backups.qml ipc call browser raise`, which exits 255 when no instance is up. Closing the window calls `Qt.quit()`. It is a window rather than an overlay because it is a working surface, and a second process rather than a surface in the shell because everything it reads is on a CIFS automount. Every read goes through `backup-browse` in a `Process` (`snapshots`, `list <snapshot> <path>`, `restore <snapshot> <path> replace|keep`), and reads are serialised rather than restarted: killing an in-flight `Process` lets its `exited` land *after* the replacement started and overwrite the newer listing. The two `ListView`s carry `keyNavigationEnabled: false` and the content item takes `forceActiveFocus()` on completion, because a `ListView` is a focus scope and, holding focus, would consume the arrow keys itself.

  **Hard links are not visible over SMB as inode identity, but they are as link count, and neither is the discriminator used.** Measured on the mount: the same unchanged file in `daily.0`, `daily.1` and `daily.2` reports three different inode numbers (nothing in the mount options gives stable server inodes) while `nlink=10` on each, and a file changed that night reports `nlink=1`. The count alone cannot say *which* snapshot a file changed in, so `list` compares each entry against the next-older snapshot on **size and whole-second mtime** -- rsync's own quick check, and therefore exactly the rule `--link-dest` applied when it decided whether to link. Entries the older snapshot had and this one lacks are listed as **deleted**, struck through, and opened or restored from the older snapshot. A directory is compared the same way on its own mtime, which moves when its listing changes and not when a file inside is edited, so it is labelled "listing changed" rather than "changed"; an editor that writes through a temp file and rename (nvim) moves the parent's mtime, which is why `.config/sway` shows as changed after an edit to `sway/config`. The "previous" snapshot is by full-resolution mtime, because the daily and the weekly of the same night land within a minute of each other and the order decides which was linked against the other (measured: `weekly.0` four seconds after `daily.3`). Stat over CIFS is effectively free once a directory is listed (127 entries in two snapshots in 70ms cold), so the comparison costs nothing visible.

  Restore copies from the NAS to the same path under `$HOME`. "Keep both" writes `name (backup YYYY-MM-DD).ext` beside the original; "Replace" over a directory is `rsync -a --delete` so the result *is* the snapshot (the dialog says so, since anything added since goes), and over anything else removes the destination and copies. Verified end to end with a scratch directory backed up, changed, and backed up again: the deleted file came back from the older snapshot, keep-both named its copy, replace from an older snapshot restored the older contents, and a directory replace removed what the snapshot lacked.

  **Do not test a snapshot's read-only-ness with `test -w`.** It reads the permission bits, still 0777 from the Synology ACL, and has no visibility into the subvolume being read-only, so it reports the snapshot root and everything under it as writable. An actual `open(O_CREAT)` on the same path returns `EROFS`, which is the test with the power to tell the two apart; deleting one is separately refused, being root-owned and a subvolume wanting `btrfs subvolume delete`. Snapshots live at `/volume1/@sharesnap/<share>/GMT-<offset>-<timestamp>` and are readable from the `backup` account, but `btrfs subvolume list` is not (`Operation not permitted`) and neither is the package's own state under `/var/packages/SnapshotReplication`, so the immutability lock and the schedule can only be confirmed in the DSM UI.
