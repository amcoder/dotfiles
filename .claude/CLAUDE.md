# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Personal dotfiles for a Linux (Debian, Sway/Wayland) and macOS environment. The repo mirrors `$HOME`: `.config/`, `.local/bin/`, `.profile`, and `.zshenv` are symlinked into the home directory, so edits to files here take effect immediately in the live environment — no build or deploy step.

## Commands

- `./install` — symlink all tracked files into `$HOME` (backs up any existing non-symlink files). Must be re-run after adding a **new** file to the repo so its symlink gets created; editing existing files needs nothing.
- `./install --deps` — also install packages (Homebrew bundle from `Brewfile` on macOS, `apt` on Debian/Ubuntu).
- `dot-add <file>` — zsh function (defined in `.config/zsh/dot.zsh`) that moves an existing file from `$HOME` into the repo, symlinks it back, and commits it. Prefer this when bringing a new config file under management.
- `dot-prune` — deletes symlinks under the four managed roots that point into the repo but no longer resolve. `install` runs it after linking, because `ln` never removes anything: renaming a tracked file leaves a dangling link in `$HOME`, and quickshell dies loading one. It only touches links whose target is inside `$DOTFILES_DIR`, so unrelated broken links elsewhere in `~/.config` are left alone.

There are no tests or linters for the repo as a whole. Neovim Lua is formatted with stylua per `.config/nvim/.stylua.toml` (2-space indent, prefer single quotes).

## Structure

- **zsh** (`.config/zsh/`): the root `.zshenv` only sets `ZDOTDIR` to `.config/zsh`; all real config lives there. Plugins are managed by zinit (auto-cloned on first shell start). Load order is documented at the top of `.zshrc`. `install` writes a generated `dotfiles-dir.zsh` (untracked) into `ZDOTDIR` exporting `DOTFILES_DIR`.
- **Neovim** (`.config/nvim/`): kickstart.nvim-style single `init.lua` for options/keymaps, with lazy.nvim loading one plugin spec file per concern from `lua/plugins/`. Add new plugins as a new file in that directory. `lazy-lock.json` pins plugin versions.
- **Themes** (`themes/`, repo root — deliberately outside the four paths `install` symlinks): one palette per theme (`catppuccin-macchiato.json`, `nord.json`) plus `templates/`, from which `.local/bin/theme` renders every app-specific config. The selection lives in `$XDG_STATE_HOME/theme/current` and the rendered files land in `~/.config`, so switching themes never dirties the repo; `install` ends by running `theme apply`, defaulting to catppuccin-macchiato. Use `theme list`, `theme current`, `theme set <name>`, `theme apply`.

  Templates are written against a role vocabulary that reuses Catppuccin's 26 colour names as generic roles (`crust`/`mantle`/`base`, `surface0-2`, `overlay0-2`, `subtext0-1`, `text`, and 14 accent names) because it is the superset; themes with fewer colours map several roles to one hex. Placeholders are `{{role}}` (`#rrggbb`), `{{role_raw}}` (bare hex, for swaylock and Qt ARGB) and `{{role_rgb}}` (`r,g,b`, for kdeglobals) — `{{ }}` rather than `$` so sway's own `$var` syntax survives. Adding a theme means one JSON file; adding an app means a template plus an entry in `TARGETS`.

  Generated files go where each app already looks, never to a central directory, so nothing has to resolve a `~` or an absolute path — GTK's `@import` takes a URL with no `~`, and sway resolves a relative `include` against the config's own directory. Each theme also declares `"appearance": "dark" | "light"`, which `theme` applies as real desktop state, not just colours: `gsettings org.gnome.desktop.interface color-scheme` (which xdg-desktop-portal exposes as `org.freedesktop.appearance`, and which is what Electron apps such as Claude desktop follow), plus `gtk-application-prefer-dark-theme` in the generated `gtk-{3,4}.0/settings.ini`. Because it is state rather than a reload, `apply_appearance` runs even under `--no-reload`, so `install` leaves a fresh machine in the right mode. The `gtk-theme` bounce that forces GTK to re-read the palette must pass through a theme of the *same* appearance (`Adwaita-dark` for dark) — bouncing via light `Adwaita` leaves the whole desktop light if the run is interrupted between the two `gsettings` calls.

  The GTK3 palette is not written to `~/.config/gtk-3.0/gtk.css`: GTK3 loads that file exactly once, when the app starts, and re-reads it neither on a file change nor on a theme change, so every running GTK3 app — Chrome above all — kept the palette it launched with until it was restarted. Instead `theme` generates a whole GTK theme at `$XDG_DATA_HOME/themes/dotfiles`, whose `gtk-3.0/gtk{,-dark}.css` is an `@import` of `gtkTheme`'s stylesheet followed by our `@define-color` lines (a later definition wins), and points `gtk-theme` at it. That one GTK re-reads from disk on every `gtk-theme` set, which is what the bounce in `apply_appearance` is for — the generated theme's name never changes, so without the detour through `Adwaita-dark` gsettings emits no change at all. Verified end to end: a running Chrome with the GTK theme selected repaints across macchiato → latte → nord with no restart.

  The theme provider sits *below* `~/.config/gtk-3.0/gtk.css` in GTK's cascade, so that file must not also carry the palette — a stale in-memory copy would mask the generated theme in every app started before the switch. `prune` deletes it from the manifest of an older `theme` run, but a process already holding it needs one restart. GTK4 is unaffected by all this and keeps its palette in `~/.config/gtk-4.0/gtk.css`, because libadwaita ignores GTK themes entirely and reads only that file — GTK4 apps still need a restart.

  `gtkTheme` names the base theme the generated one imports, and must be an existing directory under `~/.themes`, `$XDG_DATA_HOME/themes` or `/usr/share/themes`, exactly — the names are case-sensitive and the installed adw-gtk3 build is lowercase `adw-gtk3-dark`, not `Adw-gtk3-dark`. A name that does not resolve leaves the generated theme with colours but no widget rules, so GTK falls back to its built-in Adwaita; `theme` warns rather than trusting the string, and the generated CSS falls back to the built-in Adwaita resource so apps stay styled.

  Where an app has no include mechanism (`kdeglobals`, `gtk-4.0/gtk.css`, `gtk-{3,4}.0/settings.ini`, `swaylock/config`) the whole file is generated and is no longer tracked; the generator unlinks a leftover repo symlink before writing, since `install` never removes stale links. bat reads `BAT_THEME` from the generated `zsh/theme.zsh`, and nvim reads `lua/theme.lua`.

  zsh picks up a switch without restarting: `.zshrc` defines `theme-reload`, a precmd hook that watches `theme.zsh`'s mtime (via `zstat`, not a forked `stat`) and, when it changes, re-sources it along with everything derived from it — `FZF_DEFAULT_OPTS` and `$P10K_CONFIG`. Re-sourcing the p10k config is what applies the change, since powerlevel10k runs with `POWERLEVEL9K_DISABLE_HOT_RELOAD=true` and the config file ends by calling `p10k reload` itself. The p10k prompt's rounded caps are drawn in reverse video, so the colour *behind* them cannot be "the default background" — it has to be named, which is what `THEME_P10K_EDGE` (the theme's `base`) is for; it must equal the terminal background or every segment sits in a visible box of the wrong colour. `theme apply` also deletes `$XDG_CACHE_HOME/p10k-instant-prompt-*.zsh`, which bakes the old palette into a prompt snapshot that outlives the theme switch.

  tmux is split so the template carries no layout: `templates/tmux.tmpl` generates `tmux/theme.tmux` as nothing but `set -g @thm_<role>` lines, and the tracked `.config/tmux/statusline.conf` holds the whole status line, referencing only `@thm_*`. `tmux.conf` sources the colours first, then the layout. Follow that split when theming another app — a template should be the palette, not the design.

  `statusline.conf` reproduces what the `catppuccin/tmux` tpm plugin used to render (rounded window style, window number on the right, icon flags, and the application + session status modules), with the plugin's option indirection flattened out. It sets options with `-gF`, so `#{@thm_*}` resolves when the file is sourced while a doubled `##{...}` survives to render time — which is why a theme switch has to re-source `tmux.conf`, not just rewrite `theme.tmux`. The session module's prefix-sensitive colour must stay a render-time `#{E:@thm_red}` reference: tmux cannot parse a raw `#rrggbb` inside a `#{?...}` conditional. `message-style` uses `bg=default` rather than overlay0 because that is what the plugin actually drew — its `%hidden CTP_MESSAGE_BACKGROUND` resolves empty on tmux 3.7 — and `status-{left,right}-length` are left at tmux's defaults for the same fidelity reason, so a long session name can still truncate at 40 columns.

  Equivalence with the plugin was checked by standing up two `tmux -L` servers — one running the real plugin with the old settings, one sourcing `theme.tmux` + `statusline.conf` — and diffing all 19 status/window/pane options. The comparison has to resolve `#{@thm_*}` on both sides first: the plugin defers those references while this layout bakes them at source time, and it keeps its status modules in `@catppuccin_status_{application,session}` rather than in `status-right`. Assert the comparison actually ran (non-empty values, expected option count) — a version that silently compared two empty files reported a false pass.
- **Qt/KDE theming** (`.config/kdeglobals`): `sway/profile` sets `QT_QPA_PLATFORMTHEME=kde`, so Qt apps load plasma-integration's platform theme, which takes its palette, widget style, icon theme and fonts from the `[Colors:*]`, `[KDE]`, `[Icons]` and `[General]` groups of `kdeglobals`. Both toolkits use Cantarell 11 for UI text and DejaVu Sans Mono 11 for fixed-width, so Qt and GTK render identically. The GTK half lives in gsettings (`org.gnome.desktop.interface font-name`, untracked dconf) rather than in `gtk-3.0/settings.ini`, so changing one side means changing both. When comparing fonts across the two, measure cap height rather than point size — point sizes are not comparable between typefaces. KDE Frameworks apps (Dolphin, etc.) ignore a qt5ct/qt6ct palette entirely and render fully light under `QT_QPA_PLATFORMTHEME=qt5ct`, so the colour scheme has to live in `kdeglobals` (generated from `themes/templates/kdeglobals.tmpl`). The `.config/qt{5,6}ct` configs remain only for Qt5 apps (VLC), which plasma-integration 6 does not cover — launch those with `QT_QPA_PLATFORMTHEME=qt5ct` if they need theming. KDE apps are single-instance, so testing a `kdeglobals` change needs `killall dolphin` first or the old process' cached config is reused.

  Running Qt apps repaint without a restart because `notify_kde` sends what `plasma-apply-colorscheme` sends: a `ConfigChanged` on `/kdeglobals` (`org.kde.kconfig.notify`) *and* a legacy `notifyChange` on `/KGlobalSettings` (`org.kde.KGlobalSettings`) carrying `PaletteChanged`, `StyleChanged` and `IconChanged` (0, 2, 4). The second one is what actually repaints — plasma-integration's `KHintsSettings` still listens on the KDE4-era interface, and rewriting `kdeglobals` with only the kconfig signal leaves every open window on the old palette. Captured by running `dbus-monitor` against a real `plasma-apply-colorscheme` run, and verified by screenshotting Dolphin across `theme set nord` / `theme set catppuccin-macchiato`.
- **Scripts** (`.local/bin/`): standalone helper scripts, mostly for Sway/Wayland (brightness, volume, output scaling, etc.).
- **Quickshell** (`.config/quickshell/`): the Wayland status bar, built with [Quickshell](https://quickshell.outfoxxed.me/) (QML). It replaces swaybar/i3blocks; sway declares no bar of its own and does not start it directly — `quickshell.service` does, via `sway-session.target` (see the systemd section below). `shell.qml` is the entry point, defining a `PanelWindow` top bar per screen (`modules/bar/Bar.qml`). Colors come from `config/Theme.qml`, which reads the generated `~/.config/quickshell/palette.json` through a `FileView` with `watchChanges`, so a theme switch repaints the bar with no restart; its hardcoded Catppuccin values are only fallbacks for before the file loads. Every colour is still a binding, so `readonly` properties update fine. QML edits hot-reload — but a **new** file (a new singleton especially) needs a full restart, since hot-reload will not register it and the bar dies with "X is not defined". Restarting means `systemctl --user restart quickshell`, and its log is `journalctl --user -u quickshell` rather than sway's `systemd-cat` stream. `swaymsg reload` does not restart the bar, and a theme switch does not reload sway at all.

  The tree is `config/` (`Theme`, `Appearance`, `Paths`, `Icons` — data, no behaviour), `services/` (singletons owning state and `IpcHandler`s, no visuals), `widgets/` (leaf components importing only `config/`), `windows/` (window chrome, adding `services/FocusedScreen`) and `modules/<feature>/`, which may import anything. Quickshell synthesizes a `qmldir` per directory and registers the config root as module `qs`, so `import qs.services` works and singletons auto-register across directories — **do not write a `qmldir` by hand**, which permanently disables synthesis for that directory. `dev.qml` is a second entry point for working on one surface at a time (`quickshell -p ~/.dotfiles/.config/quickshell/dev.qml`); `-p` roots the config at the same directory so `import qs.*` resolves identically. Never instantiate the polkit agent, `SystemTray` or a notification server there — each claims a D-Bus name and would fight the running shell.

  `Theme` is the palette and `Appearance` is the design (fonts, icon sizes, bar height), the same split CLAUDE.md argues for tmux: a theme switch touches only the first. `services/FocusedScreen` resolves the output holding the focused sway workspace and every modal surface binds `screen` to it; it falls back to `Quickshell.screens[0]` because a `PanelWindow` on a null screen fails to map with "no output to auto-assign layer surface to". `windows/ModalOverlay` owns the whole overlay-layer-surface pattern — exclusive keyboard focus, scrim, blocking `MouseArea`, Escape, and a card that is centred or, given an `anchorItem`, hung under it — and its children become the card's column; `PolkitDialog`, `ThemePicker`, `Launcher`, `WindowSwitcher`, `PowerMenu` and every `BarPopup` are built on it, along with `widgets/{Button,TextField,ListRow,FilterList}`. An anchored card re-measures its position on every open, because bar items shift as their neighbours change width — the clock alone moves them every minute. `windows/CountdownDialog` is a `ModalOverlay` too — it lives in `windows/` rather than `widgets/` because a widget may import only `config/`. It is named for what it does rather than `ConfirmDialog`, which stays free for an ordinary wait-for-an-answer dialog.

  `widgets/FilterList` is the search-field-over-a-scored-list behind the launcher, the switcher and the session menu. The caller supplies `source`, a `fields` function returning searchable strings most-significant-first, an additive `weight`, and a full `ListView` delegate that reads `ListView.isCurrentItem` and sets `ListView.view.currentIndex` on hover. Three things it settles that are easy to get wrong:

  - **`fields` falls off multiplicatively** (`fieldFalloff`, 0.55 per position), not by a fixed subtraction. A prefix hit in a long *comment* scores higher than a mid-word hit in a *name*, so a small penalty leaves "chr" ranking some screensaver's description above Google Chrome.
  - **`weight` is added to the score, not used as a tie-break.** Scores are rarely equal, so a tie-break never fires where it matters; adding frecency is what lets a daily-used app outrank an unrelated prefix match. With an empty query every score is 0, so `weight` alone orders the list — which is how the launcher shows frecency order and the switcher MRU order. It also means the *source* order is the final fallback, so `Launcher` sorts its entries by name: unsorted, a fresh install lists apps in `DesktopEntries` scan order.
  - **Home and End are only reachable through `TextField.keyHandlers`.** A `TextInput` accepts them for cursor movement, so a `Keys` handler further up the focus chain never sees them; `keyHandlers` binds `Keys.forwardTo` on the inner input, which gets first refusal on every key. Up/Down/PageUp/PageDown/Ctrl-N/Ctrl-P need no such help — a single-line `TextInput` ignores them and they bubble.

  `searchable: false` drops the field entirely and gives the list focus, which is what frees bare letters for accelerators — `PowerMenu` uses it for the `l`/`o`/`s`/`h`/`r`/`p` mnemonics carried over from the sway `mode $session` block it replaces. `TextField` is a `FocusScope` so `forceActiveFocus()` on the field reaches the inner `TextInput`.

  Renaming or moving a file here needs `./install` (to create the new link) and leaves a dangling old link that `dot-prune` removes — `install` runs it, but a stale link left in place kills the shell at load. `find ~/.config/quickshell -xtype l` must print nothing.

  Icons are vendored Phosphor SVGs in `icons/`, drawn by `widgets/Icon.qml` as `Icon { name: "bell"; color: Theme.yellow }`. `config/Icons.qml` reads the SVG through a `FileView` and caches it (its `Qt.resolvedUrl("../icons")` is relative to `config/`, not to the config root); `Icon.qml` swaps the file's `#ffffff` placeholder fill for the requested colour and hands the result to `Image` as a `data:` URI. Recolouring has to happen in the SVG markup — tinting the rendered image with `MultiEffect` (either `colorization` or an alpha mask) blows out thin strokes at bar sizes until enclosed shapes fill in solid. To add an icon, drop the file from [Phosphor](https://phosphoricons.com/) (regular weight) into `icons/`, replace its `fill="currentColor"` with `fill="#ffffff"`, and re-run `./install`.

  Workspace icons are named by sway: each `set $wsN` in `.config/sway/config` carries a `<span foreground='...'>icon-name</span>`, and `modules/bar/Workspaces.qml` parses the span for the colour and the icon name. Sway only applies renamed workspaces to newly created ones, so after editing those lines, existing workspaces keep their old names until `swaymsg rename workspace` is run or they are recreated.

  The bar is always visible and reserves its own height via `ExclusionMode.Auto`, so windows start below it.

  `services/ThemeService.qml` holds the theme list read from the generated `themes.json` and owns an `IpcHandler` on target `theme`, so `quickshell ipc call theme toggle` opens the picker from a sway keybind ($mod+Ctrl+t); `modules/bar/ThemeToggle.qml` is the palette icon in the bar. `modules/theme/ThemePicker.qml` is the view, instantiated once in `shell.qml` like `PolkitDialog.qml` and drawn on the focused output. Highlighting a row sets `Theme.preview` and `Theme.previewWallpaper`, which override the loaded palette so the running bar and the wallpaper preview that theme. **`commit()` deliberately does not clear the preview** — only `hide()` does, on escape or click-outside. Clearing it at commit drops the desktop back to the old theme for as long as `theme set` takes to write the new palette, which is a blink for the colours and a full-screen flash for the wallpaper; `Theme` ends the preview instead when the new `palette.json` loads. Only quickshell previews live — everything else changes on commit.

  `services/NotificationService.qml` is the session's notification daemon, replacing dunst (stopped and **masked** — `systemctl --user mask dunst`; the local binary, its user unit and its D-Bus service file are left on disk so the rollback is `unmask` + `start`). It owns the `NotificationServer`, the popup queue and a 100-entry history ring buffer persisted to `Quickshell.statePath("notifications.json")`, whose directory is keyed by a hash of the config path — so `dev.qml` gets its own history and cannot clobber the real one. `modules/notifications/NotificationPopups.qml` is the transient stack (bottom-right, overlay layer, on `FocusedScreen.screen`, matching dunst's `follow = keyboard`), `NotificationCentre.qml` the history view on `ModalOverlay`, and `modules/bar/NotificationIndicator.qml` the bell. Sway calls it at `config:297-299` — `$mod+n` invokes the newest notification's default action (what `dunstctl action` did), `$mod+Ctrl+n` opens the centre, `$mod+Alt+n` toggles do-not-disturb.

  Three things about the freedesktop API as Quickshell 0.3.0 exposes it, each established by spike rather than assumed. `Notification.expireTimeout` is **milliseconds** passed straight through from D-Bus, with `-1` meaning "server default" (5s/10s/never by urgency, matching the old `dunstrc`). `notify-send -i <name>` arrives as the `image-path` hint and lands in `notification.image` as an `image://icon/<name>` URL, *not* in `appIcon` — so `image` is the primary icon source and `appIcon` only the fallback. And `trackedNotifications` has not yet been updated when the `notification` signal fires, so the service keeps its own arrays rather than reading that model.

  **Replacing a notification by id mutates the existing `Notification` in place and emits no new `notification` signal.** A record holding a copy of the fields therefore goes stale, which is why `NotificationCard` reads the live object through `entry.notification` and falls back to the stored copy only once the notification is gone (restored from disk, or closed by its sender). `summaryChanged`/`bodyChanged` are the only "this was replaced" signal on offer; they drive re-popping an already-expired notification, moving it back to the top of history, and re-saving.

  The popup cap (5) lives in the view, not the service, so notifications past the cap still expire on their own schedule and are only *hidden* behind an "N more" row — which is what dunst's `indicate_hidden` did. `IpcHandler` functions are `open`/`close`, not `show`/`hide`: `quickshell ipc call <target> show` is swallowed by the CLI's own `ipc show` subcommand (this bites `theme show` too).

  `services/LauncherService.qml` + `modules/launcher/Launcher.qml` replace `wofi --show=drun` and `--show=run`, `services/WindowService.qml` + `modules/switcher/WindowSwitcher.qml` replace `window-switcher.py`, and `services/PowerService.qml` + `modules/power/PowerMenu.qml` replace `system-menu` and its zenity confirmations. Sway calls all three over IPC — `$mod+Space` (`launcher toggle`), `$mod+Shift+Space` (`launcher run`), `$mod+Alt+Space` (`windows toggle`), `$mod+Shift+Escape` (`power toggle`). wofi, zenity, `system-menu`, `window-switcher.py` and `get-icon` are gone, and with them the last PyGObject/GTK dependency; the wofi and zenity binaries are left installed but unused.

  **Apps are launched with `I3.dispatch("exec …")`, never a `Process`.** Sway runs `exec` through `/bin/sh` (so the argv from `entry.command` has to be shell-quoted back into a line), and the resulting process lands in sway's own session scope rather than `quickshell.service`'s control group — verified by reading `/proc/<pid>/cgroup` and by watching a launched window survive `systemctl --user restart quickshell`. As a quickshell child it would be killed with the shell on every restart. `exec` takes no `--`; `I3.dispatch("exec -- cmd")` silently does nothing.

  Four things about `DesktopEntries` in 0.3.0, each established by spike:

  - **The scan starts on the first read of the model and fills in asynchronously.** Reading `DesktopEntries.applications.values` for the first time inside `show()` returns an empty array and opens an empty launcher; the model is only populated a moment later, entry by entry (`valuesChanged` fires per entry). `LauncherService.applications` is a plain binding for exactly this reason — instantiating `Launcher` in `shell.qml` is what warms it at startup.
  - **`command` is already the `%`-code-stripped, shell-unquoted argv.** `execString` keeps `%u`/`%F` and the quoting; `command` is a real string list with them removed. There is nothing to strip by hand.
  - **`NoDisplay=true` entries are excluded from the model already** (277 files on disk, 228 in `values`, `noDisplay` false for all of them), so filtering on `!noDisplay` is a no-op. **`OnlyShowIn`/`NotShowIn` are not applied, and not exposed either** — see below.
  - **New `.desktop` files are picked up at runtime** — no restart needed.

  Because `DesktopEntry` exposes neither `OnlyShowIn` nor `NotShowIn`, `LauncherService` re-reads the `.desktop` files itself in a one-shot `Process` and keeps the ids to hide in `hidden`. This is not pedantry: 107 xscreensaver hacks ship `OnlyShowIn=MATE;` from `xscreensaver-gl`/`xscreensaver-data` under `/usr/share/applications/screensavers/`, and with the lxqt and GNOME control-centre panels they were **129 of 228 entries** — the launcher shows 99 with the filter on. The id is the path below `applications/` with `/` turned into `-`, which is the spec's desktop-file ID and what `DesktopEntry.id` holds.

  **That embedded script must contain no backslash and no `${…}`.** It lives in a QML template literal, where `\/` collapses to `/` and `\[` to `[` — which turns an awk regex into a syntax error, and since the failure is on stderr the only symptom is that nothing gets filtered. The awk is written with `index()`/`substr()` and string-form regexes for exactly this reason, and the shell side splits `XDG_DATA_DIRS` with `IFS=:` rather than `tr : '\n'`. The scan runs once at startup, so a desktop-restricted entry installed mid-session is not re-checked.

  `Quickshell.iconPath(name, true)` returns `""` when the icon is missing, and `Quickshell.iconPath(name, fallbackName)` returns a URL carrying `?fallback=`, which is what the launcher and switcher use so a missing app icon still renders something. It logs a burst of `qt.svg.draw: The requested buffer size is too big` for a handful of oversized system SVGs on the first open after a restart, then never again — Qt caches per icon.

  **The window switcher takes its list from sway's tree, not `ToplevelManager`**, which has no workspace concept. `Quickshell.I3` exposes only `workspace` and `output` events through `rawEvent`, so `WindowService` runs a `swaymsg -r -t subscribe -m '["window","workspace"]'` of its own (`-r` gives one JSON object per line, which `SplitParser` wants) and re-reads `get_tree` on every event, debounced 40ms. There is no hand-maintained MRU: **sway's per-container `focus` arrays are the focus history**, so walking children in that order yields the MRU list directly and it cannot drift. The switcher preselects row *1*, not 0 — row 0 is always the focused window, so starting below it makes a single press an alt-tab.

  `StdioCollector`'s **`data` is a byte array; the string is `text`.** `JSON.parse(data)` happens to work because it coerces, so a `get_tree` collector reads fine and a `data.split("\n")` on the next one throws `Property 'split' ... is not a function` and silently leaves the list empty. Use `text`.

  Frecency lives in `Quickshell.statePath("launcher.json")` as `{ id: { count, last } }`, weighted by recency bucket (<1d ×4, <7d ×2, <30d ×1, older ×0.5). Desktop actions (`entry.actions`) appear as indented sub-rows, but only once there is a query — with none they would pad the list with rows nobody asked for, which is why wofi hid them outright (`no_actions=true`). Run mode lists every executable on `PATH` and falls back to running the typed line verbatim, so a command with arguments still works.

  `PowerService` deliberately drops "Reload Sway": it existed only to re-read theme colours, which `theme` now applies with targeted `swaymsg client.*` commands, and a reload is lockup trigger #1. `windows/CountdownDialog` inverts what zenity did: its `countdown` (seconds, `PowerService.confirmSeconds`, one value for every action) ticks down and fires `accepted` at zero, so waiting confirms rather than cancels and the dialog is an announcement with an escape hatch, not a question. That is also why the actions carry a `confirm` flag rather than a question string — "Are you sure you want to reboot?" above "Reboot in 8 seconds" asks something the dialog then answers itself. The **accept** button holds focus, not Cancel — picking an action in the menu and pressing Return again goes straight through, which is the point of a dialog that was going to proceed anyway. That in turn is why `widgets/Button` ignores `event.isAutoRepeat`: the dialog opens under a Return that may still be held, and at sway's default 600ms repeat delay the repeat would otherwise land on the freshly focused button and skip the countdown entirely. The menu closes before anything is dispatched, so a polkit prompt never contends with it for exclusive keyboard focus.

  `services/{AudioService,BrightnessService,OsdService}` + `modules/osd/Osd.qml` replace `.local/bin/volume` and `.local/bin/brightness`, and with them the notify-send-as-OSD pattern that used to put every volume keypress into notification history. Sway calls them on the media keys — `quickshell ipc call audio up|down|mute|micMute` and `brightness up|down`. pamixer and brightnessctl are left installed but unreferenced.

  There is **one** OSD surface, not one per source: `OsdService` holds only `active` and a `source` name plus the 2s timer, and `Osd.qml` owns the three descriptors, so a volume keypress and a brightness keypress a moment apart replace each other rather than stack. It sits bottom **centre**, where the notification stack (bottom right) cannot collide with it, and is click-through via `mask: Region {}` — an overlay layer surface otherwise swallows every pointer event in its geometry for its whole lifetime.

  **A QML singleton is created when it is first referenced.** A service reached only over IPC therefore never registers its `IpcHandler` — `AudioService` and `BrightnessService` instantiated nowhere loaded clean and did nothing, with `quickshell ipc show` listing neither target. Referencing them inside a conditional is not enough either, since JS short-circuits; `Osd.qml`'s three descriptors are unconditional bindings, evaluated at completion, and that is what brings both services to life. Anything IPC-only in future needs the same.

  `AudioService` reads Pipewire, and two things about it: `Pipewire.defaultAudioSink` is **null at `Component.onCompleted`** (`ready` false), so every read is `?.`-guarded; and without the `PwObjectTracker` a node reports its defaults rather than real values. `PwNodeAudio.volume` (0..1) is the same scale pamixer printed, so the 0.05 step is exactly the old `pamixer -i 5`. Up and down unmute first, as the script did.

  `BrightnessService` writes `/sys/class/backlight/*/brightness` directly — it is `root:video 0664` and the user is in `video`, so no brightnessctl. The write needs **`atomicWrites: false`**: FileView's default write-to-temp-then-rename is refused by sysfs. `watchChanges` + `onFileChanged: reload()` is what picks up the firmware's own hotkeys, and `onSaveFailed: reload()` is what stops the optimistic `level` in `set()` from lying when a write is refused — a refused write leaves the file unchanged, so nothing else would correct it. The device is discovered asynchronously by a one-shot `ls -1 /sys/class/backlight | head -1`, which works because **a `FileView` with `path: ""` is silent** (no load, no error); until `max_brightness` loads, `available` is false and the keybinds do nothing. The step is brightnessctl's `10%` of the full range, and the floor is one raw unit rather than zero, deliberately: a panel at zero is indistinguishable from a session that has died.

  `widgets/LevelBar` is the read-only fill bar both the OSD and `NotificationCard`'s `-h int:value:` progress draw; `widgets/Slider` is the same bar with a grab, and the caller keeps `value` bound to its own state and writes through the `moved` signal so the binding is never broken.

  `modules/bar/Volume.qml` + `modules/audio/AudioPanel.qml` replace **pasystray** (`config:85`, gone). The bar item is icon + percentage — click toggles the panel, middle-click mutes, wheel adjusts without the OSD, since the number the OSD would show is already on the bar. The panel is output and input level rows, the two device lists, per-app stream volumes, and an "advanced…" link to `pavucontrol` for everything Pipewire exposes that this does not (routing, profiles, moving one app to another device) — which is why the `pavucontrol` floating rule stays.

  `services/BluetoothService.qml` + `modules/bar/Bluetooth.qml` + `modules/bluetooth/BluetoothPanel.qml` replace **blueman-applet** (`config:86`, gone, along with the dead `blueman-services` / `blueman-sendto` window rules). The panel is adapter power, then the paired devices — click to connect or disconnect, hover for a forget `x`, battery percentage where BlueZ offers one. `Quickshell.Bluetooth` reports a freedesktop icon name per device class (`audio-headset`, `input-mouse`, `phone`, …) which `deviceIcons` maps onto vendored Phosphor icons, falling back to `bluetooth`.

  **Quickshell 0.3.0 registers no `org.bluez.Agent1`** — the binary carries `Adapter1`, `Device1` and `Battery1` and nothing else — so it cannot answer a PIN or a confirmation and `pair()` is unreliable by construction. That alone keeps **pairing and discovery out** of the panel; a second reason, that a scan list could not refresh inside a size-locked popup, no longer applies now that `BarPopup` is a layer surface. "advanced…" launches `blueman-manager`; that D-Bus-activates `blueman-applet` (`SystemdService=blueman-applet.service`), which *is* the agent, and both exit when the window closes — verified by killing every blueman process, opening the panel's link, and watching the applet reappear under `user@1000.service` and then go away again. No tray icon comes back with it, so nothing duplicates the bar item.

  The device list is sorted **by label alone**, never connected-first: sorting by state means clicking a device reorders the list under the cursor, sliding the next row — and the forget `x` that appears on hover — under the pointer. Same reasoning as the audio panel's device lists, one degree worse because here the click is what triggers the move.

  `services/NetworkService.qml` + `modules/bar/Network.qml` + `modules/network/NetworkPanel.qml` cover the part of **nm-applet**'s menu that got used: the wifi radio, the access points in range, the wired link, and the saved VPNs, with "advanced…" launching `nm-connection-editor`. The bar item is the signal-strength icon plus a green `shield-check` badge whenever a VPN is up.

  **nm-applet itself keeps running, and `exec nm-applet` stays in the sway config.** It is NetworkManager's *secret agent*, and Quickshell registers none — the binary has zero `SecretAgent` strings — so without it an 802.1x network fails silently and the `Lytx` openconnect VPN cannot connect at all, its cookie, gateway and cert secrets all carrying `flags = 2` (never saved, ask the agent every time). Unlike blueman-applet it has **no D-Bus service file**, so it cannot be summoned on demand the way `blueman-manager` summons the BlueZ agent; it has to be resident. What changes is only that `Tray.qml` now filters its item out by `id` (`"nm-applet"`, read off its SNI `Id` property) so the bar does not show two network indicators. That `hidden` list is the place to drop any other applet kept alive purely for a D-Bus role.

  `scannerEnabled` is off until the panel opens, and the list then goes from 1 entry to all of them over about five seconds. It fills a fixed-height `ListView` (`listRows` × `rowHeight`) that scrolls: originally because a popup could not resize, now because a list that grows under a stationary cursor moves the row you were about to click. Same reason `FilterList` has `fixedHeight`. The password prompt for an unknown WPA network replaces that list inside the same box rather than being appended below it: the card is free to grow, but growing it would shift the rows at the moment one was clicked. Escape is handled on the prompt itself so it puts the list back instead of bubbling to the card and closing the whole panel.

  Access points are sorted **by name alone**, the 8b rule one degree stronger again: signal strength moves on its own every few seconds, so sorting by it slides rows under a stationary cursor with no click involved at all.

  Quickshell 0.3.0's `Networking` has no VPN concept, so that half is nmcli: `nmcli monitor` as the change signal, debounced 200ms into a one-shot `nmcli -t -f NAME,UUID,TYPE,STATE connection show`, filtered to `vpn` and `wireguard`. `-t` escapes a literal colon in a field as `\:` and only the name can contain one, so the fixed trailing fields are split off the **right**. Verified end to end against a throwaway wireguard connection: adding and removing it moved the panel's list live, an external `nmcli up` lit the row and the bar badge, and clicking the row brought it back down.

  Two things about `Quickshell.Networking`, both established by spike:

  - **The model starts loading on the first read and fills in asynchronously**, exactly as `DesktopEntries` does. Read at `Component.onCompleted` it reports `devices: 0`, `wifiEnabled: false` and `connectivity: Unknown`, and is only right a second or two later — so every value is a binding and `Network.qml` in the bar is what warms it at startup.
  - **`networks` holds only the connected AP until `scannerEnabled` is set**, so the visible-network list does not exist until something asks for it.

  **A signal handler written at the instantiation site replaces the component's own**, it does not run alongside it: an `onVisibleChanged` next to `NetworkPanel { … }` in the bar silently overrode the one in `NetworkPanel.qml`, which is why the scan toggle lives in the panel with the prompt reset it shares a handler with.

  `windows/BarPopup` is the chrome behind all three panels: children stack in a column and the card sizes to them. It is a `ModalOverlay` with an `anchorItem` — an overlay layer surface hung under a bar item — and **not** a `PopupWindow`, which is the single most important thing about it.

  **A `PopupWindow` can never hold keyboard focus.** It has only `grabFocus`, which is the pointer grab; keys go to the *parent* layer surface, which is a different window, and Qt delivers key events only to the focused one. A text field inside a popup therefore shows a caret and then never receives a character, Escape never arrives, and — because sway will not honour the popup's grab either — clicks outside it land in whatever is under the bar instead of dismissing it. Measured with `Window.active`, calibrated against the launcher: an open `ModalOverlay` reads `true`, an open `PopupWindow` reads `false` even with its parent bar surface set to `Exclusive`. This is what the panels were originally built on, and it is why the network password prompt could not be typed into.

  **`WlrLayershell.keyboardFocus` is applied when the layer surface is created and ignored on every later change.** Setting the bar to `Exclusive` only while a popup was open changed nothing (`kb=1`, still `active=false`); the same constant set before startup made the bar active immediately. So a surface that wants the keyboard *some* of the time holds a constant `Exclusive` and toggles `visible` — which destroys and recreates the surface — which is exactly what `ModalOverlay` has always done and why the launcher works.

  Two consequences worth keeping. A `PanelWindow` is **visible by default**, so a dropdown must say `visible: false` or it maps at startup as a full-screen overlay and silently swallows every click meant for the bar. And `ModalOverlay`'s card holds `focus: true` itself, so Escape lands even with no `focusItem`; where there is one, focus moves to that child and Escape still bubbles back up.

  Because the card is now an ordinary layer surface it may **resize freely while open**, which an xdg_popup may not: `PopupWindow` takes its geometry when it maps and never again (`implicitHeight` went 762 → 728 across a bluetooth scan while `height` stayed 762, and `reposition()` does not re-send it). That constraint is gone, so the bluetooth scan list kept out of `BluetoothPanel` for this reason could come back, and the network list's fixed height is now a choice rather than a requirement. Being an overlay, an open panel also covers the bar, so a click anywhere outside the card — including on another bar item — dismisses it rather than reaching what is beneath. `AptUpgrade` still hand-rolls a `PopupWindow` and should move onto `BarPopup`, but only when there is an upgradable package to open it with.

  Three things about `Quickshell.Services.Pipewire`, each established by spike:

  - **A node's `type` is readable untracked; its `audio` values are not.** An untracked node reports `volume: 0` and `ready: false` but its type flags are already right, so `AudioService`'s three lists filter on `type` (`AudioSink` 17, `AudioSource` 9, `AudioOutStream` 21 — a playback stream is `isSink` *and* `isStream`) and the `PwObjectTracker` then tracks what they select. Filtering on `audio` instead is circular: the tracker would have nothing to track and the lists would stay empty for good.
  - **`nodes.values` is registry order, and it is not stable.** A device that re-registers — an HDMI sink following a monitor — comes back at the end of the list, so the rows reshuffle under the cursor between opening the panel and clicking a row. Both device lists are sorted by label.
  - **Writing `preferredDefaultAudioSink` is the whole of "set the default device"**; it lands in wireplumber's `default.configured.audio.sink`. WirePlumber may then decline it — an HDMI output with nothing plugged in stays refused, and `pactl set-default-sink` on the same node is refused identically — so the tick follows the *effective* default rather than what was clicked, which is the honest reading.

  `windows/Wallpaper.qml` is the desktop background, one layer surface per screen, replacing swaybg. It reproduces swaybg's `center` mode exactly — the image at its native size, centred and clipped, over `Theme.crust` — so `sourceSize` is deliberately left unset: `center` means no scaling, and binding it to the screen would silently start resampling. Two stacked `Image`s crossfade on a theme switch, and **both ends animate**, because the wallpapers are not all the same size (nord's is 1920×1080, the rest 3840×2160) and a smaller incoming image would not cover the one it replaces. The fade starts on any `Image.status` that is not `Loading`, so a theme naming no wallpaper (`Null`) or a missing file (`Error`) still fades the old image out instead of stranding it.

  **The layer is `WlrLayer.Bottom`, not `Background`** — which is where swaybg itself sits. Sway draws same-layer surfaces in creation order and `theme set` re-forks swaybg over IPC, so a `Background` surface ends up *under* a solid-colour swaybg started after the shell, and the wallpaper vanishes until the next restart. Established by spike: with both on `Background`, re-running `swaymsg output '*' bg <colour> solid_color` painted the whole screen that colour; on `Bottom` the image survives, and windows still draw above it. `mask: Region {}` keeps it click-through, as swaybg's empty input region was.

  Wallpapers are PNGs in `wallpapers/`, named by the `wallpaper` key of each theme JSON (carried into `themes.json` for the picker) and resolved against `Paths.wallpapers`. **They carry no background of their own** — it is knocked out to transparency, so `Wallpaper`'s `color: Theme.crust` fills both the letterbox and the area behind the artwork and the two cannot disagree. They used to: every Catppuccin wallpaper was painted against `#1e1e2e`, which is *Mocha's `base`* and not any theme's `crust`, so frappé, macchiato, mocha and latte all drew a visibly different rectangle inside the letterbox. Knocking the background out rather than repainting it to each crust keeps the image independent of the palette, so it stays right if a crust ever changes or a new theme points at an existing image.

  The knock-out has to recover alpha, not just replace a colour: a colour replace leaves every antialiased edge still blended against the old background. Treat each pixel as `a*fg + (1-a)*bg` for the known flat `bg` and take the smallest alpha that keeps `fg` in range — the standard unmatting solution — which recomposites over the original background to within 1/255. Write the result paletted when it fits in 256 colours, which four of the five do: `cat-blue-eye.png` was already a PNG8 and saving it as truecolour RGBA tripled it, while paletted output leaves the five within +7% in total. `themes/unmat-wallpaper <in> <out> <#bg>` does all of it — it lives in `themes/` with the palettes rather than in `.local/bin`, since like the templates it is authoring input and is never symlinked into `$HOME`. Adding a wallpaper means running it once with the image's own flat background colour. The picker previews them, and **the crossfade is suppressed while it does** — `previewing` is `Theme.previewWallpaper !== ""`, and a preview swap is instant. The colours preview instantly and cannot be animated in step, so a fading wallpaper lags the highlighted row — arrowing faster than the fade leaves the previous theme's artwork ghosting under the current one, a step behind the selection. The rule that falls out is that **the crossfade is for changes nobody watched happen** — committing from the picker is instant because you already saw it, and a `theme set` from a terminal fades. Decoding is not the constraint it looks like: a cold 3840×2160 PNG is 13-43ms and a re-visited one costs nothing at all, since a cached image produces no `Image.status` transition. `sway.conf.tmpl` ends at `output * bg $background solid_color`, which overrides the Debian default in `/etc/sway/config.d/40-sway-background.conf` and is what shows during a shell restart.

  `quickshell ipc call` costs ~31ms a call, against sway's default 40ms key repeat, so holding a volume key keeps up without a long-lived socket.

  `modules/polkit/PolkitDialog.qml` is the session's polkit authentication agent, replacing `polkit-kde-authentication-agent-1`. It is instantiated once in `shell.qml` (not per screen) and draws a modal dialog on an overlay layer surface with exclusive keyboard focus, on whichever output holds the focused sway workspace. Quickshell's `PolkitAgent` registers on startup, so nothing in the sway config launches an agent. Quickshell does not forward PAM's own failure text — it only logs "Unknown line ... from helper" — so a rejected password is reported from `AuthFlow`'s `authenticationFailed` signal instead.

  `lock.qml` is the session lock, and it is deliberately a **second process** with its own unit (`quickshell-lock.service`, started on demand by `.local/bin/lock`, never part of the session target). If the shell held the `WlSessionLock` and crashed, sway would keep the session locked — the protocol's guarantee — and leave a black screen with nothing to type into; isolating it means every bar edit and `systemctl --user restart quickshell` is lock-safe. `services/LockService.qml` owns the `PamContext` (`config: "swaylock"`, which on Debian is `@include common-auth`) and `modules/lock/LockSurface.qml` is the per-screen view, instantiated by `WlSessionLockSurface` for a real lock and by one overlay `PanelWindow` under `QS_LOCK_DEMO` — demo mode is where all layout work happens, since Escape always closes it.

  **`Quickshell.env()` returns `null` for an unset variable, not `""`.** `env("QS_LOCK_DEMO") !== ""` is therefore true when the variable is *unset*, which silently put every real lock into demo mode and drew an escapable overlay instead of locking. It is `!!env(…)` now; anything reading an optional env var wants truthiness, not a comparison against `""`.

  **`WlSessionLock.secure` is the "surfaces are up" signal.** `LockService` writes `$XDG_RUNTIME_DIR/quickshell-lock.stamp` on it and `lock` polls for that before returning, so `before-sleep` cannot suspend over a half-mapped surface; `lock` removes the stamp *before* starting the unit, which is what makes waiting for it meaningful. If nothing maps within 2s it falls back to `swaylock -f`, which is why swaylock and `swaylock.conf.tmpl` stay installed. **sway accepts a replacement lock client for an abandoned lock** — `SIGKILL` while locked leaves the session locked, and a fresh client maps and re-confirms `secure` — so `Restart=on-failure` is real crash recovery, and from a VT `systemctl --user start quickshell-lock.service` is the way back to a prompt. The unit sets `StartLimitIntervalSec=0` deliberately: a unit that gives up restarting leaves a locked session nobody can type into.

  `services/IdleService.qml` owns idle policy, which used to be swayidle's `timeout` — dim at 240s (`modules/idle/IdleDim.qml`, click-through so the input that dismisses it still reaches the window underneath), lock at 300s. swayidle survives only as a policy-free adapter for logind's Lock/Unlock/PrepareForSleep signals, which Quickshell 0.3.0 cannot hear itself. **Screen-off is a paint, never a modeset** — `IdleDim`, plus `LockService.blanked` blacking the lock surface after 60s — because `output power off` is lockup trigger #2.

  `IdleMonitor.respectInhibitors` **does** honour other clients' Wayland idle inhibitors (sway enforces it compositor-side), but only when the inhibitor is attached to a visible *view*: one on a layer surface is ignored, so quickshell's own surfaces cannot inhibit idle. It does not see *logind* inhibitors, which is what `.local/bin/noidle` and `InsomniaService`'s third mode create — and neither did swayidle, measured, so those have never prevented the screen locking and only their `sleep` half ever did anything. Now that idle policy shares a process with Insomnia, `IdleService` reads `InsomniaService.mode.inhibitIdle` directly and disarms both monitors. Cross-service references need no import: same directory, same synthesized `qs.services` module.

  Testing a real lock without risking the desktop means a **nested sway** (`sway -c <minimal>` as a window in the session). One trap: the nested compositor's IPC socket is usually found by mtime, and when that sway exits the lookup falls through to the **real** session's socket — so the next `swaymsg exec` locks the desktop you were protecting. Bind the socket once and assert the nested compositor is still alive before each call.
- **Session services** (`.config/systemd/user/`): the shell runs under systemd, not as a sway `exec`. The sway config starts `sway-session.target`, which `BindsTo` + `PropagatesStopTo` `graphical-session.target` and so pulls in `quickshell.service` (`Restart=always`, `StartLimitBurst=5`) plus the machine-local `poweralertd` and `wayland-pipewire-idle-inhibit` units already sitting in `graphical-session.target.wants/`. This keeps `swaymsg reload` and every theme switch out of the shell's lifecycle, and out of the DRM modeset path described in `.claude/sway-lockup-investigation.md`.

  The user manager never sources `~/.profile`, so the XDG base directories and `~/.local/bin` are declared in `.config/environment.d/10-xdg.conf` — without them `theme` and the `sway-*` scripts are unreachable from any user unit. `environment.d` rather than `Environment=` lines because it covers every unit at once, expands `${HOME}`/`${PATH}`, and applies on a plain `daemon-reload`. Files there merge by filename across all `environment.d` directories, so nix's unprefixed `nix-daemon.conf` sorts after `10-xdg.conf` and re-prepends its own paths. `quickshell.service` keeps only `QT_QPA_PLATFORM=wayland` and `QT_QPA_PLATFORMTHEME=kde`, which are about how the shell renders and used to be inherited from `sway-run` and `sway/profile`.

  `wayland-pipewire-idle-inhibit.service` is tracked here too. Any unit added to this target needs `PartOf=graphical-session.target`, not just `WantedBy=` in `[Install]` — `WantedBy` starts it with the session but never stops it, and a `Restart=always` unit then spins against a dead compositor for the whole logout window.

  The sway side is one quoted `exec` that chains the environment import into the target start: `/etc/sway/config.d/50-systemd-user.conf` imports `SWAYSOCK` in a *separate* `exec`, and sway launches execs asynchronously, so the target can otherwise start before the socket is in the manager's environment. The quotes are load-bearing — unquoted, sway parses `&&` (or a `;`) as the start of a second command and logs `Unknown/invalid command`.

  `PropagatesStopTo` is load-bearing and easy to lose: `BindsTo=B` only stops A when B stops, never the reverse, so without it `systemctl --user stop sway-session.target` leaves `graphical-session.target` and every service under it running — and `sway-run`'s teardown silently does nothing.

  `quickshell-lock.service` is tracked here too but has **no `[Install]` section**: it is started on demand by `lock`, never pulled in by the target. It is `PartOf=graphical-session.target` so it still dies with the session.

  `install` ends with `systemctl --user daemon-reload` and `systemctl --user enable quickshell.service`, guarded on `-d /run/systemd/system` so macOS skips it; symlinking a unit is not enough, `WantedBy=` only applies once enabled. Editing an existing unit still needs a `daemon-reload`.
- **Sway**: expects a system-level `/usr/local/bin/sway-run` launcher (documented in README, not tracked here) that exports Wayland env vars, sources `.config/sway/profile`, and runs sway **without** `exec` so it can `systemctl --user stop sway-session.target` on exit — otherwise quickshell outlives the compositor and `Restart=always` spins.
